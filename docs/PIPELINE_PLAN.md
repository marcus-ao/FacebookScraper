## 0. 一句话结论

这个项目现在有 **四个各自完好、互不相连的阶段**，而且**没有任何东西在自动跑**——
计划任务至今没有安装（E3 故意留给用户按）。

把它们连起来**不需要新建队列**，需要一个**对账器**（第 2 节）。

而真正决定"人要干多少活"的**不是编排，是分流规则**（第 6 节）。
编排最多把四条命令变成一条；**分流规则才能把"每篇都要人"变成"每类只要人一次"**。

按第 11 节的估算：稳态下人工投入可以从**约 90 分钟/周降到约 10 分钟/周**，
而其中剩下的 10 分钟里，**没有一分钟是可以再省掉的**——它们全都落在
第 4.1 节那三条不可消除的事情上。

## 1. 现状盘点：四个孤岛，底子出奇地好

| 阶段 | 现在怎么触发 | 幂等 | 断点判据（**内容寻址**） | 失败怎么被发现 |
|---|---|---|---|---|
| 回填 | 人工滚一次，**已完成** | — | `_capture_*.json` | — |
| **增量** `routes/delta.py` | ⛔ **计划任务未装，纯手工** | ✅ `should_append()` | `manifest.jsonl` / `post.json` | ✅ toast + `alerts.log` + `delta.log` + `delta_state.json` |
| **翻译** `translate.py` | 手工命令 | ✅ | `post_id + 正文指纹 + PROMPT_VERSION` | ⚠️ **只在终端**，跑完就没了 |
| **调图** K 组 | 未实现 | 设计有 | `post_id + media_index + 原图指纹 + 译文指纹 + 版本` | 未定 |
| **发布** G 组 | 未实现 | 设计有 | `post_id + 平台` | 未定 |
| 完整性 `core/integrity.py` | 内嵌在增量里 | ✅ 只报新问题 | `delta_state.alerts` | ✅ 同增量 |

**这里有一件运气很好的事，值得点破**：

> **四个阶段的"做完了没有"全都是内容寻址的**——不是"跑过了"，
> 而是"**这份内容 + 这个版本**的产物存在"。
> 正文改了、提示词版本升了、原图被补全了，下游自动过期。

这正是对账器所需要的全部前提，而它是**在没人打算做对账器的时候自然长出来的**——
因为每一组都独立遵守了同一条纪律：**真相在文件里，索引是派生的**。

**所以缺的不是能力，是连接。** 现在的形态是：

```
人：跑 delta   →  人：跑 translate  →  人：跑 images  →  人：跑 publish
    ↑ 每一步都要人记得、要人看输出、要人判断该不该进下一步
```

## 2. 为什么是「对账器」而不是「队列」

**队列的做法**：delta 抓到新帖 → 写一条待办 → 翻译消费 → 写下一条待办 → ……

**不要这样做。** 三个理由，第一个是这个项目自己的教训：

1. **队列会和现实脱节。** 这个项目已经为此立过一条铁律：
   「`post.json` 是真相，`manifest.jsonl` 是派生索引，冲突时以文件夹为准，
   **方向永远单一**」。队列是第二个真相源，一旦它和归档不一致，
   就退化成"两个都不可信"——`manifest` 那次已经演示过代价了。
2. **失败恢复要额外机制。** 队列要重试计数、死信、超时回收。
   对账器不需要：**没做完的下次自然又被算出来**。
3. **新增阶段要改协议。** 对账器加一个阶段只是多一个谓词。

**对账器的做法**：每次运行时，对每一篇帖子算一次

```
期望状态：已归档 → 有当前版译文 → 有当前版德语图 → 已排期发布
实际状态：从 manifest.jsonl / translated.jsonl / images_de.jsonl / published.jsonl 读
差值    ：这篇卡在哪一阶段
动作    ：推进它能推进的那一步；推不动就归类到"为什么推不动"
```

**没有队列文件，没有状态机，没有重试计数。** 全部信息都已经在盘上。

> ⚠️ 一个必须守住的边界：**对账器只读四份产物、只调各阶段已有的入口。**
> 它不许自己解析响应、不许自己拼提示词、不许自己点浏览器。
> 一旦它开始"顺手做一点"，它就成了第五个真相源。

## 3. 目标架构

```
                       ┌──────────────────────────────────┐
   计划任务（每天一次）  │  pipeline run                     │
   ── 触发 ───────────▶ │  ①对账 ②按顺序推进 ③分流 ④汇报    │
                       └──────────────────────────────────┘
                                     │
        ┌────────────┬───────────────┼───────────────┬──────────────┐
        ▼            ▼               ▼               ▼              ▼
   routes.delta  translate.py  localize_images.py  publish/     needs_human
   （带抖动）     （带预算闸）    （带预算闸）      （带确认闸）   （人工队列）
        │            │               │               │              │
        ▼            ▼               ▼               ▼              ▼
   manifest.jsonl translated.jsonl images_de.jsonl published.jsonl  review.html
        └────────────┴───────────────┴───────────────┴──────────────┘
                                     │
                          state/pipeline_state.json
                        （心跳 · 各阶段积压 · 成本 · 死人开关）
```

**新增的东西只有三样**：

| 新增 | 是什么 | 为什么非有不可 |
|---|---|---|
| `pipeline.py` | 对账器 + 唯一编排入口 | 现在四条命令要人记得 |
| `state/needs_human.jsonl` + `needs_human.html` | **把"人"变成一个阶段，而不是一次中断** | 见第 5 节 |
| `state/pipeline_state.json` | 心跳 + 积压 + 成本 + **死人开关** | 见第 7 节，这是当前最大缺口 |

**沿用已被验证的做法，不发明新的**：
`needs_human.html` 走 `tools/layout.py::index` 那条路子（**双击就能看**，
用户已经在用 `index.html` 了）；状态文件走 `delta_state.json` 的形态；
告警走 `core/notify.py` 的三级降级。

## 4. 人工干预的诚实清单

**"人为干涉尽可能少"的正解不是砍掉闸门，是让闸门按"类"触发而不是按"篇"触发。**
下面把每一处人工都摊开，标明它属于哪一种。

### 4.1 ⛔ 不可消除的三条（不要试图自动化，它们是承重墙）

| # | 人工 | 频率 | 为什么不能自动化 |
|---|---|---|---|
| 1 | **登录**（抓取小号 / 发布账号） | 会话失效时，约数月一次 | **全项目红线 1。** 方案 B 让增量也带登录态，但那是**复用**人工登录留下的会话。会话过期的正解是通知人去登，不是替他登。多一条登录路径就多一份被 checkpoint 拦的机会 |
| 2 | **Business Suite 选择器维护**（G1 重跑） | SPA 改版时，不可预测 | **全项目红线 5。** React SPA 的 class 是构建期混淆的。计划里早就把这条写成"预期内的定期维护"，不是故障 |
| 3 | **德语质量的最终责任** | 见第 5 节的分级 | 机器读不出"这句德语自不自然"。K3 预扫描被取消之后，连"图上有没有漏改的英文"机器都不知道了 |

⚠️ 还有一条隐性的：**这台 Windows 笔记本必须开着。**
红线 6 禁止部署到 VPS/云函数（必须住宅 IP），所以"跑在哪"这件事没有自动化空间。
`FBScraperDeltaCatchup`（登录/解锁触发）已经在兜合盖睡过头的情况。

### 4.2 ✅ 可以消除的四条（这才是自动化的着力点）

#### ① 金额 → 德国站定价：**最大的一处杠杆**

**现状**：`prompts/translate_de.md` 第 3 节要求金额**逐字符原样保留**，
理由是"德国站卖多少钱是商务决策，模型无从知道"，
并明确写着「**这些金额会由人工在审校环节替换成德国站定价**」。

**这意味着每一篇带价格的帖子都要人动一次手。** 实测：

| | 图文可发帖 | 含金额 | 占比 |
|---|---:|---:|---:|
| Facebook | 27 | 10 | **37 %** |
| Instagram | 443 | 71 | 16 % |
| **近 90 天合计** | **67** | **26** | **39 %** |

**每 5 篇就有 2 篇要人工改价** —— 这是流水线上最密的一道人工。

**解法：把"每篇一次决策"变成"每个价格一次表项"。**

```toml
[publish.price_map]
# 左边是原文里逐字符出现的美元串，右边是德国站定价。
# 程序在**发布前**替换；translate 那一侧继续保持原样不动
# （译文真相源不该混进商务决策，这条边界不动）。
"$219.99" = "219,99 €"
"$299"    = "299 €"
```

**实测覆盖面**：全部图文可发帖里只出现 **46 种**不同金额串。
**一张 46 行的表覆盖整个归档。** 而且其中相当一部分是抽奖金额
（`$100`、`$200,000`）而非产品定价。

**配套的硬闸**：正文里出现了 `price_map` 里没有的金额串 → **这一篇停下来进人工队列**，
提示"请补一行价格映射"。人**填一次表**，之后这个价格永远不再需要人。

> ⚠️ 这道闸不能省。没有它，缺失的映射会以两种方式失败：
> 要么把美元价直接发到德国站（商业事故），要么静默跳过（更糟，没人知道）。
> **它是把人工从"每篇"降到"每个新价格"的那个装置，本身就是自动化的一部分。**

#### ② 合作帖的授权确认：**实测触发频率接近 0，可以白名单化**

`HANDOFF.md` 里那条顾虑是真的：263 篇合作帖里 229 篇原作者是第三方创作者。
**但那是翻译口径。发布口径下它基本蒸发了**——

| | 图文**可发**的合作帖 | 近 90 天 | 近 90 天的原作者 |
|---|---:|---:|---|
| Instagram | **39 篇**（全档只来自 16 个原作者） | 22 篇 | **只有 2 个：`neakasa.global`、`neakasa.de`** |
| Facebook | 0（FB 无此机制） | 0 | — |

**近 90 天所有可发的合作帖，原作者全是自家兄弟账号。**
那 229 篇第三方创作者的合作帖**几乎全是纯视频 Reels——本来就发不了**
（项目约定视频只记元数据不下载）。

**解法**：

```toml
[publish.trusted_owners]
# 自家账号，合作帖直接放行
own = ["neakasa.global", "neakasa.de", "neakasaofficial", "neakasa.tech"]
```

不在名单里的原作者 → **首次遇到时停一次**，人确认授权后加进名单，之后放行。
**按作者停一次，不是按帖停一次**——16 个作者对 39 篇，差 2.4 倍；
按近 90 天算是 2 个对 22 篇，差 11 倍。

#### ③ 排期时刻：规则化，不要人挑

```toml
[publish.schedule_rule]
# 程序按规则自己找下一个空位，不需要人选时间
weekdays = [1,2,3,4,5]        # 周一到周五
times    = ["10:00", "17:00"] # 每天两个位置
order    = "chronological"    # 按原发布时间正序
```

冲突处理：位置被占就顺延到下一个。窗口上下限以 G1 实测的 UI 限制为准。

#### ④ 全量翻译的 US$24 预算拍板：**在新范围下已经不必要了**

这是本次全局复盘**最值钱的一个发现**：

> 用户已拍板**不补发历史**。而**只有要发的帖才需要译文**。
> 稳态是 **5.2 篇/周**，不是 1051 篇。

`MANUAL_STEPS.md` 第 7 步那个"等你拍板全量预算（约 US$24）"的待办，
**已经不在关键路径上了**。它现在是一个可选项：
跑，就得到一份完整的德语语料（当前没有任何自动化环节消费它）；
不跑，流水线照常运转，只译它要发的那几篇。

**建议：先不跑全量。** 让对账器**按需翻译**，用真实节奏验证质量，
攒够信心再决定要不要补齐语料。
（当前已译 12 篇：旧版 3+3 已因 `PROMPT_VERSION=5` 过期，新版 3+3 有效。）

## 5. 自治分级：一个旋钮，四档

**不要在"全手动"和"全自动"之间二选一。** 这个项目的风险是不对称的——
抓取被封不可恢复、发布不可回滚，而翻译和调图错了只是重跑。
所以应当**按阶段、按风险分别放开**。

```toml
[pipeline]
autonomy = "assisted"   # manual | assisted | supervised | autonomous
```

| 档 | 抓取 | 翻译 / 调图 | 发布 | 人在哪 |
|---|---|---|---|---|
| `manual` | 手工 | 手工 | 手工 | **今天就在这一档** |
| `assisted` | 自动 | 自动（受预算闸） | **停在待确认** | 每次批量点头 |
| `supervised` | 自动 | 自动 | **自动发"零风险帖"**，其余进人工队列 | 只处理被分流出来的 |
| `autonomous` | 自动 | 自动 | 全自动，只有硬闸拦 | 只处理硬闸告警 |

**建议的推进路径**：`manual` →（装计划任务）`assisted` →（跑够 2 周、G8 通过）
`supervised` →（稳定一个月、无事故）视情况 `autonomous`。

⚠️ **不建议直接跳到 `autonomous`。** 理由和 C7 那七条一样：
这类风险的反馈是**延迟的，而且第一次通常就是最贵的那次**。
分级的价值不在于"慢慢来"，在于**每一档都能真实运行一段时间，
把没想到的失败模式暴露在还便宜的时候**。

## 6. 分流规则：把"要不要人"变成"哪些帖要人"

`supervised` 档的核心。**一篇帖子命中任一条就进 `needs_human`，
否则自动走完。**

| # | 触发条件 | 为什么它值得停 | 预估触发率（近 90 天） |
|---|---|---|---|
| 1 | 正文含 `price_map` 里没有的金额串 | 发错价格是商业事故 | 首次建表后 **≈ 0**；新价格出现时才响 |
| 2 | 原作者不在 `trusted_owners` 里 | 二次发布的授权 | **≈ 0**（近 90 天全是自家账号） |
| 3 | 德语图的 dhash 距离超阈值 | 模型整张重画了，产品外观被改 | 阈值标定后才启用 |
| 4 | 译文里出现术语表外的新产品名/型号 | 品牌一致性 | 新品发布时 |
| 5 | 这一篇的图有人工放进 `media_de/` 的版本 | 设计同事修过，说明这篇本来就特殊 | 少 |
| 6 | 该帖媒体不全（`media_complete=False`） | 素材有缺 | 归档现状为 0 篇 |
| 7 | 任一阶段连续失败达预算 | 已经不是单篇问题了 | 少 |

**规则 1 和 2 是"一次性成本"**：填一次表就长期沉默。
**规则 3~7 是"真事件"**：它们响的时候，人确实应该看。

> ⚠️ **不许为了"看起来更自动"去放宽这几条。**
> 它们和 C7 的七条缓解措施是同一类东西：
> **不是防回归，是防"跑得挺好就顺手优化掉"。**

## 7. 可观测性：当前最大的缺口是「死人开关」

**现在有的**：`delta_state.json`（增量的运行状态）、`alerts.log`、
`delta.log`、`core/integrity.py` 的三+一项检查、`core/notify.py` 的三级降级通知。

**现在没有、而且是最危险的那个缺口**：

> `core/integrity.py` 检查的是「**账号有没有在发新帖**」。
> **没有任何东西检查「我们的流水线还在不在跑**」。
>
> 如果计划任务因为任何原因不再触发——任务被系统禁用、`.venv` 被删、
> 笔记本连续两周没开机、`.bat` 改坏了——
> **今天没有任何机制会告诉用户。安静地停一个月，和正常运行,在用户那边长得一模一样。**

这个项目已经吃过一次同型的亏：合作帖丢了 263 篇，**丢弃是完全静默的**，
"程序丢掉 263 篇，输出里一个字都没有"，因此拖了很久才被发现。
**"没跑"和"跑了但没事做"在输出上一样**，是同一个故障模式。

### 要做的三件

1. **死人开关**：`pipeline_state.json` 记 `last_successful_run`。
   超过 `[pipeline].dead_man_days`（建议 3 天）没有成功运行 → 告警。
   ⚠️ 这个检查**不能只写在 `pipeline run` 里**——它自己不跑的时候正是要它响的时候。
   放进 `FBScraperDeltaCatchup`（登录/解锁触发）那条链路，或单设一个只读检查任务。
2. **一条命令回答"它这几天在干嘛"**：`pipeline status`，
   **零网络、零花钱、零写盘**，打印各阶段积压、最近一次成功、本月花了多少、
   人工队列里有几篇。沿用 `routes.delta --status` 已经被用户接受的形态。
3. **每周一条摘要通知**："本周发了 N 篇，M 篇等你确认，花了 US$X"。
   ⚠️ 频率要克制。`core/integrity.py` 已经立过规矩：
   **误报的代价不是打扰，是让整条告警通道失效**——用户关掉通知之后，
   真正的故障就再也没人知道了。

## 8. 成本闸

翻译和调图都花钱，而**自动化意味着没人盯着**。

```toml
[pipeline]
monthly_budget_usd = 60      # 超了就停下来问，不是继续跑
daily_budget_usd   = 5
```

按第 11 节的稳态节奏估算：翻译 ≈ US$1/月（5.2 篇/周）、
图片 high 档 ≈ US$33/月（11.9 图/周）。**合计约 US$34/月。**
设 60 是留出发布新品、活动周这类波动的余量。

**账单口径必须按真实 usage 外推，不许按字符或张数猜。**
这是 CR-40 的教训：F 组按字符估给出 US$1.08–5.41，真实是 **US$23.73**，
**低估一个数量级**，因为漏掉了主导项（reasoning）。
两个阶段的真实 usage 都已经逐条写进 `translated.jsonl` / `images_de.jsonl`，
对账器直接读它们。

## 9. 故障处理矩阵

| 类别 | 例子 | 处置 |
|---|---|---|
| **自愈** | 网络抖动、429、单条内容错误 | 退避 / 跳过留断点 / 下次自然重来。**已实现** |
| **降频** | 连续 N 天零新增 | `quiet_days_before_slowdown`。**已实现** |
| **停手叫人** | 会话失效、连续失败达预算、选择器失效、金额没映射、预算超限 | 停止自动运行 + 通知 + 进人工队列。**部分已实现** |
| ⛔ **永不自愈** | 登录、绕限流、换 UA、重试登录墙 | **红线。** 遇到就停手——继续试探是把"可能被注意到"变成"确定被注意到" |

⚠️ **一条要写进代码注释的**：用户手工重试会绕过保护。
`MANUAL_STEPS.md` 已经写了「看到限流/登录墙时最不该做的事是马上再跑一次」，
流水线的输出里也要重复这句——**自动化之后，看到告警的人更可能是"顺手再跑一下"**。

## 11. 量化目标：人工分钟数

按近 90 天实测节奏 **5.2 篇/周、11.9 图/周**：

| 环节 | 今天（`manual`） | 目标（`supervised`） |
|---|---:|---:|
| 记得并跑四条命令 | ~10 min/周 | **0** |
| 看输出判断有没有出事 | ~10 min/周 | **0**（异常才通知） |
| 德语文案审校 | ~25 min/周 | ~5 min/周（抽样） |
| 德语图目视检查 | ~20 min/周 | ~3 min/周（抽样 + 只看被分流的） |
| **改价格** | ~15 min/周 | **≈ 0**（一次性 46 行表） |
| 挑排期时刻 | ~10 min/周 | **0**（规则） |
| 合作帖授权确认 | ~5 min/周 | **≈ 0**（白名单） |
| **合计** | **≈ 95 min/周** | **≈ 8–10 min/周** |

**外加不定期**：会话失效重登（数月一次，约 3 分钟）、
选择器失效重跑 G1（SPA 改版时，约 20 分钟）。

**剩下的 8–10 分钟没法再压**，因为它们落在第 4.1 节那三条承重墙上。
**任何号称能把它压到 0 的方案，压掉的一定是安全性，不是工作量。**

## 12. 把自动化推过头会踩的红线

自动化的压力会自然地指向这几处。**它们一条都不能动**：

1. ❌ **不得为了"发布不用人登录"而实现自动登录。**（红线 1）
2. ❌ **不得为了"选择器不用维护"而凭猜写选择器或加容错兜底。**（红线 5）
   猜错的选择器 + 自动发布 = 把错误内容自动发出去。
3. ❌ **不得为了"跑得更快"而提高并发、去掉随机间隔、加大抓取深度。**（红线 3 / C7）
   C7 那七条**是方案 B 的组成部分，不是锦上添花**。
4. ❌ **不得为了"少一次确认"而删掉金额闸、授权闸、dhash 闸。**
   它们是把人工从"每篇"降到"每类"的装置——**删掉它们不是自动化，是无保护**。
5. ❌ **不得让对账器自己去解析响应/拼提示词/点浏览器。**（第 2 节）
   它一旦"顺手做一点"，就成了第五个真相源。
6. ❌ **不得部署到 VPS / 云函数。**（红线 6）住宅 IP 是硬约束。
7. ❌ **不得把发布确认默认关掉。** `require_confirmation` 的默认值是 `true`；
   改成 `false` 应当是用户在看过一段真实运行之后的显式决定。

## 13. 分支与所有权

| 组 | 分支 | 文件 |
|---|---|---|
| **L 组（本文件）** | `docs/pipeline-plan` → 实施时 `feat/pipeline` | `pipeline.py`、`docs/PIPELINE_PLAN.md`、`config.toml` 的 `[pipeline]` 段、`IMPLEMENTATION_PLAN.md` 的 L 组一节 |
| K 组 | `feat/image-de` | 见 `IMAGE_PLAN.md` 第 10 节 |
| G 组 | `feat/business-suite-publish` | 见 `PUBLISH_PLAN.md` 第 12 节 |

**L 组与 K / G 的边界**：

- **L 组不改 K / G 的任何实现文件。** 它只**调用**它们的入口、**读**它们的产物。
  这既是架构约束（第 2 节），也顺带让三条分支互不冲突。
- `config.toml` 的 `[publish.price_map]` / `[publish.trusted_owners]` /
  `[publish.schedule_rule]` 是 `[publish]` 的**子表**，
  按 TOML 规则必须放在 `[publish]` 段的**最后**
  （`[translate.glossary]` 已经为这条规则写过一次警告）。
  ⚠️ **它们由 L 组添加**，G 组不要动；G 组只用 `[publish]` 的标量键。
- **L 组必须最后合。** 它依赖 K / G 的入口签名，
  在那两组合回 `main` 之前，`pipeline run` 里对应的阶段只能是占位。
  但 **L0 全段（装计划任务、status、死人开关、价格表）不依赖任何一组，现在就能做。**
