## 0. 为什么现在才写这份文件

原始需求来自业务的一段口头描述，四个模块（抓取 / 翻译 / 图片德语化 / 定时发布）
是照着描述紧急实现并串联起来的。工程侧后来做得很扎实——32,029 行 Python、45 份离线测试、
76 条真机复盘、模块图 DAG 机器护栏、证据闸、付费账本——**但业务契约一直是空的**。

代价是可量化的。举一个在这次质询里才被发现的例子：

> 目标账号 `in_neakasa.tech` 全量 1020 篇里，**577 篇（57%）是纯视频**。
> 这套系统对它们的处理是「不在图文发布范围，直接跳过，不进人工队列」——
> 也就是**当成一条已经定过的边界在执行**，而翻遍所有文档，没有任何一处决定过这件事。

这不是 bug，是**默认行为冒充决策**。这份文件存在的意义就是把这类东西挖出来、变成显式的。

## 1. 系统的意义与边界

### 1.1 一句话

> 把 US 站社媒账号已经发布的**图文帖**，自动翻译成德语（正文 + 图内文字），
> 经人工审校后，在德国站账号上创建定时发布任务。

### 1.2 为什么必须是外部抓取

目标账号**没有管理员权限**，官方 API 与官方数据导出都不可用。这不是技术选型，
是给定条件——它决定了整个架构（浏览器 CDP 附着、拦响应而不解析 DOM、人工登录、
住宅 IP、并发恒为 1）。详见 [README.md](../README.md)。

### 1.3 明确的非目标

**写在这里的每一条都是决定出来的，不是"还没做"。**

| 非目标 | 决策依据 | 日期 |
|---|---|---|
| **视频帖不做**，且很长一段时间内不纳入 | 用户决定 | 2026-09-08 |
| **第三方创作者 UGC 不进流水线**（归档里 229 篇） | ⏸ **待定**，见 §8.3 | — |
| 不实现自动登录 | 红线 1，见 [HANDOFF.md §1](HANDOFF.md) | 已有 |
| 回填不用脚本自动滚 | 红线 2，见 [HANDOFF.md §1](HANDOFF.md) | 已有 |
| 不做汇率换算、不擅自决定德国站定价 | 商业事故风险 | 已有 |
| 不对外开放，纯公司内部工具 | 用户决定 | 2026-09-08 |

⚠️ **"视频不做"有一个必须配套的动作**：跳过的视频帖今天**连人工队列都不进**，
于是「本周发了 8 条、7 条是视频」和「本周没发」在日常输出里长得一模一样。
这是 CR-23（静默丢弃）的同型问题，只不过丢的是整个内容品类。
**必须把跳过数显式报出来**——见 [OPTIMIAZATION.md](OPTIMIAZATION.md) S1-6。

### 1.4 视频不做的直接后果，业务方必须知情

德国站只能拿到 US 站约 41% 的内容。近 90 天实测：

| 账号 | 近 90 天总帖 | 其中纯图文 + 有正文 |
|---|---|---|
| `fa_neakasaofficial`（FB） | 47 | **26** |
| `in_neakasa.tech`（IG） | 73 | **36** |

按 §3.3 的目标路由模型，德国站的产出节奏约 **62 篇 / 90 天 ≈ 4.8 篇/周**。
这条线是德国站内容的**主要来源但不是唯一来源**——运营同事会另外偶尔发帖（§3.4）。

## 2. 谁用、用来做什么

### 2.1 三类角色

| 角色 | 是谁 | 在系统上做什么 |
|---|---|---|
| **运营 / 社媒营销同事**（数人） | 公司内部，含德国站运营 | 审校德语正文与德语图、批准提交、查看状态。**上线后的主要使用者** |
| **管理员** | 同上，单一角色（§4.3） | 与上面完全相同的权限。不做角色区分 |
| **开发维护者** | 你 | 改安全参数、Meta 改版后重录探查、修解析器、处理新真机故障 |

⚠️ **第三行不在 Web 界面的覆盖范围内**，且只有一个人能做。这是一个已知的、
**用户明确表示自行处理**的人身依赖（§8.2）。

### 2.2 三个里程碑

原先「上线」这一个词混着三件事，拆开：

| | 定义 | 判据 | 依赖 |
|---|---|---|---|
| **M1 上线** | 德国站账号上出现第一条**完全由这条线自动产出 + 人工审核**的帖子，业务方看过并认可 | `state/published.jsonl` 出现一条业务内容的 `status=scheduled`（**不是 G8 测试排期**） | 现有 CLI 即可，**不必等 Web** |
| **M2 交付** | 运营同事在 Web 上自助完成审校与批准，全程不需要开发者介入 | 一次完整发布，`actor` 字段记录的不是开发者 | Web + 权限 + actor 留痕 |
| **M3 稳态** | 连续多周自动运转，开发者只处理异常 | 计划任务已装且连续成功；飞书心跳未中断 | 心跳 + 会话检测 + 告警通道 |

**M1 与 M2 并行推进**（用户决定，见 §8.1）。

## 3. 内容契约

### 3.1 什么进得来

一篇帖子要进入付费与发布阶段，必须同时满足：

1. **在本账号主页上** —— 判据是 `parse.on_timeline_of()`，**不是 `owner == account`**。
   IG 合作帖由一方发布、双方主页同时显示，只比 owner 会丢掉实测 263 篇。
2. **纯图文** —— `media` 全部是 `image` 且有正文。视频、图文混合、无媒体、无正文一律跳过。
3. **作者在 `[publish.trusted_owners]` 白名单里** —— 当前是 `neakasa.*` 自家品牌账号。
4. **正文里的金额都在 `[publish.price_map]` 里** —— 当前 46 条恒等映射，作用是
   「**新金额第一次出现时停下来问人**」，已过目的直接放行。

第 3、4 条不满足的进人工队列，**不是丢弃**。

### 3.2 什么出得去

- 德语正文（`translated.jsonl` 是真相源，`text_de.txt` 是派生副本）
- 德语图（`images_de.jsonl` 是真相源；`media_de/` 里**人工放的文件程序不得覆盖**）
- 排期时刻固定柏林 10:00 / 17:00；Business Suite UI 用美西时区，两地夏令时各自换算
- 话题标签逐个原样照搬，@提及一字不动，金额按 `price_map` 映射

### 3.3 🔴 路由模型：目标与现状不一致

**目标（用户确认的业务规则）**：

```
爬 FB 的帖子  →  只发到德国站 FB Page（Neakasa Deutschland）
爬 IG 的帖子  →  只发到德国站 IG（neakasa.de）
两条独立车道，互不合并
```

**现状（代码实际在跑的）**：

```
FB 源与 IG 源两两配对（30 小时窗口 + 正文相似度 + 素材 dHash）
  ├─ 完全一致  → 合并成一个候选，取 FB 那边当基准
  └─ 只是相似  → 停下来让人选一个版本   ← 近 90 天 12 篇卡在这里
然后：一次提交同时发到 FB 和 IG 两个渠道
```

证据：`publish/workflow.py` 四处 `target_channels` 默认 `("facebook", "instagram")` 且无调用方覆盖；
`publish/business_suite.py:429` 明确写着渠道勾选沿用 composer 默认全勾选、程序不点击；
配对逻辑在 `pipeline/engine.py:690-740`。

**差异的后果**：

| | 现状 | 目标 |
|---|---|---|
| 近 90 天可发单元 | 48（其中 12 需人工选版本） | **62，且这道人工闸消失** |
| 德国站内容 | FB 与 IG 完全一样 | 各自对应源平台 |

⚠️ **这个改动需要重录 probe dump**。要让程序主动点渠道勾选框，就得有对应的交互证据——
而 [HANDOFF.md §1](HANDOFF.md) 红线第 5 条由 `publish/evidence.py::verify` 机器强制：每条定位必须能回查到
真实 dump 的具体交互编号。当前那份 dump 里**没有渠道勾选的记录**（代码注释明说是刻意不点的）。

所以完整路径是：**重录探查（人工 ~15 分钟）→ 补渠道证据 → 重跑 G8 真机验证**。
用户已知晓，列为后续优化方向，**不阻塞 M1**。

### 3.4 ⚪ 撞槽检测

运营同事会另外偶尔发帖，所以排期前必须检查目标时刻在德国站是否已被占用。

**已确认的前提**：手机 App 上即时发布的帖子**会**出现在 Business Suite 的 Planner 日历里，
因此这个功能可行，没有盲区。

**现状不是这个功能。** `publish/business_suite.py:1495` 的 `read_scheduled_baseline`
按「同时刻 + 同正文 + 同渠道 + 同图数」四条筛，做的是**同帖去重**（防止把同一篇排两遍），
不是**槽位占用检测**——别人的帖子在同一时刻，正文不匹配就被放过了。

✅ **好消息：不需要重录 probe。** `_planner_cards` 已经在枚举可见日期范围内的**全部卡片**，
改的只是筛选条件。

**规则**（用户确认）：

- 撞槽 → 顺延；顺延**间隔**与**最大次数**都是人工可配参数
- 每次顺延后对新时刻**重新检测**
- 超过最大次数仍撞槽 → **停止本次发帖任务**，推送通知给相关人员
- 不做更复杂的分支处理

## 4. 人机边界

### 4.1 人工闸合并成一道

现状有两个卡点，分属不同界面：

| 闸 | 载体 | 干什么 |
|---|---|---|
| 德语审校 | `review.md`（Markdown 文件） | 逐帖确认译文和德语图对不对。**德语图唯一的验收关口**——预扫描已取消，机器读不出"德语对不对" |
| 待确认清单 | `pipeline approve`（CLI） | 批准某篇可以真的提交 |

**目标**：合并成一道，都在 Web 上完成。运营/社媒同事**同时**完成德语审校和批准，
开发者完全退出内容判断。

### 4.2 审校发生在付费之后

`review.md` 是翻译和图片都生成完才有的——一张图约两分半、几分钱。审校驳回意味着钱已经花了。
**这是刻意接受的取舍**，因为月预算上限 US$60，重跑成本可接受。

### 4.3 权限与留痕

**权限：单一角色。** 能登进 Web 的人权限完全相同，不做 RBAC。
理由：公司内部几个人使用的小工具，骨干功能够用即可。

⚠️ **但留痕必须有，且和权限是两件事。** 实测缺口：

- `pipeline/engine.py:428` 的 `resolve_human_item` 只写 `resolution` / `selected_ref` / `recorded_at`，**没有 actor 字段**
- `publish/journal.py` 的发布留痕同样没有 actor

一个人用的时候不用记，因为永远是同一个人；**几个人用的时候，发错内容必须能追溯到人**。
`needs_human.jsonl` 与 `published.jsonl` 都是追加式的，加字段向后兼容。

⛔ **必须在 M2 之前加。历史记录补不回来。**

📌 **一个必须说清楚的限制**：内部 actor 留痕能查到"谁在 Web 上批准的"，
但社媒账号是共享的（§5.4），**Meta 侧看到的操作者永远是同一个账号**，平台侧不可区分。

## 5. 系统形态与运行环境

### 5.1 那台机器

**办公室一台专用 Windows 机常开，接家用宽带 WiFi。**

它是整条线的单点故障——关机即全线停止。约束来自三处，都绕不开：

1. **必须是住宅/普通宽带**。数据中心 IP 首次请求就被拦，VPS、云函数、GitHub Actions 全不可用
2. **两个 Chrome profile 必须常驻且是人工登录的**（抓取小号一个、发布账号一个，红线禁止自动登录）
3. **134 MB 证据 dump 绑定单机** + Windows 计划任务

### 5.2 Web 界面

**范围：全部功能 + 权限管理都上界面**（用户决定），运营同事不需要接触 CLI。

⚠️ **一条必须钉死的开发约束**：

> **Web 层不许复制任何流水线逻辑，只能调用生产代码。**

已有做对了的样板：`Demo/console/board.py`（`ThreadingHTTPServer`，直接读归档字节，
零业务逻辑副本）。守住这条，M1 撞出的真机 bug 只需改后端一处；破了这条，
并行开发的代价就会兑现。

### 5.3 🔴 配置的二分

**`config.toml` 那 605 行不是同一种东西**，上 Web 时必须分开处理：

| 类别 | 例子 | 改错的后果 | Web 上 |
|---|---|---|---|
| **运营参数** | 排期时刻、顺延次数与间隔、显示名 | 帖子发得不合适，可改可撤 | ✅ 可改 |
| **安全红线与闸** | `[delta]` 的 C7 七条缓解措施、`[publish].ui_probe_dump`、`ui_constraints_verified`、`[pipeline].autonomy`、`monthly_budget_usd`、`[publish.trusted_owners]`、`[publish.price_map]` | **封号 / 烧钱 / 发错内容**，不可撤 | ❌ **只读 + 显式申请** |

第二类为什么不能做成输入框：

- `[delta]` 那七条（随机化触发时刻、深度上限、拟人节奏、异常即停、频率降级、失败预算）——
  红线第 3 条明写「不要因为'跑得挺好'就把它们优化掉，这类风险的反馈是延迟的，且只反馈一次」。
  做成可编辑，等于邀请一个不知情的人把间隔从 6–14 秒改成 1 秒，而后果要几周后才以封号的形式出现
- `ui_constraints_verified` / `ui_probe_dump` 是**人工签字栏**，代表"有人真的在真机上量过了"。
  做成开关，签字就失去意义
- `autonomy` 从 `assisted` 改成 `autonomous` 就是"发布不再问人"，不该是个下拉框
- `trusted_owners` / `price_map` 是**业务决策**（授权别人的内容 / 决定德国站定价），不是设置项

⛔ **不要用"二次确认"代替"改不了"**——二次确认会被点成肌肉记忆。

📌 **`config.toml` 的注释是这个项目最有价值的资产之一**（每个参数为什么是这个值、改了会怎样）。
Web 表单会把注释扔掉——**注释必须跟着上到界面上**。

### 5.4 账号管理

指的是**系统用户**（谁能登 Web、加人删人），**不是**社媒账号。

社媒账号（`[targets]` 抓哪个号、`[publish]` 发到哪个号）在 Web 上**只读展示**。
换目标账号不是改设置项——它意味着重新回填（人工滚 20 分钟）、新建归档目录、
重新积累合作方名单、`price_map` 与 `trusted_owners` 全部重填，是一次项目级操作。

### 5.5 🔴 提交并发

**批准后后端立刻自己驱动浏览器提交**（用户决定）。这没有改变自治级别——
`assisted` 的定义是"发布停在待确认、人点头才提交"，人点头的动作从"跑命令"变成"点按钮"，
性质完全一样。

⚠️ **但这制造了一个已验证的竞态。** 全仓库只有两处锁——`paid_requests.lock`（付费账本）
和 `ImageRunLock`（图片批次），都基于 `core/paid_model.py` 的 `FileLock`。
**`publish/`、`pipeline/`、`routes/` 里一个锁都没有。**

以前不需要（CLI、单人、一次一条）。多人 Web 之后，两个人几乎同时点批准就是两个进程
驱动同一个发布 Chrome。而且提交前那道基线检查是「读 Planner → 确认 `match_count == 0` → 点提交」，
**两个进程都读到 0，然后都点** —— 典型 TOCTOU 竞态，后果是同一篇被排两遍或两条帖抢同一时刻。
这是 CR-41 的同型问题，但发生在**不可回滚**的发布侧。

**规则**：第二个人**直接被拒绝**，提示"有人正在提交，稍后再试"，并显示是谁在提交什么。

⛔ **不做排队。** `pipeline` 的设计原则明写着「每次从各阶段真相源对账，**不建立发布任务队列**」，
排队会破坏这条。

## 6. 可观测性与失效

### 6.1 🔴 告警通道

现状：`core/notify.py` 只有 PowerShell toast + `msg` 弹窗 + `state/alerts.log`，
**没有任何网络推送通道**。那台机器在办公室角落，toast 弹了等于没弹。

**目标：飞书。** 需要新建 webhook 通道。

### 6.2 ⚪ 心跳，不是告警

⛔ **不能把监控任务放在被监控的机器上然后只在出事时推送。** 那样的话：

```
机器关机 / 断网 / 计划任务被禁用  →  监控也没跑  →  飞书上什么都没有
机器一切正常，只是今天没新帖      →  监控跑了     →  飞书上什么都没有
```

**两种情况在飞书上完全一样。** 「沉默有歧义」正是这个项目吃过大亏的病型——
263 篇合作帖静默丢失，输出里一个字都没有；`[pipeline]` 的 `dead_man_days` 注释
自己就警告过这件事。

**做法**：机器定时往**外部心跳服务**（healthchecks.io 之类）推心跳，
**缺席由外部服务来叫**。飞书日报作为补充。外部服务是唯一一个"被监控方挂掉时观察者还活着"的选项。

### 6.3 ⚪ 会话过期：被动推断，不主动探测

两个 Chrome profile 的会话都会过期。**检测方式必须是被动的**：

- 每天那次正常的 `delta run` 本来就会碰接口，失败了就是会话出问题了 → 直接推飞书
- 发布账号同理，从提交结果推断
- 只有"今天一次都没跑过"才需要主动看一眼，而那种情况本来就该告警

⛔ **不要写定时主动探测。** 主动探测会给抓取小号加上一条**稳定的、有规律的**请求节奏，
正好是 `[delta]` C7「随机化触发时刻、频率可降级」要避免的东西。被动推断是**零额外敞口**。

**恢复流程**：任何一位运营 / 营销 / IT 同事都可以去那台专用机器上重新登录，账号密码共享。
不指定专人。

### 6.4 ⚪ Meta 改版的发现机制

Meta 改版不是"如果"是"什么时候"（`tools/_scaffolding/` 一年最多用一两次，就是改版后重录）。
改版有两种表现，只有一种现在能被发现：

| 表现 | 现在能不能发现 |
|---|---|
| 发布突然失败 | ✅ G6c 回读闸会拦，能看到 `submit_ambiguous` 或报错 |
| **填错了字段但提交成功** | ❌ **发现不了**，直到有人打开德国站看见内容错乱的帖子 |

**做法**：每次提交后把 Planner 卡片的关键字段（正文前 N 字、图数、时刻等）推到飞书，
人扫一眼。成本几乎为零，把"静默填错"变成"有人能看见"。
