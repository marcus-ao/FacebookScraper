## 2. 已核实的接口契约（**不要重新推导，也不要照 SDK 签名猜**）

核对日期 2026-08-31。来源：用户指定的
<https://docs.aihubmix.com/en/api/GPT-Image-1>、
<https://docs.apiyi.com/en/api-capabilities/gpt-image-2/overview>，
以及对 `https://api.inferera.com/v1/models` 的实际探测。

| 项 | 值 |
|---|---|
| base_url | `https://api.inferera.com/v1`（**实测 `GET /v1/models` 返回 200 且为 OpenAI 形态**） |
| 模型 id | `gpt-image-2`（付费调用前实测在该网关的模型列表里精确存在） |
| 端点 | `POST {base_url}/images/edits` |
| Content-Type | **`multipart/form-data`**（`/images/generations` 才是 JSON） |
| 鉴权 | `Authorization: Bearer <key>`（openai SDK 自动设置） |
| 必填 | `model`、`prompt`、`image` |
| 可选 | `mask`、`n`、`size`、`quality`、`output_format`、`output_compression`、`background`、`moderation` |
| 响应 | `data[0].b64_json` + `usage`；`model` **不保证返回** |
| usage 最低契约 | `input_tokens` / `input_tokens_details{image_tokens,text_tokens}` / `output_tokens`；`output_tokens_details` 可选 |
| 模型验证 | 每个客户端先查一次 `/models`；响应有 `model` 时再做显式一致性核对，缺失时记 `catalog` |
| 超时 | 720 秒（供应商提示单次生成可能超过 5 分钟） |
| 费率 | 文本输入 $5/1M · 图像输入 $8/1M · 图像输出 $30/1M |

### ⛔ 三条会直接让请求失败的事实

**1. `input_fidelity` 必须不发送。**
gpt-image-2 **强制**对参考图做高保真处理，**不再接受这个参数，传了返回 400**。

> ⚠️ **本机装的 `openai` 3.6.0 的 `images.edit()` 签名里有 `input_fidelity`，
> 且 docstring 写着「supported for `gpt-image-1` and `gpt-image-1.5` and later models」。
> 那句话对 gpt-image-2 是错的。**
> 记下来是因为：下一个会话去看 SDK 签名，一定会觉得"保真度这么关键怎么能不传"，
> 然后把它加回去。**它加回去的那一刻，整组请求全部 400。**
> 我们要的高保真是**默认就有的**，不是靠这个参数换来的。

**2. `quality` 必须显式给 `low` / `medium` / `high`，不要用 `auto`。**
省略会退到 `auto`，计费不可预测。这个项目已经因为"参数没生效又不报错"
栽过一次（F 组那次 thinking 没关掉，4096 输出额度全烧在思考上，一个字译文没产出）。

**用户 2026-08-31 拍板 `high`。** 我原本建议 `medium`（便宜 4 倍）；
用户选了 high。**这是业务取舍，代码不替用户改**——
与 `[translate].reasoning_effort` 那条同源。费用见第 7 节。

**3. `size` 必须满足四个约束，而我们的归档大面积不满足。**

约束：边长 ≤ 3840、**宽高都必须是 16 的整数倍**、宽高比 ≤ 3:1、
总像素在 **655,360 – 8,294,400** 之间。

对 818 个已归档图片文件实测的尺寸分布：

| 张数 | 尺寸 | 16 的倍数？ | 处理 |
|---:|---|---|---|
| 318 | 1080×1080 | ❌ 1080/16 = 67.5 | → **1088×1088** |
| 100 | 1080×1350 | ❌ | → **1088×1360**（正好 4:5，无形变） |
| 65 | 1440×1440 | ✅ | 原样 |
| 33 | 1440×1920 | ✅ | 原样 |
| 27 | 1350×1687 | ❌ | → 1344×1680 |
| 21 | 1440×1080 | ❌ | → 1440×1088 |
| 15 | 960×1200 | ✅ | 原样 |
| 12 | 720×720 | ✅ 但 **518,400 < 655,360** | → **816×816**（放大到过下限） |

**最常见的两档（418 张，超过一半）都不合法。**
直接 `size=f"{w}x{h}"` 会在一半以上的图上 400 —— 这正是"看起来最自然的写法"。

因此必须有一个 `legal_size(w, h)` 函数（K2），并且**它要有自己的单元测试**：
四条约束里任意一条写错，症状都是"跑起来一半图片 400"，而不是编译期错误。

用户要求由我细化。以下分类**基于真实语料统计**，不是凭空想的：
对 1057 条有正文的帖子做了品牌/型号/大写词频统计，高频项直接进清单。

### 3.1 ⛔ 必须逐字符原样保留（译错 = 商业事故，不是文案问题）

| 产品型号 | `M1`(222) `P2`(55) `P1`(53) `S1`(30) `F1`(27) `N3`(16) `Magic1`(17)，及连写形态；实施预演补入 `P1 Pro`(50)、`NeakasaP1Pro`(44)、`Riko/RIKO`(204 次命中) | 型号是标识符 |

| 数值 + 单位 | 尺寸 / 容量 / 功率 / 分贝 / 时长 / 百分比 | 见下方 ⚠️ |

| 法律标记 | ® ™ © `MSRP`(19) | 专名 |
| @提及 / #标签 / URL / 二维码 / 条码 | — | 与 translate 第 7 节一致 |

⚠️ **图内的单位比正文更严：一律不换算。**
`prompts/translate_de.md` 允许正文换算物理量（inch→cm、lb→kg），
**图片这边不允许**。理由是可验证性不同：

> 正文换算错了，`review.md` 里两栏一对就看出来；
> 图片是像素，错了只能靠人眼逐张看，而**没有人会逐张看 818 张图**。
> 在无法验证的介质上做不可逆的数值变换，是拿不确定性换好看。

**不确定时的默认动作：不动。** 与 translate 的"原文没有的数字绝对不要造"同源。

### 3.2 ✅ 应当译成德语

描述性文案、卖点短句、CTA 按钮文字、功能标注、章节标题、通用名词
（`Self-Cleaning` → `selbstreinigend`、`Free Shipping` → `kostenloser Versand`）。

**必须复用 `config.toml` 的 `[translate.glossary]`，不得另写一份。**
否则图里写 `Katzentoilette`、正文写别的，同一篇帖子里出现两种说法——
术语表存在的全部意义就是防这个。

### 3.3 德语文字从哪来

两个来源，缺一不可：

1. **该帖已有的德语译文 `text_de`**（用户明确要求用它做参照）。
   它已经过金额硬校验、标签硬校验，是当前项目里质量最高的德语来源。
2. **术语表**（同 3.2）。

⚠️ 因此 **K 组依赖 F 组**：没有 `translated.jsonl` 里当前版本的译文，
这篇的图就不该处理。硬依赖，不做降级。

## 4. 架构：照抄 `translate.py` 已被验证的那一套

**不发明新结构。** F 组那套（真相源 jsonl + 指纹 + 版本 + 单实例锁 + 断点续跑
+ 写盘前硬校验）已经被真实付费批次验证过，K 组逐条复用。

```
localize_images.py            ← 新增，与 translate.py 平级
prompts/image_de.md           ← 新增，提示词本体（改它不用动 Python）
config.toml  [image]          ← 新增段
config.toml  [image.keep_verbatim]  ← 第 3.1 节那份清单的配置化
.env         IMAGE_API_KEY    ← 新增密钥（沿用「密钥永不进 config.toml」）

archive/<账号>/
  images_de.jsonl             ← **德语图的真相源**（与 translated.jsonl 同级同语义）
  posts/<帖子目录>/
    01.jpg                    ← 原图，只读，永不改动
    media_de/
      01.jpg                  ← 产出。**人工放的同名文件不得被覆盖**
```

**每行 `images_de.jsonl` 的字段**（与 `translated.jsonl` 同构）：

```json
{"post_id": "...", "media_index": 0,
 "source_sha256": "原图字节的 SHA-256",
 "text_de_sha256": "参照译文的指纹",
 "prompt_version": 2,
 "model": "gpt-image-2",
 "model_verification": "response 或 catalog",
 "size_requested": "1088x1088", "size_returned": "1088x1088",
 "quality": "high", "output_format": "jpeg",
 "out_path": "posts/.../media_de/01.jpg",
 "output_sha256": "产出字节的 SHA-256",
 "aspect_drift_percent": 0.0, "dhash_distance": 7,
 "elapsed_seconds": 42.1,
 "created_at": "2026-...Z",
 "usage": {...}}
```

**"这张图已经做过了"的判据**（下列各项全等，且产出存在并匹配
`output_sha256` 才算完成；任一变化即过期）：
`post_id + media_index` + **原图字节指纹** + **参照译文指纹** + `IMAGE_PROMPT_VERSION`。

把原图指纹算进去，是因为归档支持"残缺→补全"升级（`Archive.should_append`），
同一个 `post_id` 的 `01.jpg` 是可能被换掉的。只认 post_id 会让旧德语图
配到新原图上——和 F 组"旧德文配新英文"是同一个 bug，那边已经踩过。

`output_sha256` 还承担程序所有权与崩溃恢复：已被人工改过的同名文件不会因为有一条
旧 JSONL 就被程序覆盖；记录已 fsync、图片尚未原子替换时若进程终止，下一次普通重跑
会因文件缺失/哈希不符而补做，不会把崩溃窗口误判为人工版本或已完成。

默认作用域由 `[image].incremental_since = "2026-08-31T00:00:00Z"` 控制，
只跟立项后的新帖。K9 用 `--latest-posts 3` 明确选择最新三篇；全历史即使显式选中，
还必须再给 `--confirm-all-history-cost`，防止误双击触发约 US$179 的历史请求。
`--latest-posts` 只允许 1..3，不能用 818/9999 之类的大数绕过全历史二次确认；
`--check` 与三个零 API 模式互斥，`--dry-run --check` 会在参数解析时直接拒绝。

人工挑选有文字图片时，使用 `--post-id <唯一帖子> --media-index N` 精确绑定一张媒体；
序号从 0 开始，`0` 对应 `01.jpg`。`--limit 1` 只是待处理队列上限，目标首图已完成后
会自然前进到下一张待处理图，**不能**当稳定单图选择器。dry-run、正式请求与幂等复跑
必须复用同一个精确媒体参数。

> **为什么新增这个参数（2026-09-01 真实事故记录）**：第二次实验成功后，曾用旧的
> `--post-id ... --limit 1` 复跑来验证幂等；首图已完成，于是队列前进到 `media 1`。
> 约 30 秒后发现并中断。本地没有生成 `02.jpg`、没有追加对应 JSONL；但网关是否已开始
> 处理或计费无法从本地证明。此后未再发付费请求，并以 `--media-index` + 回归测试关闭
> 这条误用路径。

### K1 · `Settings` 与 `--check` 自检

- 照 `translate.py::Settings` 写：provider / base_url / api_key_env / model /
  quality / output_format / timeout / max_retries / request_gap_seconds。
- `validate()` 在任何网络请求前给出**可操作**的错误，而不是等网关返回模糊 400。
- `--check` 发**一个最小的真实 edits 请求**（一张本地生成的小图 + 一句无害提示词），
  并逐条断言：
  1. 网关可达、鉴权通过，且 `/models` 精确列出 `gpt-image-2`；
  2. 响应若明确返回 `model`，必须与请求一致；若缺失，则用请求模型 + 目录预检验证；
  3. 响应里有 `data[0].b64_json` 且能 base64 解码成合法图片；
  4. `usage` 最低契约完整（输出 token 明细允许缺失）。
- ⚠️ **`--check` 会真的花钱**（一次 low 质量的小图）。必须在输出里说清楚，
  与 F 组 `--check` 的口径一致。
- 【验收】`--check` 在真实 Key 下通过并打印实际 model 与 usage；
  缺 Key 时给出复制 `.env.example` 的完整命令且**不联网**。

> **完成：2026-09-01。** low 真实 edits 返回 816×816 可解码图片；响应未带 `model`，
> 由目录预检记录为 `model=gpt-image-2 / model_verification=catalog`。usage 为
> input 1043 / output 171 / total 1214，证明“响应缺 model”兼容路径已在真实网关命中。
> 预检失败也会缓存并立刻停批，同一客户端不会在下一张重复查询目录。

### K2 · `legal_size()` —— 尺寸合法化

- 输入原图宽高，输出**满足第 2 节四条约束**、且尽量贴近原图宽高比的尺寸。
- 规则：各边四舍五入到 16 的倍数 → 边长夹到 ≤3840 → 若总像素 < 655,360
  则按比例整体放大直到过线（放大后仍须是 16 的倍数）→ 若总像素 > 8,294,400 则缩小
  → 最后校验宽高比 ≤ 3:1，越界则显式失败（**不裁剪、不填充**，那是改画面）。
- 记录 `size_requested` 与原图尺寸的**形变百分比**；超过阈值的进人工清单。
- 【验收】用第 2 节那张实测分布表逐行断言（1080×1080→1088×1088、

## 8b. 第三轮同步审查（2026-08-31）留下的三条实测数据与两个新旋钮

> 来源：`CODE_REVIEW.md` 第 15 节（CR-46 ~ CR-59）。
> 这一节存在的理由是**别再重新测一遍**——下面每个数都是对真实 818 张归档图跑出来的。

### 8b.1 `legal_size()` 已在全档验证：0 失败

818 张全部合法化成功，第 2 节那张分布表逐行对得上，
**没有一张超过 3:1**（所以那条显式失败路径至今没有真实反例），
**也没有一张无法解码**。

### 8b.2 形变阈值已标定，`aspect_drift_warn_percent = 2.0` 不要动

| 指标 | 值 |
|---|---|
| 中位 | **0.0000 %** |
| p95 | 0.653 % |
| 最大 | 2.794 % |
| 超过配置的 2.0 % | **3 / 818** |

每 270 张才响一次：既不吵，也不是死旋钮。
（项目规矩：阈值在真实数据上标定，不许拍脑袋。这一条已经做过了。）

### 8b.3 ⚠️ 新增 `scale_warn_factor`：形变告警抓不到"小图被放大"

**等比放大的宽高比形变是 0**，所以 8b.2 那道线对放大完全无感。
而 `legal_size()` 为了过 655,360 像素下限**会放大小图**。实测线性倍数分布：

```
0.8x :   7      1.0x : 772      1.1x :  18      1.2x :   6
1.3x :   5      1.4x :   4      1.5x :   3      1.7x :   1
2.3x :   1      2.4x :   1
```

最极端两张：**`278×430 → 656×1008`（2.35 倍）**、`320×400 → 720×912`（2.26 倍）。
前者的形变只有 **0.66 %**，稳稳低于 2.0 % 的告警线 —— **会静默通过**，
而发出去的德语图就是一张 2.35 倍放大件。

于是新增：

```toml
[image]
scale_warn_factor = 1.25   # 命中 13/818，量小到可以逐张人眼看
```

`images_de.jsonl` 每行也多记一个 `scale_factor`，`review.md` 会把它打出来。
**只提示、不拦截**——与 dHash 阈值同一条纪律：没在真实产出上标定之前不设硬闸。

### 8b.4 ⚠️ 新增 `failure_budget`：单张失败不再掀掉整批

旧实现用 `isinstance(exc, openai.APIError)` 判致命，而那是
`RateLimitError`(429)、`APITimeoutError`/`APIConnectionError` 与
`BadRequestError`(400，含内容审核拒绝) 的**共同基类**。后果是：
一次网络抖动、或某一张图被审核拒掉，都会断掉剩余全部付费图片，
而且**没有跳过这张继续的办法**——一张有问题的图可以永久堵住队列。

```toml
[image]
failure_budget = 3   # 与 [delta].failure_budget 同一个数，不搞第二套心智模型
```

现在只有**鉴权 / 权限 / 端点不存在 / 模型目录缺失 / 模型不匹配 /
SDK 响应解析失败 / 响应契约破裂**算致命
（这几类每张都会同样失败，继续跑只是重复花钱）；
其余计为单张失败，由**连续**失败计数兜住。

### 8b.5 K9 必须用 `--post-id`，不能用 `--latest-posts 3`

真实归档里第 3 新的帖子 `3973112941198515773` 是**纯视频（0 图）**，
它占掉一个名额，把 FB 那篇挤到第 4 位（两篇 `created_at` 只差 4 秒），
于是 `--latest-posts 3` 只排到 6 张、**完全漏掉 Facebook**；
而 `MAX_LATEST_POSTS = 3` 的费用闸不允许写 4。

计划点名那三篇的真实工作集是 **11 张**（FB 5 + IG 5 + IG 1），
命令写在 `MANUAL_STEPS.md` 第 10b 步。

### 10.3 三条降低冲突的规矩

1. **只在自己那一节里编辑共享文档。** 不要重排其它节、不要"顺手"改格式、
   不要动行尾空白。`config.toml` 的 `[image]` 与 `[publish]` 相邻，
   `IMPLEMENTATION_PLAN.md` 的 K 组与 G 组也相邻——
   **各自只碰自己那一段，git 就能自动合**。
2. **附录 D 各自追加一节，标题里带上分支名。** 两段都要保留，
   合并冲突时**不许二选一**——那是项目的历史记录。
3. **先完成的先合。** 第二个合之前先
   `git fetch && git rebase main`（或 `docs/plan-image-publish`），
   **在自己分支上解冲突**，别把冲突带进 `main`。

### 10.4 收尾时两条分支都必须做的

- 跑**全部** `tests/tests_*.py`，不能只跑自己新增的那套（项目既定要求）。
- `git diff --check` 与 `python -m compileall -q .` 干净。
- `.bat` 保持**纯 ASCII + CRLF + 无 BOM**（`tests_schedule.py` 有字节级断言）。
- 新入口调 `core.console.force_utf8()`——本机代码页 936，
  输出一旦被重定向就会崩在 `ß`/`⚠` 上。
- 按项目工作协议更新 `IMPLEMENTATION_PLAN.md`：勾选完成项、
  在下面追加 `> 完成：<日期> · <实际做法与偏差>`。
  **未通过【验收】的不得勾选。**
