## S0 · 会发错内容或烧钱

### S0-1　已排期的那篇帖子，5 张图里 4 张还是英文

**现状**：`state/published.jsonl` 里唯一一条 `scheduled` 记录
（IG `3973012230169803390`，排期 **2026-09-10 10:00+02:00**）：

```
image_sources: ["media_de", "original", "original", "original", "original"]
warnings:      第 2/3/4/5 张缺少德语图，已回退原图；图内可能仍有英文
```

一个德国市场账号，会发出一篇 4/5 图带英文的帖子。**这抵消了整个图片模块存在的意义。**

**为什么没被拦住**：`image_sources` 被记录、被显示、被写进 journal，
但**没有任何一处拿它做闸**（全仓库 grep 确认）。唯一拦截是
`[publish].require_confirmation = true` 弹给人看的清单，而那条警告混在 11 条警告里。

**两件事，都要做**：

1. **补齐那 4 张并重发**（09-10 之前，约 US$0.84）：
   ```
   .venv\Scripts\python.exe localize_images.py --account in_neakasa.tech ^
       --post-id 3973012230169803390 --media-index 1
   ```
   （`--media-index` 2 / 3 / 4 各跑一次，一次付费调用只处理一张。）
2. **加硬闸**：新增 `[publish].require_all_media_de`，默认 `true`。
   任一张回退到 `original` 就在**离线阶段**失败闭合，错误文案直接给出补图命令。
   想放行必须显式配 `false`。
   护栏 `tests_hygiene.py` [1] 会保证这个新键不会变成改了不生效的死旋钮。

### S0-2　G6c 自动回读从来没在真实长文案上通过过

**现状**：那篇帖子的状态流转是

```
submitted_unverified   ← 看到提交成功信号
        ↓
submitted_unverified   ← 「内容日历里找不到同时匹配目标时刻与完整最终正文的卡片」
        ↓
scheduled              ← 人工结转（manual_evidence: true）
```

判据在 `publish/business_suite.py:1461`：要求**整段最终正文**是日历卡片文本的子串。
而 `planner_scheduled_card` 这条信号的 `name` 与 `entry_probe_text` 字面就是
`'Hello, this is a test.'` —— **22 个字符**。真实那篇是 **1,028 字符**。

**根因有两个候选，现在分不出来**：

- 卡片可访问名对长文案截断 → 子串检查永远不成立；
- 日历页时刻格式与 composer 不同 → `_entry_naive` 解析不出。

⚠️ 我一度断言是截断，用 dump 验证后**收回**：那份 dump 里的日历卡片来自
22 字的测试文案，证明不了长文案会不会被截。

**修复顺序**：

1. **先加可分辨的诊断**（不需要浏览器，随时可做）。现在那句话把两种失败塌缩成
   一条字符串。拆成分别报告，并把日历卡片**实际读到的文本长度与前 200 字**写进
   journal。
2. **再用一篇长文案真跑一次**（需要开发布 Chrome）。这是唯一能定案的方式。

**为什么它是 S0**：不修这个，每一篇都要人工结转，
`assisted` 永远升不到 `supervised`，而"系统无法自证到底发出去没有"本身
就是这个项目最怕的失效型（沉默有歧义）。

### S0-3　`text_de.txt` 无条件覆盖，会静默吃掉人工修改

`tools/review_report.py:323`：

```python
text_de.write_text(de, encoding="utf-8")   # 没有任何"人工改过就别覆盖"的判断
```

今天如果运营同事去改 `text_de.txt`，下一次 `--review` 会静默冲掉。

⚠️ **这与 `media_de/` 的语义正好相反**（README 明写"人工放的文件程序不得覆盖"）。
这个不对称没有人设计过，是漏的。

**修法**（与 §S1-4 的人工版译文是同一件事，建议一起做）：
新增账号级 `translated_human.jsonl`，追加式，顺带记 `actor` 与时间。
`--review` 只重建派生副本，**永远碰不到人工版**。

## S1 · 会静默丢数据、或挡住自动化

### S1-1　`supervised` 档的分流规则没有实现

`pipeline/engine.py:1162` 直接抛错：

```python
raise PipelineRunError("%s 本轮明确失败闭合；尚未实现后续发布分流规则" % autonomy)
```

四个自治档位里，`assisted` 已经一条命令跑完**抓取 → 翻译 → 调图 → 离线硬闸 →
生成 ready**，只差最后的发布。`supervised` 就是把发布也纳进来，
但只发"零风险帖"。

**分流规则表**（一篇命中任一条就进 `needs_human`，否则自动走完）：

| # | 触发条件 | 为什么值得停 | 预估触发率（近 90 天） |
|---|---|---|---|
| 1 | 正文含 `price_map` 里没有的金额串 | 发错价格是商业事故 | 首次建表后 ≈ 0 |
| 2 | 原作者不在 `trusted_owners` 里 | 二次发布的授权 | ≈ 0（近 90 天全是自家账号） |
| 3 | 德语图 dHash 距离超阈值 | 模型整张重画，产品外观被改 | 阈值标定后才启用 |
| 4 | 译文出现术语表外的新产品名/型号 | 品牌一致性 | 新品发布时 |
| 5 | 该篇有人工放进 `media_de/` 的图 | 设计同事修过，本来就特殊 | 少 |
| 6 | 媒体不全（`media_complete=False`） | 素材有缺 | 归档现状 0 篇 |
| 7 | 任一阶段连续失败达预算 | 已不是单篇问题 | 少 |
| **8** | **任一张图回退到 `original`** | **S0-1** | **当前 100%** |

规则 1、2 是"一次性成本"，填一次表就长期沉默；3~8 是"真事件"，响的时候人确实该看。

⛔ **不许为了"看起来更自动"去放宽这几条。** 它们和 C7 的七条缓解措施是同一类东西：
**不是防回归，是防"跑得挺好就顺手优化掉"。**

**设计要求**：规则表清空 == `autonomous`。以后切档是改配置，不是改代码。

**尚未拍板的四件事**（做之前要先定，见对话记录 2026-09-09 第一轮）：

- 目标档位是 `supervised` 还是 `autonomous`（建议 `supervised`）；
- 触发模型：一次性命令 vs 常驻进程（建议保持一次性，交给计划任务）；
- 发布浏览器谁负责拉起（建议命令自己起，会话过期硬失败）；
- 一篇失败：整轮停还是跳过继续（建议付费类整轮停、发布类跳过并计数，连续 3 篇则停）。

### S1-2　actor 留痕缺失

- `pipeline/engine.py:428` 的 `resolve_human_item` 只写
  `resolution` / `selected_ref` / `recorded_at`，**没有 actor**；
- `publish/journal.py` 的发布留痕同样没有。

一个人用的时候不用记，因为永远是同一个人；**几个人用的时候，发错内容必须能追溯到人**。
`needs_human.jsonl` 与 `published.jsonl` 都是追加式的，加字段向后兼容。

⛔ **必须在多人使用之前加。历史记录补不回来。**

📌 限制说明：内部 actor 能查到"谁在界面上批准的"，但社媒账号是共享的，
**Meta 侧看到的操作者永远是同一个账号**，平台侧不可区分。

### S1-3　发布路径零并发保护（TOCTOU）

全仓库只有两处锁 —— `paid_requests.lock` 与 `ImageRunLock`。
**`publish/`、`pipeline/`、`routes/` 里一个锁都没有。**

以前不需要（CLI、单人、一次一条）。一旦后端能自己驱动提交（Web 批准按钮），
两个人几乎同时点就是两个进程驱动同一个发布 Chrome。而提交前那道基线检查是
「读 Planner → 确认 `match_count == 0` → 点提交」，**两个进程都读到 0，然后都点** ——
典型 TOCTOU，后果是同一篇被排两遍或两条帖抢同一时刻。

**规则**：第二个人**直接被拒绝**，提示"有人正在提交，稍后再试"并显示是谁在提交什么。

⛔ **不做排队。** `pipeline` 的设计原则明写「每次从各阶段真相源对账，
**不建立发布任务队列**」，排队会破坏这条。

### S1-4　人工版译文没有落点

见 S0-3。新增 `translated_human.jsonl` 作为人工版真相源：

| | 机器译文 | 人工版 |
|---|---|---|
| 真相源 | `translated.jsonl` | **`translated_human.jsonl`** |
| 派生副本 | `text_de.txt`（人工版优先渲染） | 同一个文件 |

**为什么不用"文件在不在"那一套**（`media_de/` 的做法）：`text_de.txt` 本来就存在，
只能靠比对内容哈希判断是否被改过 —— 脆弱，一次编码变化或换行差异就误判。

**原文变更时**：机器译文绑 `source_text_sha256`，哈希对不上就作废重译。
**人工版不能照搬这条**（那是人花时间做的）——
保留人工版、标红「原文已变更，请复核」（`stale: true`）、重新进待审队列。

### S1-5　注入的 `now` 只走了一半，`tests_pipeline_e2e.py` 已经因此变红

**现象**：2026-09-09 起 `tests/tests_pipeline_e2e.py` 失败：

```
offline_gate: 帖子 e2e-fb：排期早于 G1 实测 UI 下限
```

**根因**：`pipeline/engine.py::run()` 有可注入的 `now`（测试固定成
`2026-09-03T20:00Z`），并用它算出占位槽位；但接着调用的
`compose_post()` **没有把 `now` 传下去**（三处调用点：`engine.py:1344 / 1564 / 1633`），
于是它退回 `datetime.now(timezone.utc)` 拿**真实时钟**。

测试算出的槽位在 09-04，而真实今天已经是 09-09 → 判成"排期在过去"。

⚠️ **这是一个定时炸弹型测试**：它只在真实日期早于某个日历点之前才通过。
"通过"曾经不代表逻辑对，只代表当时还没到那天。

**生产上也不干净**：一次 run 如果跨过整点/午夜，两个时钟会给出不同的判断。

**修法**：三处调用点把 `now=now` 传下去（一行一处）。
顺带把"注入时钟必须一路传到底"做成断言，别再留第二个隐式时钟。

## S2 · 方向错但不紧急（返工成本已估）

### S2-1　路由模型：跨平台合并 vs 两条独立车道

**目标（业务规则）**：

```
爬 FB 的帖子  →  只发德国站 FB Page
爬 IG 的帖子  →  只发德国站 IG
两条独立车道，互不合并
```

**现状（代码在跑的）**：FB 源与 IG 源按 30 小时窗口 + 正文相似度 + 素材 dHash 两两配对，
完全一致就合并成一个候选，只是相似就停下来让人选版本（近 90 天 **12 篇**卡在这里）；
然后一次提交同时发到 FB 和 IG。

证据：`publish/workflow.py` 四处 `target_channels` 默认 `("facebook", "instagram")`
且无调用方覆盖；`publish/business_suite.py:429` 明写渠道勾选沿用 composer 默认全勾选、
程序不点击；配对逻辑在 `pipeline/engine.py:690-740`。

| | 现状 | 目标 |
|---|---|---|
| 近 90 天可发单元 | 48（其中 12 需人工选版本） | **62，且那道人工闸消失** |
| 德国站内容 | FB 与 IG 完全一样 | 各自对应源平台 |

⚠️ **返工成本：大。** 要让程序主动点渠道勾选框，就得有对应的交互证据 ——
红线 5 由 `publish/evidence.py::verify` 机器强制。当前 dump 里**没有渠道勾选的记录**
（代码注释明说是刻意不点的）。完整路径：**重录探查（人工 ~15 分钟）→ 补渠道证据 →
重跑 G8 真机验证**。

### S2-2　撞槽检测（现在是同帖去重，不是槽位占用）

运营同事会另外偶尔发帖，所以排期前必须检查目标时刻在德国站是否已被占用。

**已确认的前提**：手机 App 上即时发布的帖子**会**出现在 Planner 日历里，功能可行，没有盲区。

**现状不是这个功能。** `publish/business_suite.py:1495` 的 `read_scheduled_baseline`
按「同时刻 + 同正文 + 同渠道 + 同图数」四条筛，做的是**同帖去重**（防同一篇排两遍），
不是槽位占用检测 —— 别人的帖子在同一时刻，正文不匹配就被放过了。

✅ **不需要重录 probe。** `_planner_cards` 已经在枚举可见日期范围内的**全部卡片**，
改的只是筛选条件。**返工成本：小。**

**规则**（已确认）：撞槽 → 顺延；顺延**间隔**与**最大次数**都人工可配；
每次顺延后对新时刻**重新检测**；超过最大次数仍撞槽 → **停止本次发帖任务并推送通知**。
不做更复杂的分支。

### S2-3　告警只有本机 toast，那台机器没人看

`core/notify.py` 只有 PowerShell toast + `msg` 弹窗 + `state/alerts.log`，
**没有任何网络推送通道**。那台机器在办公室角落，toast 弹了等于没弹。

**目标：飞书 webhook。**

### S2-4　心跳必须由外部服务发起，不能自己推

⛔ **不能把监控任务放在被监控的机器上然后只在出事时推送。** 那样的话：

```
机器关机 / 断网 / 计划任务被禁用  →  监控也没跑  →  飞书上什么都没有
机器一切正常，只是今天没新帖      →  监控跑了     →  飞书上什么都没有
```

**两种情况在飞书上完全一样。**「沉默有歧义」正是这个项目吃过大亏的病型。

**做法**：机器定时往**外部心跳服务**（healthchecks.io 之类）推心跳，
**缺席由外部服务来叫**。飞书日报作为补充。外部服务是唯一一个
"被监控方挂掉时观察者还活着"的选项。

### S2-5　会话过期：被动推断，不主动探测

两个 Chrome profile 的会话都会过期。**检测方式必须是被动的**：

- 每天那次正常的 `delta run` 本来就会碰接口，失败了就是会话出问题了 → 直接推飞书；
- 发布账号同理，从提交结果推断；
- 只有"今天一次都没跑过"才需要主动看一眼，而那种情况本来就该告警。

⛔ **不要写定时主动探测。** 它会给抓取小号加上一条**稳定的、有规律的**请求节奏，
正好是 C7「随机化触发时刻、频率可降级」要避免的东西。被动推断是**零额外敞口**。

**恢复流程**：任何一位运营 / 营销 / IT 同事都可以去那台专用机器上重新登录，
账号密码共享，不指定专人。

### S2-6　Meta 改版有一种表现现在发现不了

| 表现 | 现在能不能发现 |
|---|---|
| 发布突然失败 | ✅ G6c 回读闸会拦，能看到 `submit_ambiguous` 或报错 |
| **填错了字段但提交成功** | ❌ **发现不了**，直到有人打开德国站看见内容错乱的帖子 |

**做法**：每次提交后把 Planner 卡片的关键字段（正文前 N 字、图数、时刻等）推到飞书，
人扫一眼。成本几乎为零，把"静默填错"变成"有人能看见"。

## S3 · 交付形态（Web 审校台）

**这一节是 M2 的范围**，业务同事自助审校与批准、开发者退出内容判断。

⚠️ **原型已经在写了**：`web/`（2,918 行，Vue + FastAPI，commit `4dae7f7`）。
**完整设计在 [`web/DESIGN.md`](../web/DESIGN.md)**，四个源文件按节号引用它 ——
2026-09-09 文档整理时它从 `docs/` 移到了代码旁边，没有删除。

下面只摘几条**最容易在实现中被破坏**的约束，细节以 `web/DESIGN.md` 为准。

### S3-1　核心架构原则：读全真，写全假

```
GET  /api/tasks                    真 —— 从 archive/ + translated.jsonl + state/ 只读算出
GET  /api/tasks/<id>               真
GET  /api/tasks/<id>/image/<n>     真 —— 直接读归档字节
POST /api/tasks/<id>/approve       假 —— 只写原型自己的本地文件
POST /api/tasks/<id>/skip          假
PUT  /api/tasks/<id>/text_de       假
```

读的那半碰只读数据，怎么试错都无害；写的那半碰追加式生产真相源，那正是不能试错的地方。

⛔ **假实现必须返回和真实现完全相同的 JSON 结构。** 少一个字段、多一层嵌套，
切换那天前端就得跟着改，"便捷切换"这个目标就没了。

**切换到生产 = 改三个 handler**（`approve` → 调 pipeline 批准路径；
`skip` → 写 `needs_human.jsonl` 终态；`text_de` → 追加 `translated_human.jsonl`）。
**前端一行不用改。**

### S3-2　技术选型与部署

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **Vue**（SFC + 构建链） | 有脏状态、保存/放弃、实时校验、编辑态；原生 JS 会很快变成手写状态机 |
| 后端 | **FastAPI + uvicorn** | 从原型到 M2 一次不用换。stdlib `http.server` 到 M2（并发 + 写入 + 登录）必须换掉 |
| 部署 | **开发机 `npm run build`，`dist/` 拷到生产机** | 那台常开的机器**不装 Node** |

生产机上：Python 依赖只增加 `fastapi` / `uvicorn`，
**不需要 Node 运行时、不需要 `npm install`、断网也能跑**。
（项目原本 3.2 万行代码只有 5 个依赖，这个风格值得保住。）

### S3-3　模块图约束（会被护栏自动守住）

```
web/
  api/          FastAPI 应用；只读端与假写入端分开放，切换时只动后者
  ui/           Vue 源码
  ui/dist/      构建产物。生产机上只要这个目录
```

> `web/` **可以** import `core/` 和 `pipeline/`；
> **任何生产代码都不许 import `web/`。**

这样 `web/` 是模块图上的叶子，`tests/tests_hygiene.py` 第 6 条 DAG 护栏会**自动**
守住「Web 层不许复制流水线逻辑」这条约束 —— 不用靠人记。

⛔ 放在 `Demo/` 下面的"自由"是假的：那里不参与测试、不受 DAG 检查，
而这个原型如果真要长成 M2，那些检查正是需要的。

### S3-4　两种标记，两个时机，两种颜色

⛔ **这是两个功能，不是一个。混成一种颜色，用几次她两种都不信。**

| | 🔴 确定性检查（红） | ⚠️ 风险预扫描（黄） |
|---|---|---|
| 问的是 | 译文有没有把不该动的动了 | 这篇翻起来哪里容易翻坏 |
| 时机 | **翻译之后**比对原文与译文 | **翻译之前**扫英文原文 |
| 谁做 | regex（`core/translated.py` 已有三个函数） | LLM |
| 成本 / 误报 | 零 / 零 | 一次调用 / 会误报 |
| 语义 | **这里错了** | **这里注意看** |
| 覆盖 | 金额、话题标签、@提及、英制单位、尺码 | 俚语双关、歧义句、美国限定表述 |

金额/单位/标签三类**已有确定性实现**，让 LLM 去做只会花钱买误报。
LLM 只负责真正模糊的三类。第三类（Black Friday、Prime Day、"ships from LA"）
天然接上"这篇该不该搬"，是 `skipped` 动作的主要触发场景。

⚠️ **原型阶段不实时调 LLM**：预跑一次存成静态文件。零成本、零延迟、可重复演示，
演示当场不会因为 API 抖动而尴尬。接口契约不变。

### S3-5　几条已经想清楚、不要重新讨论的

- **不做"有告警"和"常规"两个 tab** —— 分 tab 的实际结果是只有第一个被看，
  第二个 tab 里的被批量通过，正好绕过这个界面存在的意义。
- **不做「退回」** —— 能直接编辑之后它就是个没人处理的死信箱（退给谁？谁改？）。
  但保留 `skipped`（这篇不发），它是决定，不需要谁来接手。
- **列表上不显示 actor** —— 留痕必须记，但列表上显示会诱发互相盯梢，
  几个人的小团队里是负面效果。放详情页。
- **常态不显示，异常才显示** —— 近期 IG 帖 35/36 是合作帖，那是常态，
  每行都标就是噪声。只标第三方作者。
- **必须有「下一处 →」跳转按钮** —— 实测正文中位 843 字符、最长 2838，
  德语再长 10~20%。这个长度下光高亮不够，她会扫一眼觉得"差不多"就过了。
  跳转把"检查"从开放任务变成有终点的任务。
- **编辑时实时校验，但保存时不拦** —— 这几个检查是给人看的辅助，不是硬闸。
  硬拦人工修改等于说"机器比人懂"，而这个系统的既定原则正好相反。
- **只考虑桌面**（≥1440px）。左右并排在手机竖屏上物理不成立。
  ⚠️ 这条要在业务访谈时确认。

## S4 · 体验与效率

- **配置未分类**：`config.toml` 的 597 行不是同一种东西。运营参数（排期时刻、
  顺延次数、显示名）可改；安全红线与闸（C7 七条、`ui_probe_dump`、
  `ui_constraints_verified`、`autonomy`、`monthly_budget_usd`、`trusted_owners`、
  `price_map`）**只读 + 显式申请**。详见 REQUIREMENTS.md §5.3。
  ⛔ 不要用"二次确认"代替"改不了" —— 二次确认会被点成肌肉记忆。
  📌 `config.toml` 的注释是这个项目最有价值的资产之一，Web 表单会把注释扔掉，
  **注释必须跟着上到界面上**。
- **`tools/_scaffolding/probe_publish.py` 里 471 行 CDP 进程管理没精简**。
  它需要真实 Chrome + Business Suite 会话才能验证，改坏了只会在 Meta 改版、
  急需重录的那一刻才发现。**移动是可逆的，重写不是** —— 暂不动。
- **`scale_factor` / `aspect_drift` / dHash 那套至今没触发过**。
  它们的作用是给未来的阈值决策攒数据（`config.toml` 自己写着"第一批 20 张跑完后再定"，
  现在只有 3 张）。**需要用户拍板才删。**
