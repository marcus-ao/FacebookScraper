## 1. 六条红线

违反其中任何一条会导致封号、烧钱或大面积返工。**它们不是风格偏好。**

1. **不得实现自动登录。** 全项目只允许一条登录路径：人工在
   `scripts\start_chrome.bat` 起的专用 Chrome 里登录一次，会话留在该 Chrome 的
   profile 目录，由 CDP 附着复用。多一条登录路径就多一份被 checkpoint 拦截的机会，
   且两份会话状态必然漂移。**会话过期的正解是通知人去登。**
2. **回填由人工滚动，不许脚本自动滚。** 滚的确实是人，没有可识别的自动化行为特征。
   代价是每次 20 分钟。
3. **增量的 C7 七条缓解措施是方案的组成部分，不是锦上添花。**
   随机化触发时刻、抓取深度上限（只滚几屏不滚到底）、滚动节奏拟人、异常即停不重试、
   频率可降级、失败预算 —— **不要因为"跑得挺好"就把它们优化掉。
   这类风险的反馈是延迟的，且只反馈一次。**
4. **抓取小号与发布账号必须在两个 Chrome、两个 profile、两个端口上**（9222 / 9223）。
   把持有 DE 发布权的账号和抓取小号放进同一个浏览器指纹里，等于把两件事绑成一件；
   而**抓取小号被封是本项目唯一不可恢复的失败模式**（回填与增量两条路同时断）。
5. **不得凭猜测编写 Business Suite 的选择器。** 每一条定位都必须能回查到一份真实
   probe dump 的具体交互/快照编号。这条由 `publish/evidence.py::verify` **机器强制**，
   不靠人守。猜错的选择器 + 自动发布 = 把错误内容自动发出去。
6. **密钥不进 `config.toml`。** 那个文件进版本库。走环境变量或 `.env`。

### 自动化的压力会指向这几处，一条都不能动

- ❌ 不得为了"少一次确认"而删掉金额闸、授权闸、dHash 闸。
  它们是把人工从"每篇"降到"每类"的装置 —— **删掉它们不是自动化，是无保护。**
- ❌ 不得让对账器自己去解析响应 / 拼提示词 / 点浏览器（见 §3）。
- ❌ 不得部署到 VPS / 云函数 / GitHub Actions。**数据中心 IP 首次请求即被拦**，
  住宅 IP 是硬约束。
- ❌ 不得把 `require_confirmation` 默认关掉。改成 `false` 应当是用户看过一段真实运行
  之后的显式决定。
- ❌ 不得在失败时自动删除草稿。半完成状态必须可见。
- ❌ `.bat` 不得含非 ASCII、不得用裸 LF（`tests_hygiene.py` [5] 守着）。

## 2. 架构：两条路径 + 一张单向 DAG

### 2.1 抓取拆两条路径，这是整个设计的核心

| | 回填 | 增量 |
|---|---|---|
| 频率 | 一次性（换账号时重来） | 每天一次 |
| 方式 | 登录态 + CDP 附着真实 Chrome + **人工滚动** | 登录态 + CDP 附着，拦 XHR 响应 |
| 为什么 | 滚的是人，无自动化特征 | 复用回填那条通道 |

⚠️ **增量方案 2026-08-30 从"完全登出"改成"登录态"（方案 B，用户拍板）。**
原设计是登出增量——没有账号、没有 session、没有 cookie，**因此没有可封的东西**。
实测推翻：FB/IG 在没有登录态时直接报错（对公开账号请求 `web_profile_info` 首次即 429）。

**必须清醒记住这个方案换来了什么**：

> 封号风险从「**一次性敞口**」变成「**累积性敞口**」。
> 单次会不会被封、和 365 次里会不会被封一次，是两个量级的问题。

这就是红线 3 存在的全部理由。

### 2.2 模块图必须是单向 DAG

`tests/tests_hygiene.py` 第 6 条机器强制，三个断言：

- **6a** 模块级导入图无环（import 期直接炸的那一类）；
- **6b** 含函数体的全图，排除组装根后仍无环（抓"用延迟导入把环藏起来"）；
- **6c** 函数体内导入本仓库模块的，要么在组装根（`main` / `_cli`）里，
  要么写一句 `# 延迟导入：` 说明晚绑定的代价原因。

当前 10 层：

```
L0  core.config  core.console  core.imagehash  publish.locator_types
L1  core.chrome  core.paid_model  core.notify  core.integrity  pipeline.settings
L2  core.store  core.paid_requests  publish.journal  publish.selectors
L3  core.parse  core.capture  core.translated  publish.evidence
L4  translate  localize_images  publish.business_suite  routes.*
L5  publish.compose  publish.workflow  tools.review_report
L6  tools.publish_post  tools.compose_publish
L7  pipeline.engine
L8  pipeline.cli
```

**为什么值得机器守**：2026-09-03 之前，`core/` 之上的 13 个模块是**一个强连通分量** ——
不是"有几处循环"，是整个应用层根本没有分层。而它是**一次一行**长出来的：
每次都是"就这一次，在函数体里 import 一下"，现场留下 28 处函数内导入，
其中 6 处注释明写着"延迟导入，避免模块初始化环"。**那些注释是唯一的记录，
而注释不会让测试变红。**

### 2.3 其它架构约束

- **`core/` 是叶子层。** 不许 import `translate` / `localize_images` / `pipeline.*`。
  预算策略由**组装根**（各 CLI 的 `main()`）注入进 `RequestController`。
- **付费模型调用的共用逻辑只能有一份**，在 `core/paid_model.py`：凭据读取、
  端点/费率校验、客户端构造、整批性错误判定、文件锁、原子写、JSONL 追加。
  CR-53 就是双份实现漂移的代价：修复只落到两个副本中的一个，
  同一次 429 在两个阶段行为不同，**持续两天没人发现**。
- **译文产物的契约在 `core/translated.py`**：`PROMPT_VERSION`、写盘格式、
  "当前可用"判据、金额/话题标签/数字三类不可改内容规则。
  `PROMPT_VERSION` 随**格式**走而不是随执行器走，读方才不用 import 写方。
- **dHash 只有一份实现**，在 `core/imagehash.py`，用 **BILINEAR**。
  依据是 8/27 那组真实配对的实测（BILINEAR `[0,0,0,0,0]`、LANCZOS `[0,0,1,0,0]`，
  而配对闸是 `DHASH_DISTANCE = 1`）。
- **`tools/_scaffolding/` 不是生产链路。** `publish/` 不许 import 它。
  它一年最多用一两次（Meta 改版后重录）。
- **包 `__init__.py` 不做 re-export。** 包级 re-export 会让导入任何子模块都先把其余的
  整个拉起来，然后子模块之间为了绕开初始化环只能在函数体里写延迟导入。

## 3. 对账器，不是队列

**队列的做法**：delta 抓到新帖 → 写一条待办 → 翻译消费 → 写下一条待办 → ……
**不要这样做。** 三个理由，第一个是这个项目自己的教训：

1. **队列会和现实脱节。** 项目已经为此立过铁律：「`post.json` 是真相，
   `manifest.jsonl` 是派生索引，冲突时以文件夹为准，**方向永远单一**」。
   队列是第二个真相源，一旦和归档不一致就退化成"两个都不可信"。
2. **失败恢复要额外机制。** 队列要重试计数、死信、超时回收。对账器不需要：
   **没做完的下次自然又被算出来。**
3. **新增阶段要改协议。** 对账器加一个阶段只是多一个谓词。

**对账器的做法**：每次运行对每一篇帖子算一次

```
期望状态：已归档 → 有当前版译文 → 有当前版德语图 → 已排期发布
实际状态：从 manifest.jsonl / translated.jsonl / images_de.jsonl / published.jsonl 读
差值    ：这篇卡在哪一阶段
动作    ：推进它能推进的那一步；推不动就归类到"为什么推不动"
```

**没有队列文件，没有状态机，没有重试计数。** 全部信息都已经在盘上。

> ⚠️ 必须守住的边界：**对账器只读四份产物、只调各阶段已有的入口。**
> 它不许自己解析响应、不许自己拼提示词、不许自己点浏览器。
> 一旦它开始"顺手做一点"，它就成了第五个真相源。

点提交之前**。⛔ 拿这条定位做"上传前的闸"是做不到的，别再挪回去。

⚠️ **IG 账号名在界面上是有的，只是没被采样到。** 真机失败截图显示 `Post to` 下拉框

这个控件的值没进可访问名。**结论不变：不能拿它当定位**（红线 5 —— 截图证明文本存在、
不证明 role 与 DOM）。

### 5.2 Planner

| 要素 | 真实语义 |
|---|---|
| 可见范围 | `heading 'September'` + `heading '2026'` —— **两条独立 heading，没有 "start - end" 串** |
| 月视图条目 | `link '10:00 AM'` —— **只有时刻，没有正文没有日期** |
| **周视图条目** | `link 'Hello, this is a test. 🤪 #test September 15, 2026, 10:00 AM'` —— **正文 + 完整日期时刻在同一条 link 的可访问名里**，这是最好的锚点 |
| **图片数量** | **⛔ 不存在任何数量语义**（25 张 planner 快照全查过） |

**详情弹窗：一个渠道一个，各有独立 remote ID。** FB 和 IG 是两个不同的弹窗、
两个不同的 ID（FB `1887083152480681` / IG `4378984725697354`）。

- **FB 侧**有独立子语义：`heading h2` = 主页名、`link` = 时刻（`%B %d at %I:%M %p`）；
- **IG 侧没有**：账号名与正文**只存在于 dialog 自己那一整串可访问名里**。
  probe 只采样带 role 的元素，IG 预览里那些是无 role 的 `<span>`/`<div>`。
  **这是设计不是 bug**，但它决定了 IG 只能按"整串里含 token"来判。

⛔ 弹窗里**除了关闭什么都不点**。那上面有 `Publish now` 和 `Boost`，
误点 `Publish now` 就是立刻发布。关闭一律用 Escape（不用坐标、不找按钮）。

### 5.3 被现实推翻的五条契约

| 曾经要求 | 现实 | 结论 |
|---|---|---|
| composer 上同时露出 FB Page 与 IG 帐号 | 没有 IG 账号名 | ⛔ 提交前只能证明 FB，IG 由提交后回读兜住 |
| 一张卡片内含时刻/正文/FB/IG/图片数五组子语义 | FB 与 IG 是两个独立弹窗 | ⛔ 必须改成**两条独立渠道证据** |

| 正文是卡片内独立子元素 | FB 弹窗里正文不是独立元素 | ⚠️ 改用周视图那条 link 的可访问名 |

`heading 'September'` 属于**页面外壳**，在日历数据还在转圈时就已经渲染好了。
现在等到**真的出现能解析出时刻的条目**才算就绪。

### 5.4 那 14 个 UI 上限（用户在真实 composer 上量的）

| 项 | 实测 | UI 怎么拒 |
|---|---|---|
| 单帖图片数 | **≤ 10** | `10 photo limit on Instagram posts` |
| 画幅比 | **4:5 ~ 1.91:1** | 范围已确认；超限文案没记到 |
| 正文长度 | **≤ 2200** | `The text in an Instagram post can't be longer than 2,200 characters.` |
| 话题标签数 | **≤ 30** | `A post can't include more than 30 hashtags.` |
| 定时下限 | **当前时刻**（没有最小提前量） | —— |
| 定时上限 | ⚠️ **本月最后一天** | 日期选择器**不允许跨月**，翻不过去 |

**两条"照直觉写就会错"的**：

① **定时上限不是一个时长，是一个日历边界。** 9 月 1 日能排 29 天，9 月 28 日只剩 2 天 ——
同一个 `max_ahead` 在月初太松、在月末太紧，固定 `timedelta` 根本表达不了。
`schedule_max_ahead_seconds` 只填了 31 天这个**绝对天花板**，真正的判据是
`publish/compose.py::_validate_schedule_month` 那道"必须落在同一自然月"的闸。
⛔ **不要看到 31 天就以为可以排 31 天。**

② **月份必须在 UI 时区里判**，不是柏林、也不是 UTC。日期选择器画的是发帖设备本机
（`[publish].ui_timezone` = `America/Los_Angeles`）的日历。
**柏林 10-01 06:00 在美西还是 09-30**。`tests_publish.py` 两个方向都有断言。

📌 `instagram_caption_length_mode = utf8_bytes` 是**刻意保守**：UI 报错只说
"characters"，emoji 算 1/2/4 从界面上确定不了。utf8_bytes 对任何字符串都 ≥ 另外两种，
**只可能多拦、不可能漏放**。

### 5.5 三个同型 bug，都是"拼接文本"造成的

`_row_text` 把 `accessible_name` 与 `visible_text` 拼起来，而这两者常常一模一样。
于是 `"5 photos"` 被数成两处数字、`"September"` 变成 `"September September"` 解析不动、
一个时刻被当成两个时刻。

> **凡是要在单值上判的，就不能拿拼接串去判。**

## 6. 内容规则：哪些字碰都不许碰

具体清单在 `config.toml` 的 `[image.keep_verbatim]` 与 `[translate.glossary]`
（基于 1057 条真实正文的品牌/型号/大写词频统计）。**这里只记代码里没有的理由。**

- **优惠码是最危险的一类，且最不显眼。** 它们是任意字符串却长得像单词，
  模型最容易顺手"翻译"。码错 = 用户结账失败。
  **已知表不是穷举，任何识别出的优惠码都不动。**
- **合作方水印 / 署名不许动。** 改掉别人的水印比翻错严重得多，那是**署名权**。
- **图内的单位比正文更严：一律不换算。** 正文允许换算物理量（inch→cm、lb→kg），
  图片这边不允许。理由是可验证性不同：

  > 正文换算错了，`review.md` 里两栏一对就看出来；
  > 图片是像素，错了只能靠人眼逐张看，而**没有人会逐张看 818 张图**。
  > 在无法验证的介质上做不可逆的数值变换，是拿不确定性换好看。

- **不确定时的默认动作：不动。**
- **德语图必须复用 `[translate.glossary]`，不得另写一份。** 否则图里写
  `Katzentoilette`、正文写别的，同一篇帖子出现两种说法 —— 术语表存在的全部意义就是防这个。
- **K 组硬依赖 F 组**：没有当前版译文，这篇的图就不该处理。不做降级。

## 8. 刻意接受的边界

**自动发布是单机工具。** 证据 dump（1.97 MB + 117 张截图，134 MB）不进版本库，
因此换机器或 dump 丢失后 `--submit` 永久失效，必须重录一次探查。

2026-09-03 评估过两个替代方案，都不选：

- 导出脱敏摘要进版本库 → 摘要证明不了 final 截图存在，等于把闸调松一档；
- 原始 dump 连截图进版本库 → 撑爆仓库，且截图有漏内容风险。

代价写在明面上：`publish/evidence.py` 的模块说明、dump 缺失时的错误文案
（直接给出重录命令）、以及 `README.md` 都记了这件事。

⚠️ **另一个敞口（备查，不是待办）**：`archive/` 343 MB + `state/` 160 MB
全部在 `.gitignore` 里，**无任何备份**（用户 2026-09-08 决定暂不做）。
其中 `state/published.jsonl` **不可重建** —— 丢失会导致幂等失效，
**已经发过的帖子可能被再发一遍**。
