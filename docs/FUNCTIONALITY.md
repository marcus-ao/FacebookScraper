# 功能规划 · 按流水线阶段

**成文日期：2026-09-11；业务契约校订：2026-09-12。** 来源是业务同事（店铺运营 / 社媒运营）的需求访谈、五轮阶段设计质询，以及 2026-09-12 已接受的五阶段、八批实施计划。

本次保留原有 34 个功能编号、具体规则和决定理由。归档数量、耗时、费用和旧 UI 观察均注明日期；它们不能代替当前状态。验收状态与实施顺序在 [REQUIREMENTS.md](REQUIREMENTS.md)，真实/离线证据边界在 [HANDOFF.md](HANDOFF.md)，API 契约在 [web/DESIGN.md](../web/DESIGN.md)。

这份文件回答一个问题：**这条流水线的五个阶段各自要实现什么功能、为什么是这个形状。**
它写给实现者（你和开发 Agent）——精确优先于好读，但每个阶段开头有一段
「这一步谁在做什么」，因为脱离了人的动作，功能就只是一堆开关。

| 文件 | 管什么 |
|---|---|
| **本文件** | **五个阶段各要实现什么功能、为什么**；词有歧义时查 [附录 A 术语表](#附录-a-术语表) |
| [REQUIREMENTS.md](REQUIREMENTS.md) | 为谁做、做到什么程度算够、每个验收单元现在是什么状态 |
| [HANDOFF.md](HANDOFF.md) | 红线、真实 UI 长什么样、踩过的坑、证据能证明到哪 |
| [MANUAL_STEPS.md](MANUAL_STEPS.md) | 需要人亲自动手的步骤 |
| [web/DESIGN.md](../web/DESIGN.md) | 审校台的界面与接口契约 |

**它定义功能，不用删掉需求来表示完成。** 运行事实由 `scripts\run_pipeline.bat preflight` 和 `preflight --json` 读取；功能验收仍需有日期、输入和证据。五种状态固定为 `代码未完成`、`离线通过`、`待真实联调`、`真实通过`、`明确延期`。存在已知实现、恢复或失败闭合缺口的验收单元记为 `代码未完成`；一部分测试通过不改变整个单元的状态。代码与真实依赖拆成独立验收行。

**这份文件说功能应该长什么样，不说现在做到哪一步。** 每个验收单元当前是什么状态、还差什么，看 [REQUIREMENTS.md 第 10 节](REQUIREMENTS.md#10-五阶段验收状态)；哪些证据能证明到哪、哪些不能，看 [HANDOFF.md](HANDOFF.md)。这两处会随每次集成更新，本文件不跟着改。

## 0. 读这份文件之前

### 0.1 这份文件的由来

2026-09-11 写作时，此前四份文档描述的是**一个已经跑过技术链路、但业务契约尚未明确的系统**——四个模块照着一段口头

这份文件是第一次有业务输入之后的功能规划。它做三件事：

1. 把业务诉求翻译成可实现、可验收的功能项（编号 `F<阶段>-<序号>`）；
2. 把诉求与已有红线、闸、契约之间的冲突摊开并给出决议；
3. 定出实施依赖顺序——这些功能不是并列的，有几条是其他一切的硬前置。

### 0.4 一天是什么样的

上海时间，某个星期二。下面是目标使用场景，不是已经完成的真实验收记录。

```
22:14  美国站发了一条新帖：M1 Pro 周年促销，4 张图，英文文案 1,180 字符。
       她已经下班三小时了。

22:00  上一轮探测刚跑过，差 14 分钟没赶上。
01:00  下一轮探测抓到了。翻译几秒钟跑完，4 张图的德语化跑了 10 分钟。
01:11  这篇进了审校队列。系统没有推送——她在睡觉（§4.4 F4-3）。
06:30–07:30  晨间轮次随机滚 2–4 屏，与相邻普通轮次不足 45 分钟时合并。

08:00  她到工位。飞书私聊弹出一条卡片：「昨夜新增 1 篇待审」，
       配图是德语版第一张，卡片上有一行红字：新金额 $89.99 未收录。
08:06  点卡片里的链接，审校台加载出这一篇。
       左边英文、右边德语，红标记停在那个金额上。
       按「下一处 →」跳到第二处黄标记：「Labor Day —— 美国限定节日」。
       她把那句改写成德国站说法，顺手删掉两个不适用的标签。
08:14  切到图片区。4 张缩略图，逐张放大核对型号与优惠码，看完一张打一个勾。
08:19  链接区显示这是 Instagram 帖，原文里的短链已经被摘出来，
       换成一句 "Link in Bio"。她确认。
08:21  点「编辑确认无误」冻住内容，再选发布时刻。默认预填北京 16:00（柏林 10:00），
       系统提示 9/16 16:00 前后 90 分钟内
       已有一条排期，并给出三个空档。她挑了 9/16 14:30。
08:22  点「通过」。
08:24  系统在后台驱动浏览器，在 Business Suite 里创建定时发帖任务，回读确认成功。
       飞书弹出回执：「已排期 9/16 20:30（北京）· Instagram · 4 张图」。

这一天她在这个系统上花了 10 分钟。
```

**这个系统真正要保证的是那 10 分钟成立**，其余全是为它服务的：

- 01:11 那个时刻必须早于 08:00 —— 这是**处理截止线**，是离岗窗唯一的 KPI；
- 08:00 那张卡片必须够她判断"现在开还是等会儿开"；
- 那两个红黄标记必须可信，否则用几次她两种都不看；
- 08:21 的空档提示必须准，否则她得自己去后台翻日历。

## 1. 阶段一 · 监测与原帖抓取

### 1.1 范围与人的动作

阶段一只监测并保存 FB `neakasaofficial` 与 IG `neakasa.global`。两个平台各自计数、调度、限额和停机，不配对帖子；目标账号实际参与的合作帖照常保留，记录真实 owner 与 coauthors。视频、图文混合、无媒体、无正文仍归档和计数，但不生成抓取卡片，也不进入付费处理。

人在 9222 回填 profile 中分别打开两个目标主页，手工滚到 30 天前。回填建立 `capture_state.json.baselines` 的监测基线与启用时间，不是发布激活边界；代码不登录、不自动滚历史。日常监测只附着 9224，打开主页首屏并被动读取 GraphQL/feed 响应，同一轮完成发现与抓取。普通轮次每平台最多 300 秒，不滚动；每天一次晨间轮次在北京时间 06:30–07:30 随机开始，每平台随机滚 2–4 屏、最多 90 秒。

### 1.2 调度契约

每个上海自然日（含周末）使用同一份持久 `next_due`：

| 上海时间 | 抽样间隔 |
|---|---|
| 08:00–19:00 | 60±25%，即 45–75 分钟 |
| 19:00–08:00 | 180±25%，即 135–225 分钟 |

调度器、CLI 与 `--if-stale` 共同读写它。19:00 后保留已经抽出的下次时刻；进入 08:00 后，第一次普通轮次落在 08:00–08:15，且距上次主页导航至少 45 分钟。晨间与普通轮次相距不足 45 分钟时合并执行并记录原因。锁忙（退出码 75）只记录跳过，不推进 `next_due`；重启从持久时刻继续，不追补停机期间的轮次。

上个完整月的发帖量、覆盖率和安静期统计只展示，不改变间隔，也不因模型预算把晨间轮次提前。阶段一运行固定 `process=false`：不启动模型、标签采样、审校唤醒、月历、云盘镜像或发布通知；后续阶段只有显式 `--process` 才运行。

### 1.3 共享访问控制与停机

所有 9224 入口（监测、详情补齐、标签和 Trends）在导航前向 `SharedAccessController` 持久记录访问意图；预算按意图计数，不按 HTTP 响应数计数。

| 访问 | 上限 |
|---|---|
| 主页 | 24 次/平台/滚动 24 小时，含晨间 |
| 详情 | 1 次/帖子/扫描、3 次/平台/扫描、12 次/平台/滚动 24 小时，含人工恢复 |

真实浏览器 `--dry-run` 仍写停机与配额；`--preview` 完全离线。状态文件缺少显式初始化或损坏时失败闭合。恢复用 revision、reason 的 CAS，不清空访问历史或配额。

内容响应或页面出现 401、403、429、登录、checkpoint 或 challenge 时，立即对整个 9224 profile 硬停；停止后不继续导航、滚动或下载。已签名 CDN 的过期 403 只记该媒体失败，CDN 429 则全局停机。某平台连续三次普通轮次失败暂停该平台。平台阻断和请求错误继续保留。

### 1.4 候选、详情补齐与媒体完整性

解析到的所有候选必须在第一次媒体下载前持久化，保留原文、来源元数据和媒体线索。仅 `source_media_complete != true` 的候选可在 9224 打开一次 permalink 详情；详情不滚动、不翻轮播、不重放 GraphQL，且必须同时匹配平台、post ID，以及目标 owner/coauthor。单纯下载失败不能触发详情。

`source_media_complete` 表示来源结构与 `capture_state.json` 中的 `items[key].source.media` 已知完整；`media_complete` 表示来源完整且所有静态图片都完成实际全图下载、解码、SHA 校验和原子写入。媒体按来源顺序保存，每项只选一个尺寸；IG 不把重复封面或视频缩略图当图片。未知结构一律不完整；Facebook 多图的真实响应顺序仍须真机核验。

配额、时间预算或抓取失败立即进入人工处理，后续普通扫描不重试。显式人工恢复使用 `PLATFORM:ACCOUNT:POST_ID`、expected revision 和 reason，只尝试一次并遵守同一访问、停机、身份与媒体校验规则；保留人的工作和原始事实。卡片展示“实际验证图片数 / 已知总数”，总数未知时明确写未知。

候选类别为 `new`、`historical`、`source_updated`、`recovered`、`time_unknown`。30 天基线只把既有内容记为 historical 并汇总，不向群里逐帖刷屏。内容 revision 由规范正文与按顺序的实际媒体 SHA 决定；CDN 签名、URL 路径变化和重复响应不产生新卡片。旧归档缺字段时显示 unknown，不补造事实。

### 1.5 飞书消息

四个现有机器人继续按 detect、capture、publish、alert 分工。检测消息按批次、平台、扫描汇总，零新增时不发；每个符合条件的帖子由 capture 机器人单独发送一张结果卡。阶段一抓取消息全天即时、异步入 durable outbox，不阻塞其余原图下载；进程重启补入已持久但漏入队的消息。未知投递继续要求人工核对，不自动重发。人工处理或平台暂停告警按事件去重。

抓取卡必须包含：

- 标题“完整”“部分完成”“失败”或“待人工”，以及类别、平台、监测账号、实际 owner/coauthors；
- 来源创建、首次发现、抓取结束三个北京时间；产品标签或“未分类”；
- 英文原文前 300 字符并明确截断、正文状态、实际验证图片数/已知总数；
- 安全原因与下一步；
- 已归档时主按钮指向 `/history/{account_dir}/{post_id}`，未归档时指向 `/runtime?capture={key}`；次按钮指向源 permalink，post ID 作为次要信息。

卡片不带缩略图，不用统一 1600 字截断隐藏字段或按钮，也不声称已经进入本地化队列。发布类通知仍属于后续阶段。月度/安静期统计只显示；云盘镜像不是阶段一交付。

### 1.6 验收边界

离线验收覆盖独立车道、共享 `next_due`、晨间合并、访问意图预算、硬停、候选先落盘、一次详情、媒体实际校验、revision 去重、逐帖卡与显式恢复。真实验收还需要：人工 30 天回填；FB 多图与 IG carousel 真实响应顺序；四机器人真实发送者、卡片链接；72 小时不改变正常节奏的试运行。没有自然新帖时不能把平台链路标为“真实通过”。

## 2. 阶段二 · 抓取与存储

### 2.1 业务诉求

- 抓取帖子文案、图片、平台渠道、账号名、原始发布时间、原帖链接（对应界面中的“元信息”）；
- 原始英文帖与后续处理过的帖子都要留档，一篇帖子一个文件夹；
- 文件夹命名要便于业务区分，且能按月份归档；
- 支持业务自定义 tag 母文件夹（按产品等维度）对帖子子文件夹归类；
- 存储方式：本地 + 飞书云盘 + 数据库三种。

### 2.2 这一步谁在做什么

抓取仍然没有人。但**存储这件事有两个截然不同的读者**，把它们分开是这一阶段的全部难点：

- **她**要在审校台上按 tag、按月份、按状态筛几十上百条——这是**查询**；
- **将来某个人**（可能是法务、可能是接手的人、可能是三年后的她自己）要回答
  "2026 年 9 月我们在德国站发了什么"——这是**留证**。

查询要快、要能多条件组合、要能重建；留证要完整、要不可篡改、要能离开这个系统独立看懂。
一份存储同时干这两件事，结果一定是两件都干不好。

### 2.3 2026-09-11 的缺口记录

**元信息字段已经全有了**，不需要新抓：`post.json` 的 `text` / `media[]` / `platform` /
`account` / `owner` / `created_at` / `permalink` 齐全。

差三样：**月份层级**（现在 1020 个帖子文件夹平铺在一个目录里）、**tag 字段**（不存在）、
**另外两份存储**（飞书云盘和数据库都没有）。

### 2.4 要实现什么

#### F2-1　存储三层：一个真相，两个派生

**改哪里**：新建 `core/index_db.py`（SQLite 索引）、`core/mirror.py`（云盘镜像）、
`tools/layout.py` 增加 `reindex-db` 子命令

这是这一阶段的地基，必须先立。这个项目已经为此立过铁律：
「`post.json` 是真相，`manifest.jsonl` 是派生索引，冲突时以文件夹为准，方向永远单一」。
加两份存储而不先钉死方向，会直接退化成"三个都不可信"。

| 层 | 角色 | 方向 | 能否重建 |
|---|---|---|---|
| **本地文件夹** | **唯一真相源**（不变） | — | — |
| **SQLite** | 派生索引：审校台列表、月历、按 tag / 月份 / 状态筛选 | 本地 → DB，单向 | 全量重建 |
| **飞书云盘** | 归档留证 + 跨部门只读 | 本地 → 飞书；只回读目录和任务元数据 | 从本地冻结内容补送 |

**数据库选 SQLite。** 当前只有一台 Windows 运行机器，运营通过同一个后端访问；数据库保存在该机器的本地磁盘，使用 Python 已有驱动。图片继续保存为文件，数据库只保存元信息和引用。这个部署条件符合 [SQLite 官方适用场景](https://sqlite.org/whentouse.html)。

多台机器或多个独立写入服务出现后，重新评估 PostgreSQL，其[事务并发](https://www.postgresql.org/docs/current/mvcc-intro.html)与 [JSONB](https://www.postgresql.org/docs/current/datatype-json.html)适合关系数据和平台扩展字段。本轮不改用 MongoDB：它的[文档数据模型](https://www.mongodb.com/docs/manual/data-modeling/)可表达帖子，但现有关系查询无需为此新增服务和迁移。

SQLite 模式版本为 **2**（`PRAGMA user_version=2`），旧模式由本地源文件重建升级：

| 表 | 字段与约束 |
|---|---|
| `posts` | `task_id TEXT PRIMARY KEY`；`account_dir/platform/post_id/account/owner/coauthors_json`；`created_at/archived_at/permalink/text/source_route`；`month/primary_tag/archive_relpath/folder_name/media_complete/status/row_json`。`(account_dir, post_id)` 唯一。合作方与界面扩展数据使用 JSON 文本。 |
| `post_tags` | `task_id/tag/ordinal`；帖与 tag 组合唯一，帖与顺序组合唯一，外键指向帖子。保存业务分类，首项决定目录。原始 hashtag 保留在原文与展示投影中。 |
| `post_media` | `(task_id, ordinal)` 主键，外键指向帖子；`kind/source_url/local_path/content_type/width/height/byte_size/sha256/storage_status`。顺序从 0 开始，保留视频元数据项。 |

时间、标识和路径使用文本；顺序、尺寸、字节数和完整性布尔值使用整数。未知首次归档时间、媒体哈希等保持 NULL，不推算历史事实。`archive_relpath` 相对归档根；媒体 `local_path` 相对账号目录。平台、账号、月份、状态、分类及稳定分页排序均有索引。

**历史查询是完整契约。** 默认待办可以限制最近 90 天，历史入口须提供服务端分页、总条数、页码/每页数、可用月份、平台/月/tag/状态筛选；可以访问第 91 天及更早的详情，也包括冻结 `.tech` 的只读历史。查询不得触发翻译、图片生成、付费或发布，不裁剪底层归档。详情按稳定 ID 找源文件，不能复用 90 天待办筛选把老帖误报成不存在。

SQLite 一致性检查须实际比较文件事实与数据库的记录集合及展示字段，记录缺失、多余和内容不符项；仅有表或文件存在不算一致。源签名或版本失配时标明索引过期并重建/回退只读查询；写入仍从文件重新校验版本。重建前后人工、付费、审校、发布账本及激活边界的哈希应保持不变。

校验比较 SQL 实际列、分类关系、媒体关系及 `row_json`，并核对外键、记录集合与媒体顺序。实际媒体字节参与源签名，同名等长换内容也会失配。构建使用同目录候选库，校验且关闭连接后原子替换；失败保留上一库并回退源文件。历史分页保留 30 秒已核对快照窗口；详情只展示 `verified_at` 对应的核对记录，查看状态不触发重建。

⛔ **数据库一行也不能是真相：**

- 只有一个 indexer 进程写它，输入只有真相源文件和归档文件夹；
- **任何业务逻辑不得读 DB 做决策**，只有界面读它做展示；
- 冲突时以文件夹为准，跑一条 `reindex` 重建。

这条约束的作用和 `web/` 那条一样：它让 DB 成为模块图上的叶子，不会长成第五个真相源
（[HANDOFF §3](HANDOFF.md) 明写「对账器只读四份产物」）。`tests_hygiene.py` 的 DAG 护栏
会自动守住它——`core/` `routes/` `pipeline/` `publish/` 一律不得 import 索引层。

#### F2-2　本地布局：加一层月份 + 可读的文件夹名

**改哪里**：`core/store.py` 的路径生成、`tools/layout.py migrate`、`post.json` schema

```
archive/in_neakasa.global/
  posts/2026-09/P1-Pro/          ← 月份在外，主 tag 在内；与云盘同形（F2-3、F2-4）
    2026-09-10_1423_IG_P1-Pro_p1-pro-anniversary-sale/
      post.json          ← 来源真相与存储元信息
      text.txt  text_de.txt
      01.jpg  02.jpg     ← 原图，只读，从不修改
      media_de/          ← 德语图。程序产出，人工可覆盖
```

**文件夹名只放业务读得懂的四段：时间戳 · 平台 · 产品 · 摘要**（2026-09-15 业务决定，
改写原来结尾带 `_<post_id>` 的写法）。那串 19 位数字业务看不懂，也不该让业务看。

⛔ **日期必须留在最前面。** `store._folder_month()`、`tools/layout.py` 和
`localize/images.py::_record_path_matches_key()` 都从名字开头反推月份；把平台提到最前
会同时打断这三处，而且不报错。按名排序等于按时间排序这条不变量也压在同一件事上。

**产品段记的是建档时的主 tag，人工改 tag 只移动目录、不改名字。** 所以改过分类的帖子，
名字里的产品会和父目录不一致，**以父目录为准**。这是刻意的：重命名会让每个媒体的
`local_path` 和已经发出去的引用一起失效。

去掉 post_id 之后有两处连带约束，删掉任何一处都会静默出错：

- **归属判定改用 `folder_name`**（`store.post_folder_matches()`）。旧目录没有这个字段，
  继续按 ID 后缀判，两条都要留着——迁移中断时两种名字会同时存在。
- **`images_de.jsonl` 的所有权记录必须带 `folder_name`。** 它决定一张德语图算程序产出
  还是人工放的；认不出来就当人工图，从此永不重做。缺这个字段的旧记录回退按 ID 后缀判，
  两条都不中的行会打印一条告警——这个失败以前是完全无声的。

名字里没有 ID，就可能真的重名：没正文的帖子摘要是空的，`undated` 的帖子连时间戳都没有。
**撞上时在末尾加 `-2`、`-3`，让开的永远是新帖**，已归档的目录名不动。

`local_path` 仍是账号目录相对路径。

新单帖目录的日期、时分与月份统一按**原帖发布的北京时间（Asia/Shanghai）**生成；例如 `2026-08-31T20:00:00Z` 进入 `2026-09/`，文件夹前缀为 `2026-09-01_0400`。缺日期、非法日期或没有明确时区时使用 `undated`。`created_at` 原样保存；`archived_at` 独立记录首次入档的实际 UTC 时刻，旧记录缺少它时保持未知。旧目录及其月份不自动改名；分类移动只在现存月份内进行。

下载先做 MIME、签名和完整图片解码核验，再写同目录临时文件、flush/fsync 和原子落盘，保存实际 MIME、尺寸、字节数与 SHA-256。旧原图从不被新字节覆盖；源图修订另存文件，原文历史追加至 `source_history.jsonl`。`source_media_complete` 表示平台是否提供完整媒体列表，`media_complete` 还要求下载完整；已知新版本缺图会保留已取得内容并显示待补齐。只返回轮播封面的不完整响应不能替换已有完整媒体列表。

**摘要 slug 只在创建时算一次，之后永不重算**，结果写进 `post.json` 的 `folder_name`。
原帖被编辑就重算的话文件夹会改名，所有 `local_path` 一起失效。

**slug 限长 30 字符并转 ASCII kebab-case。** Windows 默认 260 字符路径上限在
`media_de/01.jpg` 这一层已经不宽裕，且正文里有大量 emoji。

**回填可以按 `--days N` 收紧到最近 N 天**，让基线边界可复核，而不是依赖滚动手感。
算不出日期的一律保留——内容已经抓到手，媒体 CDN URL 带签名有时效，丢掉重抓不回来。
人工滚动这条不变（红线 2），窗口只收紧归档范围。

迁移成本几乎为零：2026-09-14 清库后两个账号都是零归档，直接按新布局建；
`tools/layout.py migrate` 已支持两层→三层，留给将来可能出现的存量。

#### F2-3　tag：自动预填 + 人工可改

**改哪里**：`post.json` 新增 `tags` 字段、`core/store.py` 的预填逻辑、审校台的 tag 编辑

**tag 存在 `post.json` 的 `tags` 字段里**（数组，一篇可以有多个），同时用主 tag 组织本地目录。

| | |
|---|---|
| **自动预填** | 首次归档按 `[storage.product_aliases]` 归一型号；完整 hashtag 优先，正文补充，长型号优先、词边界匹配。`P1 Pro`、`P1Pro`、`#NeakasaP1Pro` 均为 `P1 Pro`，`M1` 不命中 `M10`。 |
| **人工可改** | 审校台上业务可以改、可以补、可以加自定义 tag |
| **匹配不上** | 进「未分类」，**不猜** |

初始别名表覆盖现有型号；不猜测未知产品。同一别名不能指向多个产品。`tags_origin` 区分 `auto` 和 `manual`；旧记录缺少来源按 `legacy` 展示。已接受的源帖修订会重算自动分类；人工和历史分类保持不变，包括人工明确保存的空数组。原文与原始 hashtag 不被分类规则改写；业务自定义 tag 仍可人工保存。

**本地目录也按主 tag 分层**（2026-09-14 业务决定，改写原「tag 不进本地目录」）：
`posts/<月份>/<主 tag>/<帖子>/`，与 F2-4 的云盘结构同形，业务在本地和云盘看到同一套层级。
落点只由 `tags[0]` 决定，匹配不上型号表的进 `未分类/`；其余 tag 仍只在字段、SQLite
和审校台里生效——目录树表达不了"一篇帖归两个产品"。

代价是明确接受的：改主 tag 要在锁内移动目录、重写每个媒体的 `local_path`、追加
manifest 行。三条对应的实现约束不能省：

- **按 `folder_name` 定位要扫月份下的各 tag 目录，不能照当前 `tags[0]` 拼路径。**
  索引可能落后于一次移动，拼出来的路径会把已归档的帖子报成不存在。
- **tag 解析必须早于落点计算。** 媒体下载先于 `append()` 发生，晚一步会让图片落进
  `未分类/` 而 `post.json` 落进 `<tag>/`。
- **认路径层级的地方要认三层。** `localize/images.py` 的所有权记录原先只认 4/5 段路径；
  认不出第 6 段就会把程序产出的德语图判成人工图，从此永不重做，而且不报任何错。

移动先追加 `tag_moves.jsonl` 操作意图，在账号写锁内搬目录、更新当前路径、追加图片归属映射及 manifest，最后追加完成记录。中断可由下一次写入或 `tools.layout recover-tags` 恢复；损坏记录停止写入等待核对。下载完成后持同一锁重新查实际目录。历史原文记录不重写，历史媒体按帖子身份与文件名定位到当前目录，镜像再核对已有 SHA；人工文件随整篇目录保留。

tag 目录名另有安全化规则（`store.tag_component()`）：`_safe_folder_name()` 只允许 ASCII，
而 `未分类` 和业务自定义 tag 都可能不是。上限 20 字符，超出截断加哈希后缀；
实测最深路径 222 字符，仍在 Windows 260 以内。

#### F2-4　飞书云盘镜像：归档留证 + 跨部门只读

**改哪里**：新建 `core/mirror.py`、`config.toml [mirror]`、常驻调度进程挂一个镜像任务

⛔ **本轮不做（2026-09-15 业务决定，状态词「明确延期」）。** `[mirror].enabled = false`
是这个决定的落点，**不是"还没做完"**——代码、目录规则和恢复路径都已经离线验过，
不要因为看到 `disabled` 就去补实现。

理由是外部依赖：Drive API 只认企业自建应用的 tenant token。消息通道已经改走群 webhook
机器人绕开了 AppSecret（F4-1），但云盘绕不开——机器人没有云盘接口。本轮先把本地和
SQLite 两层跑成真实可用的，云盘等 AppSecret 到位再开。

**重启条件**：拿到 `FEISHU_APP_ID` / `FEISHU_APP_SECRET`，填 `[mirror].root_folder_token`，
把 `enabled` 改成 `true`，然后按 [MANUAL_STEPS §7.1](MANUAL_STEPS.md#71-原帖云盘接入与恢复) 做受控目录验收。

⚠️ **这个决定留下一个敞口，要记住它是敞口而不是已解决。** `mirror_state = true` 原本
兼做 `state/` 的异地备份，其中 `state/published.jsonl` **不可重建**——丢了会让已发过的
帖子被再发一遍，而 2026-09-14 那次清库就是没有备份的。云盘不做就等于本轮没有异地备份，
须由人定期把 `archive/` 与 `state/` 拷到本机之外的另一块盘，见
[MANUAL_STEPS §1](MANUAL_STEPS.md#1-接续运行数据前先备份和核验)。

下面是已经定好的设计，开启时照此执行。

用途已确认：**以归档留证为主，兼作跨部门只读协作与备份，不会反向修改。**
因此镜像是**单向**的，不需要设计受控回填口——这省掉了整个方案里最容易出事的一块。

tag 母目录在这一层 materialize。业务看到的是这个结构——**月份在外，产品规格在内**：

```
Neakasa 社媒归档/
  2026-09/                                       ← 月份（外层）
    M1-Pro/                                      ← 产品规格 tag（内层）
      2026-09-10_1423_IG_M1-Pro_m1-pro-anniversary-sale/
        01_原帖/     text_en.txt · 01.jpg… · 元信息.json
        02_待发布/   text_de.txt · 01.jpg…                   ← 审校通过时写入
        03_已发布/   text_de.txt · 01.jpg… · 排期回执.json    ← 提交回读确认后写入
    S1-Pro/
      2026-09-14_0930_FB_S1-Pro_s1-pro-fellpflege/
    未分类/                                       ← 型号表匹配不上的进这里，不猜
      2026-09-18_2140_IG_herbst-kampagne/
  2026-08/
    M1-Pro/
```

云盘直接用本地的文件夹名，**不再另加平台前缀**——名字自己已经带平台段了。
2026-09-15 之前建的旧目录名没有平台段，镜像时补一个 `IG_` / `FB_` 前缀，
否则云盘上两个平台的同月同产品会混在一起分不出来。

**为什么月份在外侧**

**① 留证语义和月份天然对齐。** 一个月过去之后，那个月份目录就基本封存——不再有新帖写入，
只剩偶发的 tag 重挂。反过来（tag 在外）的话，任何月份的新帖都会往老 tag 目录里追加，
**没有一个目录是能封存的**。

**② tag 是会变的，移动范围要小。** 月份在外，改 tag 只是在同一个月份目录内换一层；
tag 在外，改 tag 要跨月份目录搬。

**③ 业务的实际动作是按月的。** "这个月发了什么"——打开一个目录就看完了。

代价要说清楚：想看"M1 Pro 有史以来的全部帖子"，在云盘上要翻多个月份目录。
这个代价是刻意接受的，因为它有更好的去处——**按 tag 横向检索由审校台承担**
（F2-1 的 SQLite 索引本来就支持多条件筛选）。

> **云盘负责"留证"，审校台负责"检索"。** 让云盘的目录树同时表达两个维度，
> 结果一定是两个都表达不好。

**五条规则**：

1. **写入后内容不再修改。** 同一篇改了重新审校，新增 `02_待发布_v2/`，**不覆盖 v1**——
   "当时到底发的是哪一版"必须永远查得到。
2. **`03_已发布/` 只在提交回读确认成功后写入**，不在点击提交时写。半完成状态不进留证目录。
   目录名沿用历史约定，但“已发布”在这里表示**排期回读已确认**，不表示实际公开；公开状态另存只读观察结果。实现与真实验收见 §6.1 的 S0-2 和实施清单。
3. **落点由主 tag（`tags[0]`）决定。** 云盘的目录树只能表达一个维度，而一篇帖可以有多个 tag。
   其余 tag 只在数据库与审校台里生效，**但 `元信息.json` 里记录全部 tag**——
   留证不丢信息，只是目录不表达。
4. **改 tag 只移动落点，不改内容。** 留证保护的是"内容不被改写"，不是"路径永不变"。
5. **匹配不上型号表的进 `<月份>/未分类/`**，不猜。业务在审校台补了 tag 之后重新挂。

原帖内容版本由来源身份、原文、媒体实际字节、顺序和可用性决定；分类、目录路径、抓取入口及镜像时间不参与。缺图可以镜像文字和现有原图，附 `原帖不完整.json`；补齐形成新完整版本。空正文通过空文件清单表示，不能伪造文字。只改分类不新增内容版本或重传原图，移动确认前显示等待同步。

创建目录、上传、分片准备/分片/完成与移动均先持久化操作意图，再保存回执。响应丢失或中断后的未知结果进入 `uncertain`，不能直接重发。`status` 只读本地；`preflight` 完整分页读取目录元数据，只给唯一目录候选，同名文件不能证明字节相同；`resolve` 按操作 ID、冻结摘要、远端 token 与人工说明结转，或确认未创建后恢复待执行。结转本身不上传。

云目录名按 UTF-8 最多 256 字节校验，分类目录复用本地命名函数；普通上传最大 20,971,520 字节，较大文件使用带持久进度的分片上传。分片事务超过官方 24 小时有效期停止并等待处理；finish 结果未知先核对。创建和上传串行限速，移动按 20 次/分钟的较严限制执行。HTTP 429 明确拒绝可退避；权限、容量、每日配额或配额范围未知停止；传输歧义保留待核对。错误只保存状态、错误码与请求标识，不保存原始响应体。接口与权限准备见 [MANUAL_STEPS §7.1](MANUAL_STEPS.md#71-原帖云盘接入与恢复)。

**`state/` 一起镜像**（已定）。它不是"内容"，但 `state/published.jsonl`（111 KB）
**不可重建**——丢了会导致幂等失效，已发过的帖子可能被再发一遍。
这是备份契约的一部分，不能仅因代码有 mirror 就宣布备份敞口已关闭。应周期性保存不可重建账本与相关配置，记录备份时间、文件数、字节数、哈希和恢复验证；大型 probe、截图、冻结媒体按版本单独保存，并在账本中保留引用。原始凭据保存在本机受控备份，不上传到可公开访问的云盘。

Web 批准、CLI 发布和人工结转均须走同一冻结快照和状态投影。镜像队列引用已冻结的版本，旧版缺失只能用那一版的字节补送；重试不重新读取当前内容冒充旧版。验证上传、移动 tag 落点、v1/v2 并存、冻结补送、失败恢复与远端只读权限，分别留远端文件 ID。

⛔ **云盘原文与图片不自动读回或覆盖本地。** hygiene 仅放行目录列表和异步任务元数据 GET。人工验收下载到隔离位置比较哈希，不构成自动恢复入口。

#### F2-5　源帖变更的处理

**改哪里**：`core/translated.py` 的哈希校验、`review_items.jsonl` 的 `stale` 标记

提频会看到源帖被编辑。译文绑定 `source_text_sha256`；整篇来源还必须有包含**原图实际字节哈希、数量和顺序**的 source fingerprint，不能只比较 URL、文件名、大小或首图。URL 不变而内容更换、加图/删图、调换两张图都要被识别。旧模型候选、许可和批准依据按各自绑定的来源版本失效；已排期的冻结内容保持不变并提醒人工处理。
四种情况要分开：

| 情况 | 处理 |
|---|---|
| 尚未翻译 | 直接用新版本，无成本 |
| 已翻译、未审校 | 机器译文作废重译；本篇重新进待审队列 |
| **已有人工版译文** | **不作废。** 保留人工版，标 `stale: true`「原文已变更，请复核」，重新进待审队列 |
| **已排期或已发布** | 推飞书告警，**不自动改已排期的内容**。由人决定要不要撤下重来 |

第三条的理由很简单：直接丢弃人的劳动，两次之后她就不改了。

第四条是提频带来的新情况：每天一次的时候"源帖在我们排期之后被编辑"几乎遇不到；
每小时一次之后它会变成常态。

来源文字的 `source_text_sha256` 在归档、翻译、审校、就绪事件、快照和发布比对中采用同一规范，统一去首尾空白后计算；AST 检查防止同名字段重新出现另一算法。风险高亮另存原始扫描文字的 `scan_text_sha256`，保护字偏移；最终提交文案、原始证据和媒体字节指纹不套用去空白规范，仍绑定实际内容。

#### F2-6　接续现有运行数据与可恢复备份

接续原 archive/state 时不能创建一套空发布账本“重新开始”。接续顺序为停写、备份 archive/state/运行配置、核验不可重建账本、在副本检查派生一致性，再用不入库的本机路径配置绑定。所有 Web/CLI/批处理/调度入口必须读取同一配置、环境文件、解释器、数据和锁，保留原激活时间和历史发布引用。

备份应包含 `config.toml`、存在时的 `config.local.toml`、本机 `.env` 的受控副本及解释器位置/版本记录；凭据不进仓库、日志、公共证据。审校账本非空坏行、截断尾部、非法状态/revision/时间必须显式失败并定位文件与行，保留现场后在副本修复。不能从云盘、SQLite 或空默认值自动重建人的决定或发布历史。

### 2.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|
| DB 可从文件夹全量重建 | 删掉 DB 跑 `reindex`，结果与重建前逐字段相同 |
| 历史可分页且不触发处理 | 老帖跨多页、平台/月/tag 组合筛选，页码/总数正确；第 91 天以前详情可读，付费与业务账本零写入 |

| 周期与大型证据留存 | 两个备份周期可恢复；大型媒体/probe 分版本保存，旧版本补送不读取当前文件 |

**`preflight`**：DB 与归档的差异条数（应恒为 0）、云盘镜像最后一次成功距今多久、
本地归档与镜像的篇数差。

## 3. 阶段三 · 翻译、标签与链接

### 3.1 业务诉求

- 用提示词文档规范文案翻译与图内文字翻译；
- 模型产出后若人工认为不合适，允许人工输入优化指令让模型重新生成；
- 英文 #tag 有相当一部分来自英语区热搜，直译到德国站匹配不上，希望自动获取德语地区
  热度较高、语义接近的 #tag 并推荐给业务审核选择；
- FB 支持文案内联链接、IG 不支持（只能引导去 bio），且英德落地页不同，不能原样复制。
  需要设计合理的人工审校页面与操作。

### 3.2 这一步谁在做什么

启用内容处理后，完整采集结果逐篇触发翻译与出图。同轮其它帖失败不影响已经完整入库的帖子；
人工恢复成功后在下一次维护时受理。每份采集结果只有一次入队回执，重复扫描、飞书确认与进程重启
不重复受理；激活边界、账号、来源许可及统一预算仍在付费前检查。未完整素材继续交人处理。

**这是她真正花时间的地方。** 前两个阶段她看不见，后两个阶段她只是点几下。
一篇帖子 10 分钟里，有 8 分钟花在这一节的产出上。

所以这一节的设计原则和别处不同：**别的地方优先考虑"正确"，这里要优先考虑"她会不会看"**。
一个正确但她会跳过的提示，等于不存在；一个让她多按三次才能确认的操作，
用两周之后就会变成"直接点通过"。

### 3.3 一个结构性发现：这不是翻译，是本地化

> **德语文案不再是英文文案的翻译，而是平台相关的本地化。**

FB 能内联链接、IG 不能；FB 的德语落地页和英文落地页不是同一个；#tag 要换。
三条合起来意味着 **FB 版和 IG 版的文案物理上就是两份不同的东西**。

2026-09-11 之前的旧代码曾**一次提交同时发到 FB 和 IG、用同一份文案**，并沿用 composer 默认双选。这段历史解释为何 S2-1 是硬前置；当前契约与实现方向是单一来源对应单一渠道，缺证据就阻止提交。

**所以 S2-1「两条独立车道」从优化项变成了本阶段的硬前置。**
不改它，短链和 #tag 这两个需求物理上装不进去。返工路径见 §6.2。

好消息是新的业务模型让界面简单了：FB 源 → 德国站 FB Page，IG 源 → 德国站 IG，
**每篇帖子只有一个目标渠道**，审校页不需要同时编两套文案，只需要知道"这篇走哪套规则"。

### 3.4 要实现什么

#### F3-0　目标语言：本轮只做德语

⛔ **法语本轮不做（2026-09-15 业务决定，状态词「明确延期」）。** 需求原文写的是「英译德、法」，
这里明确收窄。**不是"还没做完"，也不做 locale 抽象**——德语继续硬编码在文件名、字段名、
配置和发布目标里。

**将来补法语时要动的不只是提示词**，把代价记在这里，免得下一个人照原始需求直接开工：

| 层 | 现在的样子 |
|---|---|
| 文件与字段 | `text_de.txt`、`media_de/`、`images_de.jsonl`、`body_de`、`text_de_sha256` |
| 提示词 | `prompts/translate_de.md`、`prompts/image_de.md`，各自一个版本号 |
| 配置 | 单份 `[translate.glossary]`、单份 `[publish.link_map]`、单个 `ig_bio_url` |
| 发布目标 | `instagram_account = "neakasa.de"`、`facebook_page_name = "Neakasa Deutschland"` |
| 标签库 | `state/de_hashtags.jsonl`，Trends 采样固定 `geo=DE` |

⚠️ **真正贵的是发布契约，不是改名。** 当前是「一篇源帖 → 一个目标渠道」；加法语会变成
每平台德法各一条、共 4 条车道，连带改冻结快照、排期占用与飞书卡片。
前置还在业务侧：法国站 FB Page 与 IG 账号、法语术语表、法语落地页映射、法语 bio 聚合页。

#### 审校页的文案编辑区拆成三个区块

**改哪里**：`web/ui/src/components/TextCompare.vue` 拆成三个组件、`web/api/reader.py` 的字段

2026-09-11 当时的界面是一个大 textarea 左右对照。三个需求（优化指令、#tag、短链）塞进同一个
textarea 会互相干扰，所以拆开：

```
┌─ 主文案 ───────────────────────────────────────────────┐
│  英文原文            │  德语译文  [编辑] [✨ 优化指令…]  │
│  ……                  │  ……                              │
│  🔴 2 处  ⚠ 3 处          [下一处 →]                     │
└────────────────────────────────────────────────────────┘
┌─ 话题标签 ─────────────────────────────────────────────┐
│  #CatLover → #Katzenliebe ✓映射   #PetCare → ⚠ 待确认   │
│  #Neakasa → #Neakasa ✓品牌保持      [+ 添加] [查热度]    │
│                                              6 / 30 标签 │
└────────────────────────────────────────────────────────┘
┌─ 链接 ─────────── 本篇是 Facebook 帖 ──────────────────┐
│  原文  https://dada.link/mKbGrw                         │
│  德语  https://de.neakasa.com/…  ✓映射表  [打开检查]     │
└────────────────────────────────────────────────────────┘
                                    正文 1,842 / 2,200 字符
```

IG 帖时第三块自动变形：

```
┌─ 链接 ────────── 本篇是 Instagram 帖（不支持内联链接）─┐
│  原文里有 1 个链接：https://dada.link/mKbGrw            │
│  ⚠ IG 文案里的链接不可点击，已从正文中移除               │
│  引导话术  ○ Link in Bio 🔗   ○ Mehr dazu im Profil…    │
│            ● 自定义：[                              ]   │
│  当前 bio 指向：https://linktr.ee/neakasa_de （只读）    │
└────────────────────────────────────────────────────────┘
```

**为什么值得拆成三块**——三条都是真实的：

1. **短链留在正文里会被模型顺手"翻译"。** [HANDOFF §6](HANDOFF.md) 说优惠码是最危险的
   一类，理由是"任意字符串却长得像单词"，**链接完全同型**。拆出去之后它根本不进翻译的输入。
2. **`hashtags_preserved()` 那道确定性检查要换语义**（从"逐个原样照搬"改成"映射/推荐已确认"），
   分区之后它不会和正文的金额检查搅在一起——[风险与标记约束](../web/DESIGN.md#风险、标签与运行状态)
   那条"两种标记不能混成一种颜色"的原则在这里同样适用。
3. **两个计数器有了明确归属**，接近上限时能指出是哪一块。

#### F3-1　短链映射表

**改哪里**：`config.toml` 新增 `[publish.link_map]`、`core/translated.py` 新增链接抽取与回填、
`publish/compose.py` 的离线闸

语义**照抄 `price_map`**：一张业务维护的「英文落地页 → 德语落地页」映射表，
**没映射过的链接第一次出现时停下来问人，已过目的直接放行**。这个模式业务已经用过一次
（金额），不需要重新解释。

它**不需要业务预先给一份清单**——`price_map` 那 46 条就是这么长出来的：
第一次遇到一个新金额就停下来问，问过一次就长一条。链接同理。

| | |
|---|---|
| 落点 | `config.toml` 的 `[publish.link_map]` |
| 分类 | 按 [REQUIREMENTS §5.3](REQUIREMENTS.md) 属于**业务决策**，与 `price_map` 同级 → Web 上只读 |
| 未命中 | 进人工队列，**不是丢弃**，也不是自动直译 |
| 附加校验 | 审校台提供「打开检查」按钮，人工确认落地页真的存在且是德语站 |

Facebook 运营可在正文光标处插入 `{{link1}}`、`{{link2}}` 等对应链接占位符。最终正文按链接区已选定的德国 URL 替换，未插入的有效链接仍追加到末尾，已插入的不会再追加一份。未知编号、缺落地页或损坏的占位符阻止通过；计数与预览使用替换后的完整文案，不能按短占位符低估长度。Instagram 不支持这种占位符，继续使用稳定 bio 话术。

#### F3-2　IG 的 bio 引导话术

**改哪里**：链接区组件的 IG 分支、`config.toml [publish].ig_bio_url`（只读展示用）

IG 帖的链接区变成话术选择器：几个预设话术 + 自定义输入。

**不做「这篇要求 bio 指向 X」的动态提醒**，因为它和定时发帖是硬矛盾：

```
9/10  她审完，排期到 9/15 10:00 发布
9/15  10:00 帖子自动发出，文案写着"Link in Bio"
      ↑ 谁在这个时刻去把 bio 改成这篇对应的落地页？
```

帖子是排到未来自动发的，bio 是账号级的、一次只能放一个。要让每篇帖子的 bio 都对，
就得有人在每个发布时刻手动去改 bio——那等于把定时发布的价值抵消掉。

**所以 bio 必须是一个稳定的聚合页**（Linktree，或 `de.neakasa.com` 上一个入口页）。
系统只在链接区**只读显示**当前 bio 指向（从配置读），不产生任何要求她去做的动作。

⚠️ 聚合页是业务要先建的东西，不是系统功能。没建之前这一行显示"未配置"。见 §8。

**原文那句 bio 引导要在翻译阶段就删掉。** IG 原帖常有一句 "check the link in our bio"。
URL 被 `without_urls()` 摘走了，**这句话本身还在**，模型会照译；而链接区又会独立填上引导话术，
成品于是有两句。所以提示词按渠道渲染（`build_system_prompt()` 的 `platform` 必填），
IG 版明确要求整句删掉、不要补写替代说法。

未绑定人工决定的 IG 草稿，只要原文有 URL 或明确的 bio / profile 引导，就在独立链接区预填
一条引导话术；原文没有 URL 的 `link in bio` 也适用，避免正文删句后引流信息消失。
业务保存过的引导选择完整保留，包括明确选择「不添加」；重新打开或后台重译不会补回。

⚠️ **提示词不是唯一一道。** 模型不照做时，编辑器给一条黄色提醒
（`localization.mentions_profile_link()`）。它只能是提醒：自然语言判断误杀的代价是
拒绝一次已付费的产出，而德语的 `Bio` 还有"有机"的意思，这个品类真会写 `biologisch abbaubar`。

#### F3-3　单篇优化指令 vs 模板提示词

**改哪里**：`localize/text.py` 与 `localize/images.py` 的提示词组装、
`translated.jsonl` / `images_de.jsonl` 新增 `refine_instruction` 字段

`prompts/translate_de.md` 和 `prompts/image_de.md` 已经存在且可直接编辑。
要加的是**单篇的临时优化指令**，它**追加在模板之后，不改模板**。

输入框旁给几条**预设说法**，点一下追加（不替换已输入内容），每条带一句"为什么这么说管用"：
业务写"排版不好看"模型改不动，写"这一段太长把版面挤了，请用更短的说法重排"才对得上模板里的
溢出阶梯。预设覆盖的五类是溢出、文字压图、用词错、改动范围超出、型号/优惠码被改——都是实际会发生的失败。

**图片模板的溢出处理是有优先级的阶梯，不是一句话。** 德语比英语长 10–30%，"放不下"是常态：
先换更短的德语说法 → 在原文字块外接矩形内重新断行 → 同一矩形内等比缩小字号（下限约 85%）→
**仍放不下就保留英文原文**。禁止改矩形、拉伸字形、压到产品上、加色块腾地方，并写明理由
（"读者看到的是排版事故，业务无法用文字指令修回来"）——裸禁令在长提示词里最先被丢掉。
⚠️ 旧模板同时写着"保持行数"和"可重新断行"两条互斥规则，模型会随机挑一条，这是版面事故的主因。

| | 模板提示词 | 单篇优化指令 |
|---|---|---|
| 影响范围 | 全部帖子 | 一篇 |
| Web 上 | **只读展示** | 业务可输入 |
| 留痕 | `PROMPT_VERSION` / `IMAGE_PROMPT_VERSION` +1 | 写进 `translated.jsonl` / `images_de.jsonl` 的 `refine_instruction` |

**另有一条反方向的路：优化建议（2026-09-15 新增）。** 两条都要，因为它们回答的不是同一个问题：

| | 单篇优化指令 | 优化建议 |
|---|---|---|
| 谁先开口 | 人给指令 | 模型给清单 |
| 产出 | 重写后的整篇译文，作为机器候选 | 逐条 `{quote, replacement, kind, why}`，`why` 用中文 |
| 落点 | `translated.jsonl` | `state/translation_suggestions.jsonl` |
| 采纳 | 人点「采用到正文编辑区」 | 人逐条点「采用」，在编辑区做替换后仍需保存 |

文案重写任务在受理时冻结翻译提示词版本；排队期间版本变化时先停止旧任务。结果缺少版本或版本
不再当前时，保留记录供查看但禁用采用。已保存人工稿不因提示词升级失效。
保存期间仍可继续编辑：返回成功只确认点击保存时的快照，等待时追加的输入保留在编辑区，需再次保存。

⛔ **建议只是清单，后台任务不碰任何一份译文真相源**（红线 6）。它和两种优化共用
`refinements.jsonl`、同一把锁和同一个付费执行器，作为第三种 `kind`，不另起一套任务系统。

三条必须钉死的规则：

1. **`quote` 必须在当前德语正文里只出现一次**，否则「采用」会改错地方。定位不到的条目
   在解析时就丢弃，**不做模糊匹配**；丢了几条要报出来，不静默吞掉。
2. **每条建议都要过金额、标签、链接与链接占位符检查**，相对点击时的德语正文检查不变。
   人工已经换过的德国站价格和标签不能被要求退回英文原文。越界的单条丢弃，其余建议保留。
3. **译文或源文改动后旧建议标为失效**，「采用」停用，不自动重做。判据是
   `source_text_sha256` + `text_de_sha256` + `SUGGEST_PROMPT_VERSION` 三者同时成立。

生成请求冻结当前编辑区正文，支持尚未保存的修改；排队和执行时不换成磁盘上的另一个版本。
源文和德语输入均先摘除 URL。页面逐字符核对返回的正文快照，未保存的任意正文修改也会立即
停用旧建议；采用一条后其余建议同样需要重新核对。忽略状态只属于本次生成，下一次结果重新展示。

⚠️ **前端的替换必须用函数形式的 `String.replace`。** 即使搜索的是普通字符串，替换串里的
`$&`、`` $` `` 仍会被当成特殊模式展开；Python 的 `str.replace` 没有这一条，两边看起来一样。

⛔ **模板提示词在 Web 上只读。** 按 [REQUIREMENTS §5.3](REQUIREMENTS.md) 的二分，
它属于"改错会静默影响全部产出"那一类。要改走显式申请。

**注释必须跟着上界面。** `prompts/*.md` 和 `config.toml` 的注释是这个项目最有价值的
资产之一（每个参数为什么是这个值、改了会怎样），Web 表单会把它们扔掉——
只读展示时要带上原文注释。

本轮设置页的两个可写项为 `default_times`（默认 `16:00`、`23:00`，只作业务时区预填值）和 `snooze_default_days`（默认 3 个上海工作日）。版本冲突拒绝保存，并保留原注释和其它配置；频率、账号、预算、许可、映射表及模板等受控参数保持只读且有原因说明。

#### F3-4　文案重生成与图片重生成的成本差两个量级

**改哪里**：`web/api` 新增异步任务端点、`core/paid_requests.py` 的预算闸调用点、
`config.toml [image].max_refine_per_media`

| | 文案重生成 | 图片重生成 |
|---|---|---|
| 历史单次成本（2026-09-11 估算） | DeepSeek，当时全月约 US$1 | **当时约 US$0.211 / 张**；本次按当前报价与 usage 留账 |
| 历史耗时（2026-09-11 样本） | 秒级 | **当时约 2.5 分钟 / 张**；不是当前耗时保证 |
| 界面 | 直接点，无需确认 | **按钮上直接显示本次预计花费** |
| 限制 | 无 | **3 次 / 张**；走已有 `RequestController` 预算硬闸 |
| 执行方式 | 持久化任务，返回 job ID | **异步任务**，刷新继续查询同一 job ID |

⛔ **重生成不得覆盖人工放进 `media_de/` 的图。** [README](../README.md) 明写
"人工放进去的文件程序不得覆盖——设计同事手工修的那张一定比模型那张对"。
重生成产出落到新版本号，人工图仍然优先渲染。这一张换成人工图之后，**前后端模型优化入口停用**：
人工图优先于程序产出，再生成一版也不会被采用，那笔钱是白花的。

**三次预算的前提是上一版还找得回来。** 每张图生成过的版本在审校台逐版可见（时间、当次指令、
改动像素占比），可以打开预览与当前图片比较后换回去；预览不改变当前版本。
换版只追加一条所有权记录，**不调用模型、不计费、不占次数，也不增加日/月预算统计**。
上传或换版与图片生成共用锁；排队优化在调用前复核审校版本，过期选择不能被旧任务覆盖。
图片优化产物写入失败时保留上一版选择；失败产出与请求记录不删除，受理次数和已发生费用不回退。
不做这件事的话，第二版比第一版差就只剩下载改图一条路，3 次预算实际只有 1 次可用。

**业务可以直接上传自己处理好的图替换某一张。** 落点是 `media_de/NN.<ext>`，最大 32 MB。
人工选择按文件名和哈希追加到 `media_de/manual_uploads.jsonl`；即使上传的是历史生成图，也按人工选择使用。
上传不写程序所有权账本 `images_de.jsonl`。先写好新文件并将旧件备份到 `media_de/superseded/`，
再替换当前图；写入失败保留旧图。审校页显示人工图标记、替换时间及超线的画幅提示。
人工图生效时历史生成版本仍可预览，采用按钮停用，避免出现“已采用”却仍在发布人工图的假成功。

只有一版历史图也提供预览入口；冻结账号只能查看，不能采用版本。文案优化候选尚未采用时，
已有德语图沿用同源且仍有效的生成依据，普通人工正文编辑也不触发重新出图；显式图片优化使用当前稿。
审校、下载和发布使用一致的图片有效性判据，源文、原图或提示词过期不能靠选择历史版本绕过。
下载包内文案与服务端最终文案渲染一致，包含 FB 德国落地页或 IG CTA 和本地标签。

⚠️ **上传是换素材，不是转交人工。** 替换后这篇记为 `edited`，继续走系统排期；`handed_off` 是终态，
表示"系统不再代发"，必须由菜单内单独的确认动作触发。“下载本篇素材”不改变状态，资源包说明也保留系统排期语义。

⚠️ **这是本项目第一次让非开发者触发付费调用。** 预算闸从"防止脚本跑飞"变成
"防止有人反复点"——两者的触发模式完全不同，闸的位置要重新检查。
3 次/张的上限意味着单张封顶 US$0.63，月预算 US$60 撑得住。

上面的美元数是历史估算，预算判断始终使用当前配置和统一账本。**每图最多受理三次优化**，在受理入口计数，并发点击也不能超过；失败和不确定请求不能用删 job 或换入口绕过。

模型任务必须关联来源版本、提示词版本、拥有进程身份、paid request ID 和更新时间。恢复要区分仍在执行、进程已中断、请求未发出、结果已落盘、远端可能已计费；有 owner 在运行时不能抢占。恢复入口先对账并以 job 版本做并发检查，返回可执行下一步，**恢复本身不隐含再次付费请求**。不确定项保留需人工核账状态，旧候选不再允许应用，已存在人工文案/图片保持优先。费用统计包括首次处理、重生成、风险扫描、已知用量和不确定费用，不能用任务次数代替账单。

“源文没变”与“模型产物仍为当前版”是不同判断。`stale: false` 只说明源文哈希关系，不能保证旧 prompt 的机器译文/图片仍有效；页面须给出 machine_current、机器 prompt 版本与当前 prompt 版本。当前翻译 prompt 为 7，图片 prompt 为 3。2026-09-16 主检出业务归档仍为空，历史样本不能充当当前素材或真实验收证据；版本变化也不代表可以自动付费重做。

#### F3-5　德语 #tag 热度推荐

**改哪里**：新建 `routes/hashtags.py`（采集）、`core/hashtag_rank.py`（排序）、
`state/de_hashtags.jsonl`、常驻调度进程挂一个周更任务

⛔ **本轮不做（2026-09-15 业务决定，状态词「明确延期」）。** 标签只由业务在标签区手工
选取与编辑。`[hashtags].enabled = false` 是这个决定的落点，**不是"还没做完"**——三个
采集器的代码、排序和降级路径都已经离线验过，不要因为看到 `disabled` 就去补实现。

理由是三个来源当时全都取不到数：同类德语账号名单业务给不到（§8）、Google Trends 公开页
已 429、IG `.global` 也在 429 停机。留一个只会显示"排序依据不完整"的按钮，不如先不显示。

⛔ **关掉的是整条链路，不只是采样。** `enabled` 原先只被 `SamplingConfig.load()` 读，
而**德语候选词那次 DeepSeek 调用排在采样之前**——只关采样的话，业务每点一次按钮仍然产生
一笔账单。闸放在 `pipeline/hashtag_suggestions.suggestions_enabled()`，审校台据此隐藏按钮。

**重启条件**：恢复 9224 会话访问，业务给出德语同类账号名单，把 `enabled` 改回 `true`。

下面是已经定好的设计，开启时照此执行。

先说清楚一件事：**IG / FB 不存在"热搜榜 Top-N"这种接口。** 能采到的是三个可计算的量，
合起来才构成这个系统里"热度"的定义：

| 信号 | 采什么 | 来源 | 频次 |
|---|---|---|---|
| **量级** | 标签累计帖子数 `media_count` | IG 搜索接口（登录态，探测号） | 按需，只查候选词 |
| **当前热度** ⭐ | 同类德语账号近 14 天用了哪些标签、各用几次 | 一组德语宠物 / 清洁类账号的公开时间线 | 每周一次 |
| **趋势方向** | 同组德语候选的相对兴趣随时间变化 | Google Trends 公开页面导出的 CSV，`geo=DE` | 每周一次 |

第二个是主信号，也是这个方案里最值钱的一条：它拿到的是"德语圈这两周实际在用什么标签"，
比任何通用热搜榜都更贴我们的品类。而且它每周跑一次就够——标签热度不是按小时变的。

**本轮先跑降级形态。** 主信号需要一份德语同类账号名单，业务暂时给不到（见 §8）。
所以本轮允许主信号暂时缺数据，**三类采集器及业务接线都在范围内**；名单为空时只跳过该来源。实现一个来源不能关闭另两个来源：

```
名单为空  →  跳过周更采集，不报错
          →  推荐仍然产出（LLM 候选 + media_count + Google Trends 排序）
         →  界面上标明「缺少同类账号采样，排序依据不完整」
```

Google Trends 使用已确认的公开 CSV 路线：同一个英文标签的 3–5 个德语候选须在**同一候选组、同一个 `geo=DE`、相同时间范围与同批比较**内采样。它是组内归一化相对兴趣，不能把不同组/不同时间批次的 0–100 分数横排，也不能宣称为 IG 德国热搜。记录原始 CSV/哈希、候选组、地域、时间范围和采样时间；无可比数据则明示降级。

公开导出用请求专属的被动控件证据，绑定实际 CSV 下载按钮；任意登录按钮/链接不是导出证据。导出/导入保留原始 BOM/CRLF 字节并核 context 摘要，支持周/月 CSV。429/challenge 持久停止；只读状态给版本，人工核对恢复后在共享锁内做版本 CAS，恢复不代表已经导出。2026-09-12 的公开页已 429 停止，新适配与离线测试不算真实采样。

IG `media_count` 是**全球累计量级**，不是德国本周热度；同类德语账号信号是配置名单近 14 天实际用词频次，按周采集。两者从人工登录的探测 profile 走受 C7 限制的真实页面路径，分别保留来源、原始值、时间和失败原因。每个来源都要有 fresh/stale/failed/missing/空名单跳过的可解释结果；过期旧值不能作为当前新数据。标签采样、候选生成、排序与手工选择的证据分开记录。

**单篇的推荐流程**：

```
英文原帖 tag
   ├─ 品牌 / 型号（#Neakasa #M1Pro）→ 原样照搬，不进推荐
   │                                    （[image.keep_verbatim] 已有表）
   └─ 语义标签（#CatLover #PetCare）
         ↓  LLM 给德语候选词（每个英文 tag 给 3–5 个）
         ↓  在热度库里查这些候选的信号；库里没有的当场补查
         ↓  按热度排序
      推荐 Top-N 给业务勾选（默认预选与原帖等量，上限 30）
```

**四条必须钉死的规则**：

1. ⛔ **热度采集失败不得阻塞发帖。** 采不到就退回"LLM 德语候选 + 业务手选"，
   只是少了排序依据。它是增强，**不能变成发布链路的硬依赖**。
2. ⛔ **标签数默认与原帖等量。** 踩过"最多 3 个标签"静默删掉发布内容的坑，
   不能重犯。实测原帖标签中位 6 个、最多 11 个，IG 的 30 上限从未触发。
3. **推荐时必须显示热度的采样时间。** "上周的热搜"和"今天的热搜"是两回事，
   不标出来就是在骗人。
   而且混入搜索行为反而让它的行为画像更像真人——纯时间线轮询是很机械的模式。

#### F3-6　付费边界：抓全部，但不为所有内容花钱

**改哪里**：`pipeline/engine.py` 的分流判定、审校台列表的「翻译这篇」按钮与端点

业务规则是“抓全部，发不发由她定”。`[publish.trusted_owners]` 控制可自动进入付费的作者，第三方默认人工内容级许可；本地化后的正式内容审校仍是另一阶段。被信任必须是当前配置中明确列出的作者，不按 `neakasa.*` 前缀自动扩大范围。

所以这道闸保留，但它的位置变了：

```
原作者在当前受信名单       →  预算允许时翻译 + 出图 →  进队列（德语成品）
原作者是第三方创作者       →  只抓不花钱           →  进队列（英文原帖 + 「翻译这篇」按钮）
```

理由不是省钱（2026-09-11 旧归档样本中 `.global` 的 31/31 合作方为 `.tech`，不是今天的全量统计），
是**她做这个判断需要的信息在翻译之前就齐了**——"这是别人拍的猫，我们能不能二次发布"
看英文原帖就够了，不需要先付 US$0.211 × N 把它变成德语。而且这本身是个信号：
**这一篇系统没敢自己处理**。

审校台上第三方作者的帖子必须显眼标出（[界面信息规范](../web/ui/DESIGN.md#操作与信息) 的
"常态不显示，异常才显示"原则——近期 IG 帖 35/36 是合作帖，那是常态，只标第三方作者）。

#### F3-7　两个计数器

**改哪里**：标签区与主文案区的组件

| 计数器 | 上限 | 实测触发情况 |
|---|---|---|
| 正文字符数 | IG **2,200 字符**（不是字节） | 最长一篇 1,647，德语 +20% 后 1,976，**0/21 触发** |
| 标签数 | IG 30 个 | 中位 6，最多 11，**0/21 触发** |

**只做计数器，不做超限硬闸、不做自动压缩。** 这条约束在真实数据上不成立，
为它建一整套处理流程（截断？让模型压缩重写？拒绝提交？）等于凭空多一条要维护的路径。

但计数器必须有：最长那篇余量只有 10%，德语翻译波动一下就可能真的顶上去，
到那天她需要当场看见。接近上限（≥ 90%）时变黄。

⚠️ **注意是字符不是字节。** 这批正文里 emoji 让字节数比字符数多 4%，按字节算会把余量
白白吃掉；如果哪天文案变得 emoji 密集，差距会更大。

编辑时 `/check` 按正文、标签、链接或 CTA 的完整当前草稿计算最终发布字符数；Facebook 先替换 `{{linkN}}`，再计入未使用链接和标签。后端响应未到时的本地近似数必须明确显示“约”，收到当前草稿的结果后显示准确数；旧响应不能覆盖后来编辑的计数或问题。数字/金额提示与结构性问题仍分开，失效占位符不能通过。

#### F3-9　审校台按平台拆成两个入口

**改哪里**：`web/ui/src/app/nav-model.ts`、`router.tsx`、`pages/review/ReviewPage.tsx`、
`features/post-list/ListFilters.tsx`、`web/api/reader.py` 的列表 summary、`core/feishu.py` 的卡片标题

2026-09-15 业务决定：**待审列表拆成 Facebook 与 Instagram 两个独立入口**，
不再是一个混合列表加平台下拉。理由就是 §3.3 那条结构性发现——FB 能内联链接、IG 不能，
落地页和标签规则也不同，混在一起每点一篇都要先想"这篇走哪套规则"。

| | |
|---|---|
| 路由 | `/review/facebook`、`/review/instagram`；`/review` 按 `?platform=` 重定向 |
| 导航 | 两条并列项，不是一项加筛选 |
| 角标与总数 | 服务端 `summary.by_platform_status` 按平台分别给，不由当前页重算；硬闸数读取同平台的 `by_platform_hard_alerts` |
| 保存后的列表 | 详情带回当前硬闸，重新复核人工稿或完成逐篇授权后，行提示和所属平台硬闸数同步更新 |
| 列表列 | 不再显示平台列——这个入口里每行都一样，显示出来是噪声 |
| 飞书 | `ready` 与 `backlog` 卡片标题带平台；积压按平台分别计算最早等待时长，并直达对应待审列表；晨间合并的待审卡保留所含平台名称 |

⚠️ **详情路由不变**（`/review/<account>/<postId>`），旧飞书卡片和书签继续可用。
但路径上看不出平台，所以列表链接带 `?platform=`；**没带的由详情页自己补回 URL**
（它知道 `detail.platform`）。导航**不从账号目录前缀 `fa_`/`in_` 猜平台**——那是归档层的
约定，让导航去解析它，等于把同一条规则抄到第三处、还换了种语言。

**排期、90 分钟同渠道间隔和月历不跟着拆**（本轮范围止于列表，见 §5）。

#### F3-8　英文语义风险预扫描

在翻译前对英文源文做真实风险扫描，覆盖 `pun`（俚语/双关）、`ambiguous`（歧义）、`us_only`（美国限定语境）。每份结果绑定账号、post ID、源文哈希、提示词哈希/版本、模型和生成时间，保留风险位置与中文解释。改源文或提示词后旧结果过期；人工优先内容展示不被旧候选覆盖。

`not_scanned`、`failed`、`succeeded` 且风险列表为空是三个不同事实；失败或没扫过不能写“安全/无风险”。红色本地确定性检查与黄色模型提醒分开，风险不是自动拒绝发布的事实判定。扫描共用来源许可、日/月预算与付费账本；缺本地凭据时先明确失败，不能制造“已向远端发出”的假账。页面只读取与当前内容绑定的实际扫描状态和来源。

### 3.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|
| 链接不进翻译输入 | 给一段含链接的正文，翻译请求体里不含该 URL |
| 未映射链接会停 | 新链接首次出现时进人工队列，不直译不放行 |
| 标签数不被静默削减 | 12 个标签的原帖，产出仍是 12 个 |
| 热度采集失败可降级 | 断网时仍能出推荐（LLM 候选），不报错不阻塞 |
| 名单为空可降级 | 同类账号名单为空时周更任务跳过且不报错，推荐照常产出 |
| 三类采样分别成立 | Trends 同组 DE 同时间比较、IG 全球累计、同类德语账号周更各留真实来源与时间；失败/过期分别降级 |
| 风险状态不混淆 | 未扫、失败、成功零风险、来源/提示词变化分别显示；真正扫描发生在翻译前且费用入统一账本 |
| 模型任务可恢复 | 未请求/执行器死亡/结果不确定/成功已落盘分别恢复，旧版本返回冲突；无自动付费重放 |
| 设置白名单与注释保留 | 只接受默认时刻/挂起天数，过期 CAS 或受控字段被拒，原注释与无关键不变 |
| 人工图不被覆盖 | `media_de/` 有人工文件时触发重生成，人工文件仍在且仍优先 |
| 图片重生成受双重约束 | 第 4 次重生成被拒；超月预算时按钮被拒并给出原因 |
| 第三方作者不自动付费 | 原作者不在 `trusted_owners` 时，零付费调用，队列里是英文原帖 |
| 计数器按字符算 | 含 emoji 的正文，计数结果等于 `len(str)` 不等于 `len(bytes)` |

**`preflight`**：德语标签热度库最后采样距今多久、本月已发生的重生成次数与花费、
`link_map` 未命中导致进人工队列的篇数。

## 4. 阶段四 · 飞书推送

### 4.1 业务诉求

- 在企业飞书建一个 bot，处理完新帖后即时推送待审信息给对应运营人员；
- 没有新帖则不推；
- 为防止待审积压被遗忘，还要定时推送当前待审任务情况；
- 推送内容包括原帖基本信息、待审帖基本信息、可直接点击的审核页面跳转链接。

### 4.2 这一步谁在做什么

**飞书卡片是这个系统的主入口，不是通知。** 她的审校时间是随机的，完全跟着推送走——
没有推送她就不会想起来打开审校台。

这句话有两个后果，整节设计都从它们来：

- **卡片必须够她判断"现在开还是等会儿开"**。信息不足她就得先点进去看，那这条推送就白推了；
- **推送一旦被她静音，整条通道就死了**，而且是静默地死——她不会告诉你她静音了。
  所以推送频率与措辞是功能的一部分，不是文案润色。

### 4.3 历史缺口与当前外部依赖

2026-09-11 的问题是通知只有本地 toast/弹窗/log（S2-3），运营收不到。当前内容卡片、按帖去重/晨间摘要、固定尝试与人工核对恢复的离线行为都已具备，多收件人部分失效漏发也已复审修复。

**2026-09-15 起消息走群自建机器人（F4-1），不再等应用权限。** 用户已在同一业务群创建四个机器人；将四个地址和各自签名密钥填入本机 `.env`（[MANUAL_STEPS 第 2 节](MANUAL_STEPS.md#2-配置本机凭据)），再人工运行 `notifications --self-test`。云盘镜像仍然要应用凭据，外部心跳仍未启用。

**运营可达性单独验收**：受管卡片使用服务机 `public_base_url`；消息通道可达不代表办公电脑能打开链接，按第 7.4 节和人工接入步骤核验。

每类消息默认只有一个阶段角色。F4-3 的多收件人部分失效处理仍保留离线契约，不能在改路由时删掉原有投递与去重记录。

服务机为唯一真实业务入口；业务电脑通过固定办公地址使用同一实例，开发机地址不作为生产卡片入口。

### 4.4 要实现什么

#### F4-1　Bot 形态：群自建 webhook 机器人

**改哪里**：`core/feishu.py::WebhookBot`、`config.toml [feishu]`、本机 `.env` 的四个地址及各自签名密钥

⚠️ **2026-09-15 推翻了原来的"自建应用"决定，走的是当时写下的退路。**
原判断没错——私聊、按人聚合、卡片回调确实只有自建应用做得到。但那条路卡在
"企业飞书管理员开 AppSecret"这个**你控制不了的外部依赖**上，卡到整个阶段四一条消息也发不出去，
而飞书卡片按 §4.2 是这个系统的主入口。入口发不出消息，前面三个阶段跑得再对也没人看得见。

群自建机器人只要一个 URL，人自己在群里就能建。换来今天能跑，代价是下面四项：

| 丢掉的 | 后果 |
|---|---|
| 私聊 | 消息发到群，组内可见。待审卡带德语文案和风险提示，等于组内都看得到 |
| 卡片缩略图 | 机器人没有图片上传接口，`img_key` 必须先由应用上传。F4-4 把首图写成"现在开还是等会儿开"的唯一依据，这条**已降级** |
| 远端 uuid 去重 | `im/v1/messages` 的 `uuid` 参数机器人不支持；未知结果必须先人工核对，不能靠重试确认 |
| 远端 message ID | 响应里**没有** `message_id`（已核官方文档）。人工核对"已送达"填的是自己写的说明，不是平台 ID |

前两项是真实功能降级，不是等价替换。缩略图的代码位仍然留着（`notification_card` 认
`image_key`），将来拿到应用凭据可以补回来；`prepare_preview` 也仍然在发送前重读当前有效稿，
只是把首图状态写成文字（"德语首图（未随卡片投递，请在审校台查看）"）。

**`FeishuClient` 不能删。** `core/mirror.py::DriveClient` 是它的子类，云盘镜像（F2-4）
仍然依赖自建应用的 tenant token。所以"放弃自建应用"只针对**消息通道**。

**同一业务群的四个机器人，都必填。** 接收方在代码里是阶段角色标签，URL 由 `WebhookBot`
按标签从环境变量解析：

| 角色 | 环境变量 | 收什么 |
|---|---|---|
| `detect` | `FEISHU_WEBHOOK_DETECT`（+`_SECRET`） | 新帖检测推送机器人：`monitor_found` |
| `capture` | `FEISHU_WEBHOOK_CAPTURE`（+`_SECRET`） | 新帖爬取推送机器人：`monitor_saved` |
| `publish` | `FEISHU_WEBHOOK_PUBLISH`（+`_SECRET`） | 新帖发布推送机器人：`ready`、`scheduled` |
| `alert` | `FEISHU_WEBHOOK_ALERT`（+`_SECRET`） | 状态告警推送机器人：`backlog`、`schedule_failed`、`morning`、`system` |

⛔ **发件箱只保存角色，不保存地址。** webhook 地址本身带 token。四个机器人在同群是预期行为；重复填写同一机器人地址会在发送前拒绝，运行页使用 `duplicate_bot_targets` 展示。配置状态只说明地址存在及格式，不证明群内实际可见。

⚠️ **签名校验推荐开。** 不开就必须在群里设关键词，那时卡片标题里的 "Neakasa" 要当关键词用——
而这个约束不在代码里，只在群设置里，改标题会静默失效。

#### F4-2　八类消息，四个阶段机器人

**改哪里**：`core/feishu.py` 的阶段映射、冻结收件角色与消息模板

既然要建这条通道，它应该同时解决 2026-09-11 旧优化清单里
S2-3 / S2-4 / S2-5 / S2-6 那四条——它们本来就在等一个消息推送通道。

| 消息类型 | 收件人 | 时机 | 对应缺口 |
|---|---|---|---|
| **新帖检测** | 检测机器人 | 每轮按批次/平台/扫描汇总一张，零新增不发；全天即时 | §1.5 |
| **抓取完成** | 爬取机器人 | 每个符合条件的帖子一张，说明完整/部分完成/失败/待人工；全天即时 | §1.5 |
| **待审提醒** | 发布机器人 | 在岗窗内即时；离岗窗积压到次日 08:00 合并 | 新增 |
| **待审积压提醒** | 状态告警机器人 | 上海 14:00 与 18:00，只在有积压时推 | 新增 |
| **排期成功回执** | 发布机器人 | 提交回读确认后，带 Planner 卡片关键字段 | S2-6 |
| **排期失败回执** | 状态告警机器人 | 提交失败或回读不确定时，遵守在岗窗 | 本轮新增 |
| **晨间摘要** | 状态告警机器人 | 在岗窗内汇总，无事不推 | F4-3 |
| **系统告警** | 状态告警机器人 | 会话过期、抓取失败、预算超限、`doc_id` 轮换；豁免静默 | S2-3 / S2-5 |

**第四类是本轮补的缺口，也是最容易被漏掉的一类。** 她点了「通过」，系统半小时后在
浏览器里提交失败——2026-09-11 的旧链路没有业务侧回执。她会以为已经排上了，直到那天德国站没帖子。
排期失败保持独立的 `schedule_failed` 业务类型，虽然与 `system` 同由状态告警机器人发送，仍有自己的文案、下一步与静默规则。

失败回执的措辞必须**给出下一步**，不要只报错误码：

```
❌ 排期失败：日期选择器不允许跨月
   你选的是 10/02，而 Business Suite 当前只能排到 9/30。
   请改选 9 月内的日期重试。           [重新选时刻 →]
```

**原“两组隔离”决定已由用户改为同群四机器人（§0.2）。** 当初分组是为避免技术告警淹没待审，导致两边静音。现在通过专属状态告警机器人、带阶段名称的卡片、同事件去重、无事不推及静默规则控制噪声；同群成员会看到系统异常，这是本次明确接受的可见范围。告警要说明下一步，不能只堆错误码。

#### F4-3　静默时段与合并推送

**改哪里**：`core/feishu.py` 的投递队列、`config.toml [delta].on_duty_window`（静默时段共用在岗窗，没有独立的 `[feishu].quiet_hours`，理由见 §0.5）

**这是时区错位带来的硬约束，不是体验优化。** 美国站发帖峰值落在上海 20:00–23:00，
流水线跑完约 01:00 —— 而她上海 08:00–19:00 在岗。83% 的帖子处理完的时候她在睡觉。

**规则**：

- 在岗窗内（配置项，默认上海 08:00–19:00）→ 即时单条推送；
- 离岗窗内 → 积压，不推；
- 次日在岗窗开始 → **合并成一条**（"昨夜新增 3 篇待审"）；
- 阶段一 detect 批次摘要、capture 逐帖卡和 system 告警即时入发件箱；后续待审消息遵守在岗窗。收件机器人与静默规则独立判断。

队列按**帖子/业务事件**汇总；一篇既有发现又有处理事件只计一次。发送前重新读取当前状态、人工优先文案、检查结果和首图；已排期、不发、接管或仍挂起的条目退出待审推送。晨间摘要包括夜间新增与兜底补抓、按视频/混合/无媒体/无正文分类跳过、处理延迟与失败、当前待审和最早等待时间。无新增、积压、失败或可行动变化时不推空日报。

**发送尝试前冻结消息。** 未尝试条目允许根据当前内容组卡；一旦可能已送到飞书，投递 ID、收件角色和正文都固定。签名信封每次尝试重算，避免超过 1 小时有效期。发送意图先落为 `uncertain`；网络超时、5xx、无有效状态码或进程中断后均停在待核对。只有明确拒绝（如限流响应）才进入 `retry`，15 分钟后重试。同一机器人串行发送至少间隔 0.61 秒，采用低于官方每秒 5 次、每分钟 100 次的速率；依据见[自定义机器人指南](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)。

人工核对通过 delivery ID、版本及“已送达/未送达”结果收敛。机器人不返回 message ID，所以“已送达”填核对说明（接口字段名仍是 `message_id`）。当前角色的有效原卡补送沿用 ID 和内容；合并卡部分失效时，旧尝试保留，只对仍有效且未收到的事件生成新提醒。人工误判仍可能导致重复，不能把本地回执当远端去重。

**发件箱模式版本 2 冻结每个事件的 `recipients`。** 发送与到期归档共用该字段及同一阶段映射，避免改路由后永远无法归档。旧版本已送达记录保留原角色，不补发到新机器人；从未尝试的旧投递取消后按新阶段发送；已尝试但未知的旧结果先人工核对。明确未送达后才结转当前角色，原卡/旧 ID/裁决记录保留，新投递按事件和当前角色去重；部分过期合并卡只转仍有效内容。旧 `FEISHU_WEBHOOK_OPS/TECH` 不自动猜测为新机器人地址。

⚠️ **静默时段按她的作息配置，不是按机器所在地的作息。** 这两件事今天恰好都在上海，
将来她换时区或换人时，改的应该是一个配置项，不是一堆硬编码。

不做这一条，第一周就会被静音，之后所有推送一起失效。

终态消息的在线保留期默认 `keep_delivered_days=30`。超过期限后，只能把全部关联事件/投递均已终结的完整组件按内容 SHA 归档，再收缩主 outbox；原卡片、UUID、收件人和回执仍可追溯，主状态保留事件去重索引，重启后不重发。`uncertain`、`retry`、`pending`、离岗未发或仍缺收件回执的内容不归档，不能按事件创建时间直接删掉。归档是保留旧证据的方式，不是抹掉投递历史。

阶段一 detect 卡按平台和扫描汇总，零新增不发；capture 对每个合格帖子单独发卡。卡片使用英文原文前 300 字符、实际媒体校验结果和真实 owner/coauthors，不带缩略图，也不声称本地化已经开始。

⛔ **回填帖不推。** 判据是 `post.json` 的 `source_route`：只有 `delta`（含复用同一路径的
兜底补抓）才推，`backfill` 是人主动滚出来的历史，逐篇推等于上线第一天刷屏。

⚠️ **静默窗有两道闸**——组卡时一道、实际发送时一道。只豁免其中一道，卡片会在离岗窗
悄悄消失且不报错。

#### F4-4　卡片内容

**改哪里**：`core/feishu.py` 的卡片模板

```
┌ Neakasa 德国站 · 新的待审 ───────────────┐
│ [缩略图]  Instagram · 4 张图              │
│           原帖 8/24 22:07                 │
│                                           │

```

那两行告警是"现在开还是等会儿开"的唯一依据，必须在卡片上。

⚠️ **上面那张图是自建应用时代的形态；`2026-09-15` 起卡片里没有缩略图**（F4-1）。
当前有效首图是德语图还是原图仍然写在卡片上（"德语首图（未随卡片投递，请在审校台查看）"），
因为那句话本身就是"现在开还是等会儿开"的部分依据；但图片要到审校台才看得到。

摘要来自发送时**当前有效**的人工/机器德语文案，并显示来源渠道、图片数、原帖时间、确定性检查、
风险扫描状态/提示和直达该帖的审校链接。不能把原图、旧机器文案或未扫描伪装成当前成品。
重读当前稿失败时卡片标 `preview_error`，正文明说"内容可能不是最新"，而不是静默发旧快照。

积压提醒的措辞用**「最早一篇已等待 X」**，不要用「你还有 N 篇没做」。前者是事实，
后者是催促——她的审校时间本来就是随机的，催促推几次就会被静音，
然后整条通道一起失效。

#### F4-5　心跳仍然走外部服务，不由飞书承担

**改哪里**：常驻调度进程增加心跳推送、`config.toml [heartbeat]`

⛔ **不能让被监控的机器自己推心跳然后只在出事时告警。** 那样的话：

```
机器关机 / 断网 / 计划任务被禁用  →  监控也没跑  →  飞书上什么都没有
机器一切正常，只是今天没新帖      →  监控跑了     →  飞书上什么都没有
```

两种情况在飞书上完全一样。

**做法**（= S2-4）：机器定时往外部心跳服务（healthchecks.io 之类）推心跳，
**缺席由外部服务来叫**。飞书日报作为补充。外部服务是唯一一个
"被监控方挂掉时观察者还活着"的选项。

提频让这条更重要：每小时一次的东西停了，比每天一次的停了更难被人注意到。

**会话过期用被动推断，不主动探测**（= S2-5）：每一轮正常探测本来就会碰接口，
失败了就是会话出问题了 → 直接推飞书。发布号同理，从提交结果推断。

⛔ **不要写定时主动探测。** 它会给探测号加上一条稳定的、有规律的请求节奏，
正好是 C7「随机化触发时刻、频率可降级」要避免的东西。被动推断是零额外敞口。

### 4.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|
| 无新帖不推送 | 空轮次不产生任何飞书消息 |
| 静默时段不打扰 | 上海 23:00 产生的待审在次日 08:00 合并推出（注入时钟） |
| 合并推送不丢条目 | 夜间 3 篇，次日那一条里 3 篇都在 |
| 八类消息按四机器人路由 | 检测→detect，抓取→capture，待审/排期成功→publish，积压/排期失败/晨报/系统→alert |
| 失败回执会发出 | 提交失败与回读不确定两种路径都产生业务侧消息 |
| 积压提醒只在有积压时推 | 队列为空时 14:00 / 18:00 不产生消息 |
| 静默时段按共同作息走 | 改 on_duty_window 后探测与飞书同时采用新窗口，没有独立 quiet_hours 或硬编码 |
| 按帖聚合与当前内容 | 夜间重复发现/处理同帖只计一次；排队后人工修改、挂起、不发、接管、源变更均重新计算 |
| 晨间摘要与首图说明 | 补抓/分类跳过（四类中文标签）/延迟单列；首图是德语图还是原图写成文字并注明未随卡片投递；无事不推 |
| 不确定投递不盲重放 | 响应丢失或进程中断后重启不发送；人工核对后恢复冻结原卡 |
| 请求信封契约 | `card` 是 JSON **对象**（`content` 那套要 `json.dumps`，机器人相反）；签名每次尝试重算；`code` 与旧版 `StatusCode` 两种成功响应都认，`19021`/HTTP 5xx/非 JSON 一律失败闭合 |
| 凭据不落盘 | 群地址与签名密钥不出现在 `feishu_outbox.json`、`status()` 或任何异常文案里 |
| 同群四机器人配置 | 四地址缺一不可且各不相同；重复机器人地址被拒绝，运行页不把同群报错 |
| 路由迁移及归档 | 八类消息送达后超过保留期均归档；旧成功回执不重发，多旧角色结转同一新角色不重复，部分过期卡只转有效内容 |

**人工验收一次**：`notifications --self-test` 在同一业务群收到四张自检卡，卡片的预期机器人名称与实际发送者一一对应；
卡片链接在她机器上能打开对应帖子详情页；手动停掉调度进程，外部心跳服务在阈值内告警。

## 5. 阶段五 · 审校结果、排期与月历

### 5.1 业务诉求

- 审核通过 → 业务选定发布日期 → 系统在 Business Suite 后台自动创建定时发帖任务
  → 核验成功后推飞书 → 同步更新任务列表状态；
- 系统页面里要有一个 Calendar，展示当月所有已在 Business Suite 排期的任务；
- 审核不通过 → 业务可调整（译文 / #tag / 短链 / 按自输入指令重生成图片）直至满足条件；
- 也允许暂时不发送这篇，并提供便利的按钮下载文案与图片，自行调整或手工去后台发帖。

### 5.2 这一步谁在做什么

她在这一步做的每个动作都是**不可撤销或很难撤销**的：排期一旦提交，撤下来要去
Business Suite 手动删；发出去的帖子撤不回来。

所以这一节的设计原则是：**把不可逆的动作前面那一步做厚**（空档提示、跨月置灰、
提交前实时复核），**把可逆的动作做薄**（挂起、改 tag、重生成随便点）。

还有一条：**系统做不了的时候，要让她能顺畅接手**。
[HANDOFF §1](HANDOFF.md) 写着"硬拦人工是这个项目的反模式"——
下载按钮和 `handed_off` 状态就是为这句话服务的。

### 5.3 排期时刻改成任意时刻，并按北京时间填写

`[publish.schedule_rule].times` 从"固定槽"降级为**默认预填值**。业务可以选任意不冲突的
时刻。

**2026-09-16 业务时区由柏林改为北京**（`[publish].timezone = "Asia/Shanghai"`）：运营在
上海，让她按自己的钟点填写，少一道每次都要做的心算。

⚠️ **代价是德国受众的钟点不再写在脸上。** 北京 16:00 是柏林 10:00，但北京 10:00 是柏林
凌晨 4 点——后者看起来最像个正常时刻，恰恰是粉丝睡着的时候。所以每个时刻旁边常驻一行
德国当地时刻（`planning.audience_local()`），换算结果落在柏林 00:00–06:00 时给黄色提示，
**提示但不阻断**。默认预填值也跟着改成 `["16:00", "23:00"]`（≈柏林 10:00/17:00）。

**业务时区和 UI 时区是两件事，不要合并。** `[publish].ui_timezone`
（`America/Los_Angeles`）是 Business Suite 那台设备的时区，决定日期选择器能选到哪个月；
换成北京之后这道边界更刺眼，见 F5-3。付费账本的月份口径有自己的常量，不跟着改——
那是账目边界，不是发布时刻。

### 5.4 要实现什么

#### F5-1　撞槽检测改成时间窗重叠判定

**改哪里**：`publish/business_suite.py:1495` 的 `read_scheduled_baseline` 筛选条件、
`config.toml [publish].min_channel_gap_min`

2026-09-11 的历史现状（S2-2）：按「同时刻 + 同正文 + 同渠道 + 同图数」筛，做的是**同帖去重**
（防同一篇排两遍），不是槽位占用检测——别人的帖子在同一时刻，正文不匹配就被放过了。

**改成**：同一渠道内，目标时刻**前后 90 分钟**内已有任何卡片 → 判定为冲突。

不能只判精确同刻——Planner 上差 5 分钟的两条帖，在粉丝 feed 里就是同时发两条，
是运营事故。90 分钟这个数是按"德国站一天 1 条左右"定的：足够挡住"看起来像同时发"，
又不会把同一天的两条堵死。

**同帖去重仍然保留**，它和撞槽是两个检查，不要合并（[附录 A 术语表](#附录-a-术语表)把它们分开定义
就是为这件事）。

**必须先证明月历完整和渠道可识别。** 2026-09-11 曾按“已有枚举器，改筛选即可”估计；2026-09-12 的实施要求明确补录单渠道和整月读取证据。只读到可见周、未加载完的格子或只有月份标题时，不能把未见到卡片解释为空档。

#### F5-2　顺延规则按"谁选的时刻"分两种

**改哪里**：`publish/workflow.py` 的撞槽分支

S2-2 原本确认的规则是"撞槽 → 自动顺延"。但那是**系统自己排时刻**时的规则。
业务已经手动选了时刻，系统再自动顺延，等于**改了她的决定**。

| 场景 | 撞槽时怎么办 |
|---|---|
| **人工选时刻**（当前的 assisted 档） | **当场拒绝并给出最近的 3 个空档**，让她自己改。不自动顺延 |
| **系统自排**（未来的 supervised / autonomous 档） | 走原规则：自动顺延，超过最大次数则停止并推送通知 |

#### F5-3　日期选择器必须表达 UI 上限，且要在正确的时区里判

**改哪里**：审校台的日期选择器组件、`publish/compose.py` 的离线闸

[HANDOFF](HANDOFF.md) 保留的 **2026-09-01 历史实测**为：当时日期选择器不能翻到下一月。这是当时观察，不是永久业务上限；2026-09-12 要按当前页面的实际可见范围、可操作控件和月份完整性动态计算，不能一直写死“同月”。

两条必须做对：

1. **不可选的日期直接置灰**，不要让她选了才报错；
2. **页面日期范围先按已观测的 UI 时区解释**，再与业务时区互相转换；历史探查为 `America/Los_Angeles`，每次联调重新确认，不按机器位置心算。

下面保留 2026-09-01 同月上限下的时区算例，用来验证换算，不把“下月禁止”写成永久规则：

```
界面给业务看的是北京时间，可选范围要按美西自然月算。
北京比美西快 15–16 小时，所以美西 9 月的尾巴伸进北京 10 月一整个白天：

  北京 10-01 12:00  =  美西 09-30 21:00  →  美西还在 9 月，允许
  北京 10-01 16:00  =  美西 10-01 01:00  →  美西已进 10 月，不允许
```

⚠️ **这一段会被当成 bug 报上来**：界面写着北京时间，却在 10 月 1 日下午三点多戛然而止。
月历页保留「跨月时差」标记并写清理由。

北京没有夏令时，业务时刻这一侧全年固定 `+08:00`；**会切的是美西那一侧**（2026-03-08 /
11-01），窗口时差因此在 15 和 16 小时之间来回。`business_time()` 里"不存在/出现两次"的
两个分支照样保留——上海没有夏令时不等于这个函数以后不会换到有夏令时的时区。
必须用 `ZoneInfo` 显式换算，两个方向都要有断言。

#### F5-4　状态模型：八态

**改哪里**：新建 `archive/<账号>/review_items.jsonl`、`web/api` 的状态端点、
[接口状态契约](../web/DESIGN.md#编辑与状态) 同步更新

```
pending_review ──编辑──> edited ──确认无误──> content_locked ──选时刻并提交──> approved ──回读确认──> scheduled
      │  ▲                        ▲    │                                    │              │
   挂起│  │到期唤醒 + 推飞书       └────┘ 解除冻结                            │           人工已在后台删除
      ▼  │                                                                  └──明确失败──> pending_review
   snoozed(wake_at)                                                                         ▲
      │                                                                                     │
      ├──不发──────> skipped     （终态，要填理由）                                          └── unscheduled
      └──自己处理──> handed_off  （终态，可选回填原帖链接）
```

| 状态 | 含义 | 界面表现 |
|---|---|---|
| `pending_review` | 待我审 | 正常显示 |
| `edited` | 我改过（存在人工版译文） | 标「已修改」小标记 |
| `content_locked` | 内容已冻结，等着选发布时间 | 留在待审页签；编辑入口全关，显示「解除冻结」 |
| `snoozed` | 挂起，到期回来 | 移出主列表，单独一个「挂起」页签，显示 `wake_at` |
| `approved` | 已通过，等系统提交 | 整行变灰 |
| `scheduled` | 已排期 | 同上 + 排期时刻加粗 |
| `skipped` | **不发**（终态） | 移出列表，**必须填理由** |
| `handed_off` | **已交人工处理**（终态） | 移出列表，可选回填原帖链接 |

**为什么冻结要单独一态**：原来「确认内容」和「提交到 Business Suite」挤在一次点击里，
于是在她说"这份可以"和"它真的到了后台"之间，系统没有任何耐久的东西，草稿也一直可改到
点下去的那一刻。拆开之后，点「编辑确认无误」当场把正文与图片字节按 SHA 冻进快照，
四个编辑入口一起关掉；时刻留到之后再绑（`snapshots.bind_schedule`）。

**冻结不要求发布录证。** 缺 probe 意味着这篇**不能排期**，但不该拦着她确认文案和图片
对不对——所以 `approval-options` 把 `lockable` 和 `available` 分成两个字段。

**冻结留在「待我审」页签**，不进「已处理」：它还等着人选时刻，挪走就没人再看它了——
和下面「挂起必须会自己回来」是同一条理由。

解除冻结是单独一次带确认的点击，把快照标成 `discarded` 但**保留字节**：它是当时确认过
什么的证据。

**`unscheduled` 是唯一能解除防重的路径**，判据在 F5-10。

**为什么「挂起」和「不发」必须是两个动作**：语义完全不同。挂起是"我现在不想处理"，
不发是"这篇不该发"。混成一个的结果是**挂起的帖子永远没人管**——而这正是
早期设计拒绝无到期机制的"退回"的理由。
带到期提醒的挂起不是死信箱，因为它会自己回来。**默认到期 3 个工作日**：
比"明天"长，够她真的去问清楚；比"一周"短，不至于忘了这回事。

**为什么 `handed_off` 不能记成 `skipped`**：[附录 A 术语表](#附录-a-术语表)里 `不发` 的定义是
"决定不发"，而这里是"决定不用系统发"。记成同一个状态，"这个月发了几篇"就会算错，
云盘留证里也会永远缺这一篇。回填框**不强制**——她不填我们就只知道"交出去了"，
那也比记成"决定不发"诚实。

**落点**：`review_items.jsonl` 追加式，每次状态流转一条记录，带时刻、动作、理由、
`wake_at`（挂起时）。本轮**不记操作人员**（§0.3）。

每条事件都保留 `actor: null`，不是省略字段。批准期间冻结并锁定内容；点击后的回执不确定需保持阻塞并核对，不能当成明确失败立即回到可再提交状态。恢复只补齐有证据的状态、快照、镜像和通知，幂等运行不能产生第二次远端提交。

到期检查挂在 §1.2 那个常驻调度进程上，不新开进程。

#### F5-5　月历：后台定时读 + 手动刷新

**改哪里**：新建 `publish/planner_cache.py`、`state/planner_cache.json`、
审校台新增月历页

同一份 Planner 数据同时服务三处：**月历展示**、**撞槽检测**（F5-1）、
**提交后回读核对**（S2-6）。读一次，三处用。

月历展示的是**当月在 Business Suite 里的全部排期**，包括运营同事自己用手机发的
——那正是业务想要的"掌握当月所有任务状态"。

**月历有两层。** 远端层是上面这份读回来的数据，带「数据截至 HH:MM」；本地层来自系统自己的
审校账本与发布账本（已冻结待选时刻、已提交待回读、本地记为已排期），画成虚线卡并标明来源。
这样排期一提交成功本地层立刻出现，不必等下一次读后台，而"后台到底有没有"仍然只由远端层
说话。已冻结但还没选时刻的落不到任何一天，单独列出来，否则它就从视野里消失了。

⛔ **本地层只作展示，不进 `planning.evaluate_slot` 的占用判定。** 拿自己的记录证明自己
没冲突，等于不检查。本地账本读不出来时页面显式报错——"本地没有排期"和"读不出来"不能
长得一样。

读取须覆盖**完整可见月份的所有日期格、每个格子的全部带时刻条目、手工 Planner 项和延迟加载内容**。日期格数量只能证明控件存在；标题出现、首屏稳定或读取一周均不能宣称整月就绪。每张卡片需带业务日期、UI 时刻、渠道、任务/远端标识和观察来源；平台给出的 active-time/活跃时间建议不是帖子，不计占用或已排期数。无法判定是否完整时返回 unknown/incomplete 并禁用空档保证，不能把未知当 0。

**公开状态只读观测。** `scheduled` 仍是已回读确认排期；另以观测时间、远端状态/公开链接记录 `published/public`、仍排期或 `unknown`。到了计划时刻也不能自动宣布公开；未看到明确远端状态时如实显示未知，不点击 `Publish now` 验证。

⚠️ **后台读和人工提交争同一把发布锁**（两者都要驱动发布 Chrome）。所以后台读必须
**低优先级、可放弃**：try-acquire 拿不到锁就跳过这一轮，下一轮再读。
**人工提交永远优先。**

页面上必须显示**「数据截至 HH:MM」**——不显示的话业务会以为看到的是实时状态。

#### F5-6　冲突判定做成两段式

**改哪里**：审校台的时刻选择端点、`publish/workflow.py` 的提交前检查

缓存可能是一小时前的，这一小时里别人可能用手机发了一条。历史观察表明手机手工项可能出现在 Planner，当前仍须按完整月份读取和实际状态观察验证；不能笼统宣布没有盲区。

| 阶段 | 数据来源 | 作用 |
|---|---|---|
| **选时刻时** | 缓存（快） | **乐观提示**："这个时刻可能和 X 冲突"，并给空档 |
| **提交前** | **实时读一次 Planner** | **悲观裁决**：最终判定，冲突则拒绝 |

这样既不牺牲交互体验，也不会因为缓存过时而排重。

#### F5-7　驳回后的修改循环

**改哪里**：审校台的四个编辑入口、`translated_human.jsonl`

业务不通过时，可以在同一个页面上改四样东西，改完直接通过——**不做"退回"**
（能直接编辑之后，无到期机制的退回会成为没人处理的死信箱）：

| 可改的 | 落点 |
|---|---|
| 德语译文（直接编辑） | `translated_human.jsonl`（人工版真相源，S1-4） |
| 德语译文（让模型按指令重生成） | `translated.jsonl` 新记录，带 `refine_instruction` |
| #tag | 帖级的标签选择记录 |
| 短链 | 帖级覆盖 + 是否回写 `[publish.link_map]` 由人决定 |
| 德语图（按指令重生成） | `images_de.jsonl` 新记录，带 `refine_instruction`；**不覆盖人工图** |

⛔ **必须区分"人直接改的"和"模型按人的指令改的"**：前者进 `translated_human.jsonl`
（永不被机器覆盖），后者进 `translated.jsonl`（仍是机器产物，可被更新版本取代）。
混成一个会导致“重跑一次把人工修改冲掉”——这是 S0-3 在 2026-09-11 的历史复现，当前人工真相源和回归专门守住这个边界。

#### F5-8　资源下载

**改哪里**：`web/api` 新增打包端点

业务选择自行处理时，一键打包下载该帖的：德语文案 `.txt`、德语图
（缺德语图的用原图并标注）、元信息 `.json`。下载后状态转 `handed_off`。

这个功能的真正价值是**给系统留一个体面的失败出口**。[HANDOFF §1](HANDOFF.md)
写着"硬拦人工是这个项目的反模式"——当系统做不了的时候，
让人能顺畅接手比让人被困住重要得多。

#### F5-9　提交并发保护

**改哪里**：新建 `publish/lock.py`（复用 `core/paid_model.py` 的 `FileLock`）

2026-09-11 原始盘点时只有 `paid_requests.lock` 与 `ImageRunLock`，这是当时补发布锁的原因。当前是否满足共享锁、僵死进程辨识和恢复，以对应实现和测试为准，不沿用旧“没有锁”的状态描述。

本轮只有一个审校人，"两个人同时点批准"不会发生。但**锁仍然必须做**，
因为竞争方换了：**F5-5 的后台定时读 Planner 会和人工提交争同一个发布 Chrome**。
提交前那道基线检查是「读 Planner → 确认无冲突 → 点提交」，
后台读插在中间就是典型 TOCTOU，后果发生在**不可回滚**的发布侧。

⚠️ 给未来的人：**不要因为"只有一个人用"就删掉这把锁。** 它防的不是人，是进程。

**规则**：人工提交优先；后台读 try-acquire 失败就跳过本轮。
将来多人时第二个请求**直接被拒绝**，提示"有人正在提交，稍后再试"。

**不做排队。** `pipeline` 的设计原则明写「每次从各阶段真相源对账，
**不建立发布任务队列**」，排队会破坏这条。

#### F5-10　排期之后要能改期或撤销

**改哪里**：`publish/records.py::unschedule`、`publish/journal.py` 的 `cancelled_remote`

`scheduled` 原来是死路一条：业务临时改主意，只能自己去 Business Suite 删，而本地账本
会永远说这篇已排期，防重也就永远拦着它。

**系统不去自动删远端卡片。** 删错不可逆，而且当前根本没有删除控件的录证。改成人删完回来
登记一次，系统负责核实：持发布锁实时读整月，确认这条的 remote ID 确实不在了，才放行。
月历没读完整、没覆盖到那个时刻、或者这条压根没有 remote ID，都拒绝登记——
**「没看见」不等于「不存在」**。

⛔ `published.jsonl` 的原始 `scheduled` 行保留不删，只追加一条 `cancelled_remote`。
作废按 **attempt** 记而不是按来源：同一篇另有一次没撤销的 scheduled，照样要拦住。

#### F5-11　到点之后核实有没有真的发出去

**改哪里**：`publish/observations.py::overdue`、`pipeline/service.py::check_published`

排期时刻过去之后的下一次月历读取，重点核这几条：观察到公开就记 `published`；超过
`[calendar].publish_grace_minutes` 仍未观察到，给 alert 机器人推一条。

措辞是**「未观察到」而不是「未发布」**——没看到不等于没发出去，而这两句话会让运营做出
完全不同的处置。仍然不按时钟推算公开状态，也不点 `Publish now` 去验证。

#### F5-12　提交过程要看得见

**改哪里**：新建 `publish/operations.py`、`publish/workflow.py` 的 `report` 回调

浏览器那七步常见几十秒到几分钟。原来它跑在一个同步请求里，进度只打在服务端控制台，
业务人员只能盯着转圈，关掉页面就不知道结果了。

现在 `/approve` 立刻返回操作编号，浏览器在请求之外跑，页面轮询
`/api/publish-operations/{id}` 看当前第几步。记录落在 `state/publish_operations/`，
重启不丢；它带着 worker 身份，**进程没了的记录读回来是 `uncertain` 而不是 `failed`**——
点击意图已经耐久记在发布账本里，标成失败会诱导人再点一次。

能不开浏览器就判定的失败（录证没签、内容没冻结）仍然当场同步返回：让人轮询几秒才看到
「发布环境没录证」没有意义。

任务详情按当前冻结快照恢复最近提交操作，刷新或返回页面后继续轮询；撤销排期后不展示旧成功回执。
异步提交独立登记维护操作，HTTP 返回后仍阻止部署切换，直至后台任务结束。

⛔ 并发仍然**直接拒绝而不排队**，见 F5-9。后台任务只是让一次提交可观察，不是队列。

### 5.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|
| 可选日期随实际范围变化 | 历史同月夹具只允许已读范围；新月份刷新成功后更新上下界，读取不完整时不承诺空档 |
| 月边界按已观测 UI 时区换算 | 美西夹具含北京 10-01 12:00 与 16:00 两侧，两个方向都测；新证据时区单独记录 |
| 夏令时窗口正确 | 美西 2026-11-01 与 2027-03-14 前后的换算有断言；业务时区换成有夏令时的时区时仍拒绝那两个不合法时刻 |
| 德国受众钟点可见 | 每个时刻旁边给出柏林当地时刻；落在柏林 00:00–06:00 时提示且**不阻断** |
| 冻结挡住编辑 | `content_locked` 下正文、本地化、图片优化全部 409；解除冻结后恢复；旧快照标 `discarded` 且字节仍在 |
| 冻结先于时刻 | 未绑时刻的快照能建、能绑一次、绑第二个不同时刻被拒；未绑时刻不得提交 |
| 冻结不要求发布录证 | 录证缺失时 `available=false` 而 `lockable=true` |
| 提交可观察 | 提交立刻拿到操作编号；客户端断开仍跑完且状态可查；进程消失的记录读回来是 uncertain 不是 failed |
| 本地图层不参与裁决 | 本地有一条 approved、远端无卡片时，`evaluate_slot` 仍判该时刻可用 |
| 撤销登记要实证 | 月历未读完整/未覆盖该时刻/无 remote ID 时拒绝；卡片仍在时拒绝；`published.jsonl` 原行保留，防重按 attempt 解除 |
| 到点未公开会告警 | 注入时钟越过排期时刻加宽限期后推一条 alert；已观测到公开则不推 |
| 撞槽能拦住别人的帖 | Planner 上有一条正文不匹配的卡片，90 分钟内排期被拒 |
| 撞槽与同帖去重不混 | 同一篇排两遍报"重复"，别人的帖同时刻报"撞槽"，两条路径分开 |
| 人工选时刻不自动顺延 | 撞槽时返回拒绝 + 3 个空档，不产生任何提交 |
| 挂起会自己回来 | `wake_at` 到期后重新进待审列表并推飞书（注入时钟） |
| `handed_off` 不计入跳过 | 统计口径里 `skipped` 与 `handed_off` 分别计数 |
| 并发提交被拒 | 两个请求同时提交，第二个收到拒绝 |
| 后台读会让路 | 锁被占用时后台读跳过本轮且不报错 |
| 月历真正完整 | 整月日期格、带时刻徽标、手工任务、延迟加载、无条目和读取失败分别验证；活跃时间建议不计帖子 |
| 冻结与恢复不重提 | Web/CLI/人工结转统一快照，receipt 绑定指纹；批准中断/回读不确定后只补证据充分的本地投影 |
| 公开状态诚实 | 排期到点没有公开证据仍为 unknown；真实公开状态观察不触发写平台 |

**`preflight`**：Planner 数据截至何时、完整月份范围、排期数、已观察公开数、公开状态未知数、`handed_off` 篇数。没有公开观察证据时不算成“0 篇发出”。

**真实验收分别留证**：长正文完整回读、多图数量/顺序/最终字节、FB 德国落地页链接、IG 稳定 bio 聚合页 CTA、手工 Planner 条目、月历延迟加载、同渠道 90 分钟冲突、任意业务时刻及月界/DST。提前准备两篇具体内容给用户审查，确认后各完成一个 FB-only 和 IG-only 排期，分别取得目标账号/渠道/时刻/remote ID 回读。最终还要由运营从飞书卡片打开审校台、修改/检查、选期确认并收到回执，不能以两个独立脚本提交代替完整操作流程。

### 6.1 那三条 S0 是硬前置，不是待办

2026-09-11 的旧优化清单曾写：

> **S0 全部清掉之前不要装计划任务** —— 自动化会把每一条 S0 从"偶发一次"变成"每天发生"。

本轮目标在岗周期为每小时，受 C7 预算约束。下面“没有闸、每篇人工结转、无条件覆盖”都指 2026-09-11 当时复现的缺口；它们不能因为增加自动化而被略过：

| | 为什么必须先修 |
|---|---|
| **S0-1** | 一个德国市场账号发出 4/5 图带英文的帖子，且**没有任何一处拿 `image_sources` 做闸**。提频之后这会变成常态 |
| **S0-2** | G6c 自动回读至今没在真实长文案上通过过，**今天每一篇都要开发者人工结转**。不修这条，「开发者退出内容判断」根本不成立，而且**云盘的 `03_已发布/` 会一直是空的**（F2-4 规则 2） |
| **S0-3** | `tools/review_report.py:323` 无条件重写 `text_de.txt`。业务一改就被静默吃掉——而阶段三、五的整个修改循环都建立在"人能改译文"之上 |

**S0-3 与 S1-4 是同一件事**（旧优化清单明写"建议一起做"）：
新增账号级 `translated_human.jsonl` 作为人工版真相源，`--review` 只重建派生副本、
永远碰不到人工版。修好它，S0-3 那条"静默吃掉人工修改"自动消失。

### 6.2 S2-1 是阶段三与阶段五的共同地基

短链要分平台、#tag 要分平台、排期要分渠道，**全都压在"两条独立车道"上**。

它原本是返工成本最大的一项，完整路径是：

```
1. 重录 probe 探查（人工约 15 分钟，需要开发布 Chrome）
2. 补渠道勾选的交互证据 —— 当前 dump 里没有这项记录，代码注释明说是刻意不点的
3. 重跑 G8 真机验证
```

红线 5 由 `publish/evidence.py::verify` **机器强制**：每条定位必须能回查到真实 dump
的具体交互编号。**没有证据就写不出选择器**，这一步绕不过去——不用靠人记，测试会变红。

换机器或丢失绑定的 dump 时，证据闸会阻止真实提交，须重新录证；2026-09-15 迁到服务机之后这一条实际发生了，录证要在服务机上做（§7.2）。2026-09-12 已记录单渠道控件及被动 probe，选择器仍须对应真实证据；控件录证不等于长文、多图或单渠道提交回读通过。

重录时要顺手做的两件事（否则还得再录一次）：

1. 记录**渠道勾选区的交互**（S2-1 需要）；
2. 抄下**德国站 IG 在勾选区的显示名**（F5 需要，见 §8）。

完成后的收益不只是解锁本轮需求：跨平台配对那道人工闸消失（近 90 天有 12 篇卡在
"只是相似，停下来让人选版本"），可发单元从 48 涨到 62。

### 7.1 刻意接受的三处代价

**① 两条独立车道 → 同一条内容各做一遍。** 实测重叠期（2026-07-10 ~ 08-27）
IG 19 篇纯图文里 **6 篇（32%）与 FB 某篇是同一条内容**（4 篇正文相似度 1.00）。
拆车道之后这 6 篇会被翻译两次、图片德语化两次、她审两次，约占她工作量的 17%，
而且**两个平台会产出两个不同的德语版本**——同时关注德国站 FB 和 IG 的用户会看到
同一个活动有两套说法。

曾提过一个方案（保留配对逻辑降级为"孪生提示"，一键沿用另一平台的译文与德语图），
**业务决定不做，两个平台各自独立处理。** 记在这里是为了以后德语版本不一致时，
不用重新排查原因。

**② 多人期间暂不记操作人员 → 这段时间的留痕事后补不回来。**
2026-09-16 用户明确选择 2–5 人同权、受控办公网 HTTP，暂不登录、不记录个人身份。
能访问入口的电脑具有相同业务能力；网络限制不是人员认证，HTTP 不提供传输加密。
启用身份管理之前的记录无法追溯具体人员，不得用 IP 或编辑会话编号补造身份。

`review_items.jsonl` **必须保留 `actor` 字段位（本轮值为 `null`）**，
这样启用身份管理时不用改 schema，也不用给旧记录写兼容分支。

**③ 2026-09-11 的回读缺口会连带阻止云盘回执归档。** F2-4 规定回读确认后才能落 `03_已发布/`；这是当时 S0-2 的影响，保留为历史依赖。当前目录是否有内容以冻结快照和真实回执为准，目录名不代表公开状态。

### 7.3 Windows 服务机自动部署

开发提交 main 后，由 Windows Actions 完成固定依赖安装、离线检查、前端构建及隔离浏览器检查，再提供绑定提交 SHA 的部署包。服务机主动拉取，先准备独立目录和虚拟环境，确认任务及编辑空闲后短暂停顿切换；运行内容不变的提交无需重启。

控制器独立于运行版本。`shared/archive`、`shared/state`、`shared/.env` 持续使用，版本内部只保存程序、前端及环境。两个运营可编辑设置保存在共享状态中，其余业务规则随已验证版本交付。回退只切换程序和环境，不恢复旧账本、人工稿、激活边界或访问配额。

维护期间不受理业务写入或会更新索引的查询；已经受理、排队及执行中的操作完成后才能退出。页面报告未保存状态和在途提交，失联草稿不会自动忽略；运营可延后 30 分钟。飞书卡仅通知并链接审校台，不提供自定义机器人回调审批。

每个标签页独立登记，文案、设置、优化指令、审校对话框和自定义排期都纳入草稿保护。更新中、断线或旧页面遇到版本冲突时保留输入；离开页面须明确确认，不能借“查看运行状态”跳转丢弃草稿。

候选下载及验证失败保留当前服务；切换失败或已启用版本的进程退出后，经同一维护协议恢复可用旧版。故障版本保持阻止自动重装，技术人员显式重试或新版本到达后再处理。控制器普通重启恢复最后已确认版本，切换中断按事务记录恢复。

首版不自动迁移真相源格式、升级控制器、登录 Chrome 或强杀未完成任务；真实服务机部署与演练步骤见 [MANUAL_STEPS §15](MANUAL_STEPS.md#15-服务机部署与日常更新)。

### 7.4 办公局域网入口

受管 Web 可显式监听 `0.0.0.0:8765`，业务从固定办公 IPv4 或明确配置的内网主机名访问。监听地址、端口、标准入口和允许来源网段保存在服务机控制目录，不随代码更新或回退覆盖。默认安装仍为回环模式，候选预检始终用回环临时端口。两个模式共享同一套数据绑定。服务机安装配置 `ops/service-machine.network.json` 采用 2026-09-17 用户确认的 WLAN `10.66.4.35:8765`，只允许 `10.66.4.0/24`；已安装实例按 [MANUAL_STEPS §17.4.1](MANUAL_STEPS.md#1741-已有实例改为当前办公网) 维护改址，新网络的现场可达性单独验收。

页面、图片、下载和 API 先核对连接来源与 Host；远程写入另核对同源 Origin 和 JSON。标准入口以外或未允许网段被拒绝。部署健康保留本机访问，业务可查看投影后的部署状态、登记本标签页的编辑状态和暂缓更新。维护管理继续用本地 CLI。HTTP 下使用随机标签页标识及复制回退，无须调整浏览器安全设置。

2–5 个客户端共享现有版本冲突检查，后保存的过期修改被拒绝且保留草稿；没有实时协同编辑或发布队列。全部标签页的未保存内容和在途请求参与维护，脏会话失联不自动清除；标签页编号不代表人员身份。锁屏和跨夜可达性、登录后恢复需在实际服务机验收，联网不等于已验收业务能力。

| F4-5 心跳 | 「最后一次成功心跳距今多久」 |
| F5-5 Planner 缓存 | 「数据截至何时、整月范围/完整性、手工任务、已观察公开数与未知数」 |
| F5-4 `handed_off` | 「本月 N 篇交人工处理」 |

**判断标准**：状态页只读文件与既有证据，不能触发扫描、翻译、联网投递或平台写入。页面和 `preflight --json` 使用同一五阶段数据契约；缺失、过期、损坏和未知分别可见。验收记录注明日期与证据，数字过期只更新记录，不删需求。

> 「这张表会过期，`scripts\run_pipeline.bat preflight` 不会 —— 以它为准。」
