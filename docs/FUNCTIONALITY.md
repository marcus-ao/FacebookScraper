# 功能规划 · 按流水线阶段

**成文日期：2026-09-11；业务契约校订：2026-09-12。** 来源是业务同事（店铺运营 / 社媒运营）的需求访谈、五轮阶段设计质询，以及 2026-09-12 已接受的五阶段、八批实施计划。

本次保留原有 34 个功能编号、具体规则和决定理由。归档数量、耗时、费用和旧 UI 观察均注明日期；它们不能代替当前状态。验收状态与实施顺序在 [REQUIREMENTS.md](REQUIREMENTS.md)，真实/离线证据边界在 [HANDOFF.md](HANDOFF.md)，API 契约在 [web/DESIGN.md](../web/DESIGN.md)。

这份文件回答一个问题：**这条流水线的五个阶段各自要实现什么功能、为什么是这个形状。**
它写给实现者（你和开发 Agent）——精确优先于好读，但每个阶段开头有一段
「这一步谁在做什么」，因为脱离了人的动作，功能就只是一堆开关。

| 文件 | 管什么 |
|---|---|
| **本文件** | **五个阶段各要实现什么功能、为什么**；词有歧义时查 [附录 A 术语表](#附录-a-术语表) |
| [REQUIREMENTS.md](REQUIREMENTS.md) | 为谁做、做到什么程度算够、每个验收单元现在是什么状态 |
| [HANDOFF.md](HANDOFF.md) | 红线、真实 UI 长什么样、踩过的坑、证据能证明到哪 |
| [MANUAL_STEPS.md](MANUAL_STEPS.md) | 需要人亲自动手的步骤 |
| [web/DESIGN.md](../web/DESIGN.md) | 审校台的界面与接口契约 |

**它定义功能，不用删掉需求来表示完成。** 运行事实由 `scripts\run_pipeline.bat preflight` 和 `preflight --json` 读取；功能验收仍需有日期、输入和证据。五种状态固定为 `代码未完成`、`离线通过`、`待真实联调`、`真实通过`、`明确延期`。存在已知实现、恢复或失败闭合缺口的验收单元记为 `代码未完成`；一部分测试通过不改变整个单元的状态。代码与真实依赖拆成独立验收行。

**这份文件说功能应该长什么样，不说现在做到哪一步。** 每个验收单元当前是什么状态、还差什么，看 [REQUIREMENTS.md 第 10 节](REQUIREMENTS.md#10-五阶段验收状态)；哪些证据能证明到哪、哪些不能，看 [HANDOFF.md](HANDOFF.md)。这两处会随每次集成更新，本文件不跟着改。

### 0.4 一天是什么样的

上海时间，某个星期二。下面是目标使用场景，不是已经完成的真实验收记录。

```
22:14  美国站发了一条新帖：M1 Pro 周年促销，4 张图，英文文案 1,180 字符。
       她已经下班三小时了。

22:00  上一轮探测刚跑过，差 14 分钟没赶上。
01:00  下一轮探测抓到了。翻译几秒钟跑完，4 张图的德语化跑了 10 分钟。
01:11  这篇进了审校队列。系统没有推送——她在睡觉（§4.4 F4-3）。
07:00  兜底对账深扫一遍，确认没有漏掉的（§1.4 F1-3）。

08:00  她到工位。飞书私聊弹出一条卡片：「昨夜新增 1 篇待审」，
       配图是德语版第一张，卡片上有一行红字：新金额 $89.99 未收录。
08:06  点卡片里的链接，审校台加载出这一篇。
       左边英文、右边德语，红标记停在那个金额上。
       按「下一处 →」跳到第二处黄标记：「Labor Day —— 美国限定节日」。
       她把那句改写成德国站说法，顺手删掉两个不适用的标签。
08:14  切到图片区。4 张缩略图，逐张放大核对型号与优惠码，看完一张打一个勾。
08:19  链接区显示这是 Instagram 帖，原文里的短链已经被摘出来，
       换成一句 "Link in Bio"。她确认。
08:21  选发布时刻。默认预填柏林 10:00，系统提示 9/16 10:00 前后 90 分钟内
       已有一条排期，并给出三个空档。她挑了 9/16 14:30。
08:22  点「通过」。
08:24  系统在后台驱动浏览器，在 Business Suite 里创建定时发帖任务，回读确认成功。
       飞书弹出回执：「已排期 9/16 14:30（柏林）· Instagram · 4 张图」。

这一天她在这个系统上花了 10 分钟。
```

**这个系统真正要保证的是那 10 分钟成立**，其余全是为它服务的：

- 01:11 那个时刻必须早于 08:00 —— 这是**处理截止线**，是离岗窗唯一的 KPI；
- 08:00 那张卡片必须够她判断"现在开还是等会儿开"；
- 那两个红黄标记必须可信，否则用几次她两种都不看；
- 08:21 的空档提示必须准，否则她得自己去后台翻日历。

## 1. 阶段一 · 监测「有没有新帖」

### 1.1 业务诉求

- 以接近实时的频率监测指定账号是否发布了新的图文帖；
- 检测到后自动开始抓取并进入后续流程；
- 监测对象：FB `facebook.com/neakasaofficial`、IG `instagram.com/neakasa.global`；
- 帖子类型为静态图文，分「纯图 + 文案」与「带文本图 + 文案」两类。

### 1.2 这一步谁在做什么

**没有人。** 这是整条线上唯一一个完全无人参与的阶段，而这正是它容易出问题的地方——
它坏掉的时候，表现是"今天没有新帖"，和"今天真的没有新帖"长得一模一样。

所以这一阶段的功能有一半不是为了"抓得快"，是为了**让沉默说话**：
跳过了几篇、探测了几次、上次成功是什么时候、出口 IP 变了没有。

### 1.3 「接近实时」的解，不在探测频率上

业务说的"接近实时"，真实担忧是「系统没及时抓到导致审核延迟大」。把链路摊开就会发现，
探测频率只在一种情况下影响得了审核延迟：

```
源帖发布  →  探测发现  →  翻译 + 图片德语化  →  进队列  →  她打开审校台
                                                            ↑
                                        她在岗才看得到，她不在岗就得等到上班
```

2026-09-11 设计采用的历史实测数据（47 篇纯图文，按上海时间）：

```
10:00 ████ 4      ← 她在岗
11:00 █ 1
12:00 ███ 3
20:00 ████████ 8   ← 她已下班
21:00 ██████████ 10
22:00 ████████████████████ 20
23:00 █ 1

她在岗时段（08:00–19:00）落地的：  8 / 47 = 17%
她下班后落地的：                  39 / 47 = 83%
```

**83% 的帖子落在她下班之后**。对这一批，01:00 发现和 04:00 发现对她完全一样——
她要到 08:00 才会看。所以离岗窗要守的不是延迟，是**处理截止线**：
在她 08:00 到工位之前，这批东西必须已经翻译完、图也出完了。

而在岗时段那 17%，快慢确实有区别：1 小时内发现并处理完，她当天就能审掉。

这就是[附录 A 术语表](#附录-a-术语表)把「热窗 / 冷窗」改名成「在岗窗 / 离岗窗」的原因。
旧词读起来像"帖子多的时段"，而帖子最多的那个时段恰恰是该用低频的那个。

### 1.4 要实现什么

#### F1-1　监测目标切到 `neakasa.global`

**改哪里**：`config.toml [targets]`、`core/parse.py::on_timeline_of()` 的调用方、
新建 `archive/in_neakasa.global/`

2026-09-11 的归档分析发现，美国团队在 2026 年 7 月换了号，而旧配置没有同步。历史交接分布如下：

```
月份      .tech(owner)   .global(owner)
2026-06        21              0
2026-07         3             14      ← 交接
2026-08         0             17
```

所以这不是"项目级目标切换"，是配置过期。而且 **31 篇 `.global` 帖全部是与 `.tech` 的
合作帖**，由 `on_timeline_of()` 抓进来，今天就躺在 `archive/in_neakasa.tech/` 里；
`[publish.trusted_owners]` 也早在 2026-09-01 就把 `neakasa.global` 加进白名单了。
换句话说，这个账号的内容我们一直在抓，只是归错了档。

**抓取范围规则（业务确认）**：

> `.global` 参与的图文帖全部抓取，**不看合作方是谁**。发不发由人在审校台决定，
> 不由系统规则决定。

判据仍然是 `parse.on_timeline_of()`，不是 `owner == account` —— IG 合作帖由一方发布、
双方主页同时显示，只比 owner 会把 `.global` 的帖子全部漏掉。

`archive/in_neakasa.tech/`（1020 篇）**冻结**：只读、不进流水线、不再产生费用，但不删。
它是 `[translate.glossary]`（1057 条真实正文的词频统计）、`[image.keep_verbatim]`、

#### F1-2　在岗窗 / 离岗窗分层轮询

**改哪里**：`config.toml [delta]`、新建 `pipeline/scheduler.py`（常驻进程，见 F1-5）

```
在岗窗   上海 08:00–19:00   每 1 小时 ± 抖动     11 次/天
离岗窗   上海 19:00–08:00   每 3 小时 ± 抖动      4 次/天   （19 / 22 / 01 / 04）
兜底对账 上海 07:00          翻 2–3 屏做差集       1 次/天
                                     ≈ 16 次/天/平台 · 两平台合计 32 次/天
```

守不守得住处理截止线，按实测最坏情况算一遍：

```
最晚一篇实测 23:00 发
  → 离岗窗触发点 19 / 22 / 01 / 04，最迟 01:00 发现
  → 处理最坏 25 分钟（10 张图 × 2.5 分钟/张）
  → 01:25 完成，距 08:00 还有 6 小时 35 分余量
```

在岗窗那 11 次不是浪费：它接住落在上海 10:00–12:00 的那 17%（当天就能审掉），
同时给白天一个"坏了有人看得见"的观测面。

**窗口边界必须算出来。** 在岗窗跟着她的作息；发帖窗按**上一个完整自然月**的真实归档时刻分布重算，分别记录 FB/IG 样本数、月份、覆盖率、边界、计算时间和采用/保持原计划的原因。缺少某个平台、月份未完整或样本不足时保留既有计划并显示不足原因，不能把少量旧 `.tech` 样本当成新 `.global` 的完整覆盖。

上面的 25 分钟只是一篇十图内容的 2026-09-11 估算。真实截止预算必须包含**两个平台扫描及同一轮整批帖子的翻译、风险扫描、全部图片处理、等待与安全余量**。预算超出默认兜底窗口时前移兜底；需跨日期前移时也以同一 08:00 截止点计算。无法证明有足够时间则明确显示截止风险，不能承诺 08:00 完成。调整窗口不自动提高 C7 允许的轮询频率或扫描深度。

#### F1-3　兜底对账：回答「有没有漏」

**改哪里**：新建 `routes/reconcile.py`（复用 `routes/delta.py` 的会话与解析路径）

常规探测只拉首屏，回答的是"有没有新"。漏帖有三种成因它都看不见：
探测那一刻正好失败、首屏被置顶帖挤掉、源帖发布后短时间内被编辑导致排序变化。

兜底对账每天一次，翻 2–3 屏，与归档做差集。发现漏帖时：**补抓 + 计入次日日报，不单独告警**。
「漏了一篇」是必须被看见的信号，但不是要把人叫起来的事。

它压在 07:00，是她 08:00 上班前的最后一道防线。这一轮同时兼做当天的最后一次探测，
不额外增加一次露面。

⛔ **兜底对账用探测号，且触发时刻与深度都要随机化。** 它是全天唯一一次深扫，
固定时刻 + 固定深度正好是 C7「随机化触发时刻」要避免的行为特征
（见 [HANDOFF §1](HANDOFF.md) 红线 3）。时刻在 `reconcile_at ± reconcile_jitter_min`
内随机，深度在 `reconcile_scrolls ± 1` 内随机。

抖动范围要保证**整批最坏情况仍早于处理截止线**。2026-09-11 的“07:30 + 单篇 25 分钟”算例没有覆盖双平台整批，不能继续作为安全判据；应采用 F1-2 的完整预算前移兜底，并让 `preflight` 展示最晚触发、批量预算、截止点和余量。错过有效窗口记成错过；恢复服务不追补睡眠期间所有轮次。

同一轮中，只有实际执行过该平台兜底深扫，才能合并它的普通探测。前一平台耗时导致后一平台开扫前已经过期时，跳过深扫但保留正常探测，并把跳过原因计入技术告警与晨间摘要，按日期/平台去重；不能在轮次开始时预先删除普通探测后悄悄漏掉整个扫描。继续保持先持久化下次时刻再调用扫描的顺序，重启不密集补跑。

`scripts/start_chrome_detect.bat` + `tools/start_chrome_detect.py`

这是提频的配套缓解，不是可选项。2026-09-11 之前两条抓取路径共用小号，旧
[README](../README.md) 因此记录“回填与增量会同时断掉”的风险。当前决定是三套 profile 隔离，不再沿用该旧架构。

|---|---|---|---|---|

自动登录是触发 checkpoint 的最高频动作。

#### F1-5　常驻调度进程

**改哪里**：新建 `pipeline/scheduler.py`、`tools/schedule.py` 增加 `Alive` 任务模板

Windows 计划任务表达不了"在岗窗 1 小时 + 离岗窗 3 小时 + 每次随机抖动"这种模式，
而且 踩过"两个计划任务并发进入同一个 delta 主干"的坑——每小时一次的重叠概率
比每天一次高一个量级。

**做法**：一个常驻进程负责算下一次触发时刻、持锁和安排工作；Windows 计划任务只负责
**开机拉起 + 进程死了自动重启**（形状照抄现有的 `FBScraperAlive`）。

调度主循环保持可响应。模型处理由持久化批次和独立执行器承担，长模型调用不能占住主循环；正在处理时新发现的内容保留为后续批次。扫描开始/结束/成功/分类/补抓和处理开始/结束/成功/失败分别留事实，不能用“扫描成功”推导“内容已处理完成”。进程中断后的批次恢复先核账，不自动重放不确定付费请求。

标签周更以及远端镜像/消息 I/O 同样放在独立 worker，不能在一次导出、上传或投递等待中拖住扫描与维护。批次通过 `operation_id` 关联实际模型费用；恢复要求 batch ID 和当前状态版本，先核请求/产物，不自动 claim 后继批次或重放付费。

调度器同时安排另外三件维护工作：

- 挂起帖子的到期唤醒（§5.4 F5-4）；
- 德语标签热度库的周更（§3.4 F3-5）；
- 飞书积压提醒与合并推送（§4.4 F4-3）。

Windows 常驻任务应支持安装、查询、停用、恢复；安装前检查旧每日任务是否会重复运行。控制命令、任务实际 Action、运行账户、工作目录、单实例、开机恢复和停用效果均需分别验证；生成 XML 不是安装成功。发布任务仍由人审核触发，不建立无人审核发布队列。

#### F1-6　提频带来的五处连带修改

**改哪里**：`config.toml [delta]`、`routes/delta.py`、`core/store.py` 的 capture 清理

| 现有机制 | 在 1 小时节奏下的问题 | 怎么改 |
|---|---|---|
| `stale_after_hours = 26` | "距上次成功超过 N 小时才真跑"这道闸完全失效 | 改成按窗口的最小间隔判定 |
| `keep_captures = 7` | 16 次/天下等于排查转储只留 10 小时 | 改成 `keep_captures_days`，按天保留 |
| `failure_budget = 3` | 3 次连续失败在高频下 3 小时内就会触发 | 保持敏感，但要区分"网络断"与"被封"（F1-8） |
| `quiet_days_before_slowdown` | 降频机制仍需要，但要作用在窗口上 | 连续 N 天零新增 → 在岗窗降到离岗窗频率 |
| `delta.lock` | 重叠概率上升一个量级 | 健壮性重新验证，必须能识别僵死锁 |

#### F1-7　跳过数必须显式报出

**改哪里**：`pipeline/engine.py` 的 run 输出、`pipeline/cli.py` 的 preflight
（`preflight` 的 90 天预演**已经在算这个数**，只需搬进日常输出）

视频 / 图文混合 / 无媒体 / 无正文的跳过数，进入每一轮输出与飞书日报，**分类计数**。

⛔ **「沉默有歧义」是这个项目吃过最大亏的病型**——263 篇合作帖静默丢失，
输出里一个字都没有，很久都没人知道。「今天没新帖」和「今天发了 8 条全是视频」

#### F1-8　出口 IP 的类型与稳定性检查

**改哪里**：`pipeline/cli.py` 的 preflight 增加检查项

红线 2 写的是"住宅 IP"，而 **FB/IG 看到的是出口那一跳**——商业 VPN 与云专线的出口
几乎全是机房段。它现在跑得通（1020 篇是实打实抓下来的），说明登录态对 IP 类型的
容忍度比登出态高得多，但请求量上去之后余量不再充裕。

更要命的是：**出口 IP 如果会轮换，账号会看到"从很多个 IP 登录"——那正是 checkpoint
的触发条件**。

**做法**：把「出口 IP 的 ASN 类型 + 最近 N 次是否同一出口」做成 `preflight` 的检查项。
能算出来的就不要写在文档里等人记。

这项仍是当前安全要求：展示采样时间、出口/ASN 类型、最近记录、变化次数、稳定性及证据是否过期；未知不能显示为已满足。`preflight` 只读已有网络证据，不为状态页主动增加 FB/IG 请求。

告警时要能区分"被封"与"网络断"——高频下这两种在日志里长得很像，分不清就没法处置。

#### F1-9　监测与抓取的群播报

**改哪里**：`routes/delta.py` 的落档循环、`core/monitoring.py` 的逐篇事实、`pipeline/notifications.py` 的组卡、`pipeline/service.py::Runtime.scan`

§1.2 说这一阶段的功能有一半是**让沉默说话**，但在 2026-09-14 之前，沉默只对着本机
`state/alerts.log` 说。这一条把它说到群里：一轮扫描发现新帖就推一张卡，原帖落档后再推一张。

**先解决一个数字问题。** `delta_state.json` 的 `last_new_count` 来自 `ScanResult.new`，
而 `res.new` 只在 `arc.append()` 成功之后才 +1 —— 它是**落档成功数，不是发现数**。
所以不动抓取路径的话，"发现"和"抓到"在数字上根本分不开，两张卡只会把同一个数字说两遍。

抓取路径因此逐篇记三件事到 `state/monitoring_facts.jsonl`：

| 事实 | 记在哪一步 | 卡片用它回答 |
|---|---|---|
| `post_discovered` | `should_append()` 放行之后、`download_media()` **之前** | 这一轮看到了几篇，哪几篇，是新帖还是补齐已有帖 |
| `post_captured` | `arc.append()` 返回 True 之后 | 实际落了几张图、落在哪个目录 |
| `post_capture_incomplete` | `arc.append()` 返回 False | **哪几篇发现了却没抓下来** |

只追加 JSONL，不改会话、请求节奏或滚动行为，也不新增任何网络请求；`--dry-run` 一个字不写。

⛔ **第三类是这一条真正的价值。** "发现 3 篇只落档 2 篇"今天在任何地方都看不出来，
而原图 CDN URL 带签名且有时效（§HANDOFF 5），"下一轮再抓"不是稳妥假设。

**两张卡，不是两种形态。** 一轮扫描最多两张：逐篇明细渲染进卡片正文，不按篇发卡——
实测最忙那个小时有 20 篇（§1.3），按篇发会把群刷掉。无新帖则完全不推：
32 次/天 × 两平台 = 64 张"今天没有新帖"会让这条通道在第一周就被静音。

两张卡的先后顺序**由 kind 名字的字典序决定**（`monitor_found` < `monitor_saved`），
因为 `Outbox.dispatch` 先按 `sorted(KINDS)` 建投递、再按建立顺序发送。改名会静默换序。

**两张卡都进业务组，且不受在岗窗静默限制。** 阶段一不开 `--process`，所以待审卡根本不会
产生——这段时间里这两张卡是运营唯一的信号。而 83% 的帖子落在上海 20:00 之后，压到次日
08:00 又让"接近实时"失去意义（晨间摘要本来就覆盖汇总口径）。技术组只接系统告警。

⚠️ **静默豁免和收件人是两件事**，代码里也分开：`ALWAYS_DELIVERED` 只管豁免，收件人仍按
`kind == 'system'` 判。把两件事绑成一个集合，改豁免时会静默改掉收件人。
`[feishu].scan_reports = false` 可以单独关掉这两张卡，不影响待审提醒。

抓取退出码非零时播报照发，并在落档卡上标出退出码：整段播报不能因为失败就消失。

### 1.5 刻意接受的代价

**抓取账号的封号风险从"每天 1 次"变成"每天 16 次"。** 红线 3 写着这类风险
"反馈是延迟的，且只反馈一次"。记在这里不是为了翻案，是为了以后出事时不用重新推导。

公平地记下提频买到的东西：对不规律发帖鲁棒（那 17% 落在在岗窗的帖子当天可审）、
不依赖"他们总在 PT 07:00 发"这个假设、源帖被快速编辑或删除时能抓到原始版本。

**F1-4 的账号拆分是这个决定能够成立的前提。** 不做拆分而直接提频，
等于把唯一不可恢复的失败模式的概率乘以 16。

### 1.6 验收判据

**离线测试**（守"改坏了会变红"）：

| 判据 | 怎么验 |
|---|---|
| `neakasa.global` 归档建立 | 给一份含合作帖的 capture，`.global` 参与的全部入档，合作方不限 |
| 窗口边界是算出来的 | 给定一份 manifest，发帖窗函数输出可复现的边界 |
| 月度样本不足保持计划 | 上个完整月、单平台缺失、低覆盖率三类输入分别显示样本数/覆盖率/保持原因；不提频 |
| 双平台整批截止预算 | 多帖多图跨两平台累计，兜底按预算前移；超一天预算仍对齐正确截止点 |
| 调度不被付费处理堵塞 | 模型执行期间扫描/维护仍可推进；新发现进入后续批次，扫描与处理事实分开 |
| 高频下不重入 | 并发触发时第二个进程被锁拒绝并记录 |
| 兜底对账会随机化 | 连续 30 次取样，触发时刻与深度的分布不是常数 |
| 探测号与回填号真的隔离 | 两个 profile 路径不同、端口不同；hygiene 测试断言不共用 |
| 跳过数分类可见 | 每轮输出含「本轮跳过 N 篇：视频 x / 混合 y / 无正文 z」；四类都要有中文标签 |
| 发现与落档分别可观测 | 逐篇事实区分 `post_discovered` / `post_captured` / `post_capture_incomplete`；不传 journal 或 `--dry-run` 时不写 |
| 一轮最多两张卡 | 发现卡先于落档卡；无新帖不推；退出码非零仍推并标出退出码 |
| 播报不被在岗窗压住 | 上海 23:00 的发现当场推业务组，不等次日 08:00；待审卡仍受静默约束 |

**`preflight`**（守"实际跑得怎么样"）：

| 指标 | 含义 |
|---|---|
| 端到端延迟 P50 / P95 | 源帖 `created_at` → 进审校队列的时刻 |
| **处理截止线达成率** | 有多少批次在 08:00 前处理完。这是离岗窗唯一的 KPI |
| 最近 N 次出口 ASN | 是否同一出口，是否机房段 |
| 上次成功探测距今多久 | 会话过期的被动推断依据（§4.4） |

处理请求到内容就绪的 P50/P95 与源帖发布到首次就绪的 P50/P95 分开：前者从 requested_at 起算，后者还包含发现等待。源延迟需 `source_created_at` 和按源引用首次 `post_content_ready` 事实；旧历史没有这些事实时返回未知，不补造零延迟。晨间就绪率记录样本数，不能以进程活着或扫描成功推算。

## 2. 阶段二 · 抓取与存储

### 2.1 业务诉求

- 抓取帖子文案、图片、平台渠道、账号名、原始发布时间、原帖链接（对应界面中的“元信息”）；
- 原始英文帖与后续处理过的帖子都要留档，一篇帖子一个文件夹；
- 文件夹命名要便于业务区分，且能按月份归档；
- 支持业务自定义 tag 母文件夹（按产品等维度）对帖子子文件夹归类；
- 存储方式：本地 + 飞书云盘 + 数据库三种。

### 2.2 这一步谁在做什么

抓取仍然没有人。但**存储这件事有两个截然不同的读者**，把它们分开是这一阶段的全部难点：

- **她**要在审校台上按 tag、按月份、按状态筛几十上百条——这是**查询**；
- **将来某个人**（可能是法务、可能是接手的人、可能是三年后的她自己）要回答
  "2026 年 9 月我们在德国站发了什么"——这是**留证**。

查询要快、要能多条件组合、要能重建；留证要完整、要不可篡改、要能离开这个系统独立看懂。
一份存储同时干这两件事，结果一定是两件都干不好。

### 2.3 2026-09-11 的缺口记录

**元信息字段已经全有了**，不需要新抓：`post.json` 的 `text` / `media[]` / `platform` /
`account` / `owner` / `created_at` / `permalink` 齐全。

差三样：**月份层级**（现在 1020 个帖子文件夹平铺在一个目录里）、**tag 字段**（不存在）、
**另外两份存储**（飞书云盘和数据库都没有）。

### 2.4 要实现什么

#### F2-1　存储三层：一个真相，两个派生

**改哪里**：新建 `core/index_db.py`（SQLite 索引）、`core/mirror.py`（云盘镜像）、
`tools/layout.py` 增加 `reindex-db` 子命令

这是这一阶段的地基，必须先立。这个项目已经为此立过铁律：
「`post.json` 是真相，`manifest.jsonl` 是派生索引，冲突时以文件夹为准，方向永远单一」。
加两份存储而不先钉死方向，会直接退化成"三个都不可信"。

| 层 | 角色 | 方向 | 能否重建 |
|---|---|---|---|
| **本地文件夹** | **唯一真相源**（不变） | — | — |
| **SQLite** | 派生索引：审校台列表、月历、按 tag / 月份 / 状态筛选 | 本地 → DB，单向 | 全量重建 |
| **飞书云盘** | 归档留证 + 跨部门只读 | 本地 → 飞书，永不反向读 | 重新镜像 |

**数据库选 SQLite**，不选 Postgres / MySQL：单机部署、零运维、单文件、Python 自带，
不增加依赖（目标运行机器现在只有 7 个运行时依赖，这个风格值得保住）。它解决的是
`manifest.jsonl` 全表扫描做不到的事——分页、多条件筛选、月历聚合。

**历史查询是完整契约。** 默认待办可以限制最近 90 天，历史入口须提供服务端分页、总条数、页码/每页数、可用月份、平台/月/tag/状态筛选；可以访问第 91 天及更早的详情，也包括冻结 `.tech` 的只读历史。查询不得触发翻译、图片生成、付费或发布，不裁剪底层归档。详情按稳定 ID 找源文件，不能复用 90 天待办筛选把老帖误报成不存在。

SQLite 一致性检查须实际比较文件事实与数据库的记录集合及展示字段，记录缺失、多余和内容不符项；仅有表或文件存在不算一致。源签名或版本失配时标明索引过期并重建/回退只读查询；写入仍从文件重新校验版本。重建前后人工、付费、审校、发布账本及激活边界的哈希应保持不变。

⛔ **数据库一行也不能是真相：**

- 只有一个 indexer 进程写它，输入只有真相源文件和归档文件夹；
- **任何业务逻辑不得读 DB 做决策**，只有界面读它做展示；
- 冲突时以文件夹为准，跑一条 `reindex` 重建。

这条约束的作用和 `web/` 那条一样：它让 DB 成为模块图上的叶子，不会长成第五个真相源
（[HANDOFF §3](HANDOFF.md) 明写「对账器只读四份产物」）。`tests_hygiene.py` 的 DAG 护栏
会自动守住它——`core/` `routes/` `pipeline/` `publish/` 一律不得 import 索引层。

#### F2-2　本地布局：加一层月份 + 可读的文件夹名

**改哪里**：`core/store.py` 的路径生成、`tools/layout.py migrate`、`post.json` schema

```
archive/in_neakasa.global/
  posts/2026-09/M1-Pro/          ← 月份在外，主 tag 在内；与云盘同形（F2-3、F2-4）
    2026-09-10_1423_m1-pro-anniversary-sale_3973012230169803390/
      post.json          ← 真相源。新增 folder_name / tags 两个字段
      text.txt  text_de.txt
      01.jpg  02.jpg     ← 原图，只读，从不修改
      media_de/          ← 德语图。程序产出，人工可覆盖
```

三条现有不变量全部保住：按名排序仍等于按时间排序（日期在最前）；`*_<post_id>` 仍能
幂等查找，不用打开文件；`local_path` 仍是仓库相对路径。

**摘要 slug 只在创建时算一次，之后永不重算**，结果写进 `post.json` 的 `folder_name`。
原帖被编辑就重算的话文件夹会改名，所有 `local_path` 一起失效。

**slug 限长 30 字符并转 ASCII kebab-case。** Windows 默认 260 字符路径上限在
`media_de/01.jpg` 这一层已经不宽裕，且正文里有大量 emoji。

**回填可以按 `--days N` 收紧到最近 N 天**，让基线边界可复核，而不是依赖滚动手感。
算不出日期的一律保留——内容已经抓到手，媒体 CDN URL 带签名有时效，丢掉重抓不回来。
人工滚动这条不变（红线 2），窗口只收紧归档范围。

迁移成本几乎为零：2026-09-14 清库后两个账号都是零归档，直接按新布局建；
`tools/layout.py migrate` 已支持两层→三层，留给将来可能出现的存量。

#### F2-3　tag：自动预填 + 人工可改

**改哪里**：`post.json` 新增 `tags` 字段、`core/store.py` 的预填逻辑、审校台的 tag 编辑

**tag 存在 `post.json` 的 `tags` 字段里**（数组，一篇可以有多个），同时用主 tag 组织本地目录。

| | |
|---|---|
| **自动预填** | 抓取时用 `[image.keep_verbatim].models` 那张型号表匹配正文。正文里出现 `M1 Pro` 就归到 `M1 Pro` |
| **人工可改** | 审校台上业务可以改、可以补、可以加自定义 tag |
| **匹配不上** | 进「未分类」，**不猜** |

型号表是从 1057 条真实正文的词频统计出来的，命中率会很高，业务基本零负担；
而这张表本来就要维护（`[image.keep_verbatim]` 是图片德语化的硬依赖），不是新增负担。

**本地目录也按主 tag 分层**（2026-09-14 业务决定，改写原「tag 不进本地目录」）：
`posts/<月份>/<主 tag>/<帖子>/`，与 F2-4 的云盘结构同形，业务在本地和云盘看到同一套层级。
落点只由 `tags[0]` 决定，匹配不上型号表的进 `未分类/`；其余 tag 仍只在字段、SQLite
和审校台里生效——目录树表达不了"一篇帖归两个产品"。

代价是明确接受的：改主 tag 要在锁内移动目录、重写每个媒体的 `local_path`、追加
manifest 行。三条对应的实现约束不能省：

- **按 `folder_name` 定位要扫月份下的各 tag 目录，不能照当前 `tags[0]` 拼路径。**
  索引可能落后于一次移动，拼出来的路径会把已归档的帖子报成不存在。
- **tag 解析必须早于落点计算。** 媒体下载先于 `append()` 发生，晚一步会让图片落进
  `未分类/` 而 `post.json` 落进 `<tag>/`。
- **认路径层级的地方要认三层。** `localize/images.py` 的所有权记录原先只认 4/5 段路径；
  认不出第 6 段就会把程序产出的德语图判成人工图，从此永不重做，而且不报任何错。

tag 目录名另有安全化规则（`store.tag_component()`）：`_safe_folder_name()` 只允许 ASCII，
而 `未分类` 和业务自定义 tag 都可能不是。上限 20 字符，超出截断加哈希后缀；
实测最深路径 222 字符，仍在 Windows 260 以内。

#### F2-4　飞书云盘镜像：归档留证 + 跨部门只读

**改哪里**：新建 `core/mirror.py`、`config.toml [mirror]`、常驻调度进程挂一个镜像任务

用途已确认：**以归档留证为主，兼作跨部门只读协作与备份，不会反向修改。**
因此镜像是**单向**的，不需要设计受控回填口——这省掉了整个方案里最容易出事的一块。

tag 母目录在这一层 materialize。业务看到的是这个结构——**月份在外，产品规格在内**：

```
Neakasa 社媒归档/
  2026-09/                                       ← 月份（外层）
    M1-Pro/                                      ← 产品规格 tag（内层）
      2026-09-10_IG_m1-pro-anniversary-sale/     ← 一篇帖子一个文件夹
        01_原帖/     text_en.txt · 01.jpg… · 元信息.json
        02_待发布/   text_de.txt · 01.jpg…                   ← 审校通过时写入
        03_已发布/   text_de.txt · 01.jpg… · 排期回执.json    ← 提交回读确认后写入
    S1-Pro/
      2026-09-14_FB_s1-pro-fellpflege/
    未分类/                                       ← 型号表匹配不上的进这里，不猜
      2026-09-18_IG_herbst-kampagne/
  2026-08/
    M1-Pro/
```

**为什么月份在外侧**

**① 留证语义和月份天然对齐。** 一个月过去之后，那个月份目录就基本封存——不再有新帖写入，
只剩偶发的 tag 重挂。反过来（tag 在外）的话，任何月份的新帖都会往老 tag 目录里追加，
**没有一个目录是能封存的**。

**② tag 是会变的，移动范围要小。** 月份在外，改 tag 只是在同一个月份目录内换一层；
tag 在外，改 tag 要跨月份目录搬。

**③ 业务的实际动作是按月的。** "这个月发了什么"——打开一个目录就看完了。

代价要说清楚：想看"M1 Pro 有史以来的全部帖子"，在云盘上要翻多个月份目录。
这个代价是刻意接受的，因为它有更好的去处——**按 tag 横向检索由审校台承担**
（F2-1 的 SQLite 索引本来就支持多条件筛选）。

> **云盘负责"留证"，审校台负责"检索"。** 让云盘的目录树同时表达两个维度，
> 结果一定是两个都表达不好。

**五条规则**：

1. **写入后内容不再修改。** 同一篇改了重新审校，新增 `02_待发布_v2/`，**不覆盖 v1**——
   "当时到底发的是哪一版"必须永远查得到。
2. **`03_已发布/` 只在提交回读确认成功后写入**，不在点击提交时写。半完成状态不进留证目录。
   目录名沿用历史约定，但“已发布”在这里表示**排期回读已确认**，不表示实际公开；公开状态另存只读观察结果。实现与真实验收见 §6.1 的 S0-2 和实施清单。
3. **落点由主 tag（`tags[0]`）决定。** 云盘的目录树只能表达一个维度，而一篇帖可以有多个 tag。
   其余 tag 只在数据库与审校台里生效，**但 `元信息.json` 里记录全部 tag**——
   留证不丢信息，只是目录不表达。
4. **改 tag 只移动落点，不改内容。** 留证保护的是"内容不被改写"，不是"路径永不变"。
5. **匹配不上型号表的进 `<月份>/未分类/`**，不猜。业务在审校台补了 tag 之后重新挂。

**`state/` 一起镜像**（已定）。它不是"内容"，但 `state/published.jsonl`（111 KB）
**不可重建**——丢了会导致幂等失效，已发过的帖子可能被再发一遍。
这是备份契约的一部分，不能仅因代码有 mirror 就宣布备份敞口已关闭。应周期性保存不可重建账本与相关配置，记录备份时间、文件数、字节数、哈希和恢复验证；大型 probe、截图、冻结媒体按版本单独保存，并在账本中保留引用。原始凭据保存在本机受控备份，不上传到可公开访问的云盘。

Web 批准、CLI 发布和人工结转均须走同一冻结快照和状态投影。镜像队列引用已冻结的版本，旧版缺失只能用那一版的字节补送；重试不重新读取当前内容冒充旧版。验证上传、移动 tag 落点、v1/v2 并存、冻结补送、失败恢复与远端只读权限，分别留远端文件 ID。

⛔ **云盘永不反向读。** hygiene 测试断言镜像模块里没有任何从飞书读回写本地的路径。
破了这条，"方向永远单一"这条铁律就失效了，而它是这个项目数据可信度的全部来源。

#### F2-5　源帖变更的处理

**改哪里**：`core/translated.py` 的哈希校验、`review_items.jsonl` 的 `stale` 标记

提频会看到源帖被编辑。译文绑定 `source_text_sha256`；整篇来源还必须有包含**原图实际字节哈希、数量和顺序**的 source fingerprint，不能只比较 URL、文件名、大小或首图。URL 不变而内容更换、加图/删图、调换两张图都要被识别。旧模型候选、许可和批准依据按各自绑定的来源版本失效；已排期的冻结内容保持不变并提醒人工处理。
四种情况要分开：

| 情况 | 处理 |
|---|---|
| 尚未翻译 | 直接用新版本，无成本 |
| 已翻译、未审校 | 机器译文作废重译；本篇重新进待审队列 |
| **已有人工版译文** | **不作废。** 保留人工版，标 `stale: true`「原文已变更，请复核」，重新进待审队列 |
| **已排期或已发布** | 推飞书告警，**不自动改已排期的内容**。由人决定要不要撤下重来 |

第三条的理由很简单：直接丢弃人的劳动，两次之后她就不改了。

第四条是提频带来的新情况：每天一次的时候"源帖在我们排期之后被编辑"几乎遇不到；
每小时一次之后它会变成常态。

来源文字的 `source_text_sha256` 在归档、翻译、审校、就绪事件、快照和发布比对中采用同一规范，统一去首尾空白后计算；AST 检查防止同名字段重新出现另一算法。风险高亮另存原始扫描文字的 `scan_text_sha256`，保护字偏移；最终提交文案、原始证据和媒体字节指纹不套用去空白规范，仍绑定实际内容。

#### F2-6　接续现有运行数据与可恢复备份

接续原 archive/state 时不能创建一套空发布账本“重新开始”。接续顺序为停写、备份 archive/state/运行配置、核验不可重建账本、在副本检查派生一致性，再用不入库的本机路径配置绑定。所有 Web/CLI/批处理/调度入口必须读取同一配置、环境文件、解释器、数据和锁，保留原激活时间和历史发布引用。

备份应包含 `config.toml`、存在时的 `config.local.toml`、本机 `.env` 的受控副本及解释器位置/版本记录；凭据不进仓库、日志、公共证据。审校账本非空坏行、截断尾部、非法状态/revision/时间必须显式失败并定位文件与行，保留现场后在副本修复。不能从云盘、SQLite 或空默认值自动重建人的决定或发布历史。

### 2.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|
| DB 可从文件夹全量重建 | 删掉 DB 跑 `reindex`，结果与重建前逐字段相同 |
| 历史可分页且不触发处理 | 老帖跨多页、平台/月/tag 组合筛选，页码/总数正确；第 91 天以前详情可读，付费与业务账本零写入 |
| 源图片变化可识别 | 同名等长换字节、增删图片、改变顺序均使指纹变化；人工图保留，已排期只提醒 |
| 接续和备份保持边界 | archive/state/config/.env 受控副本核验，所有入口同源同锁，原激活和历史发布记录不变 |
| 周期与大型证据留存 | 两个备份周期可恢复；大型媒体/probe 分版本保存，旧版本补送不读取当前文件 |
| 没有业务代码读 DB 做决策 | hygiene：`core/` `routes/` `pipeline/` `publish/` 不得 import 索引层 |
| 文件夹名不会二次变更 | 改正文后重跑归档，`folder_name` 不变 |
| 路径长度安全 | 最长可能路径 < 240 字符（用最长的真实 slug） |
| 镜像是单向的 | hygiene：镜像模块没有任何从飞书读回写本地的路径 |
| 留证不被覆盖 | 同一篇改两版，云盘上 v1 与 v2 同时存在 |
| 改 tag 只在月份内移动 | 8 月的帖子在 9 月改 tag，落点仍在 `2026-08/` 下 |
| 多 tag 只落一处 | `tags` 有 3 个时云盘上只出现 1 份，且 `元信息.json` 里 3 个都在 |
| 人工版译文不被作废 | 源文哈希变化时人工版仍在，只多一个 `stale: true` |

**`preflight`**：DB 与归档的差异条数（应恒为 0）、云盘镜像最后一次成功距今多久、
本地归档与镜像的篇数差。

## 3. 阶段三 · 翻译、标签与链接

### 3.1 业务诉求

- 用提示词文档规范文案翻译与图内文字翻译；
- 模型产出后若人工认为不合适，允许人工输入优化指令让模型重新生成；
- 英文 #tag 有相当一部分来自英语区热搜，直译到德国站匹配不上，希望自动获取德语地区
  热度较高、语义接近的 #tag 并推荐给业务审核选择；
- FB 支持文案内联链接、IG 不支持（只能引导去 bio），且英德落地页不同，不能原样复制。
  需要设计合理的人工审校页面与操作。

### 3.2 这一步谁在做什么

**这是她真正花时间的地方。** 前两个阶段她看不见，后两个阶段她只是点几下。
一篇帖子 10 分钟里，有 8 分钟花在这一节的产出上。

所以这一节的设计原则和别处不同：**别的地方优先考虑"正确"，这里要优先考虑"她会不会看"**。
一个正确但她会跳过的提示，等于不存在；一个让她多按三次才能确认的操作，
用两周之后就会变成"直接点通过"。

### 3.3 一个结构性发现：这不是翻译，是本地化

> **德语文案不再是英文文案的翻译，而是平台相关的本地化。**

FB 能内联链接、IG 不能；FB 的德语落地页和英文落地页不是同一个；#tag 要换。
三条合起来意味着 **FB 版和 IG 版的文案物理上就是两份不同的东西**。

2026-09-11 之前的旧代码曾**一次提交同时发到 FB 和 IG、用同一份文案**，并沿用 composer 默认双选。这段历史解释为何 S2-1 是硬前置；当前契约与实现方向是单一来源对应单一渠道，缺证据就阻止提交。

**所以 S2-1「两条独立车道」从优化项变成了本阶段的硬前置。**
不改它，短链和 #tag 这两个需求物理上装不进去。返工路径见 §6.2。

好消息是新的业务模型让界面简单了：FB 源 → 德国站 FB Page，IG 源 → 德国站 IG，
**每篇帖子只有一个目标渠道**，审校页不需要同时编两套文案，只需要知道"这篇走哪套规则"。

### 3.4 要实现什么

#### 审校页的文案编辑区拆成三个区块

**改哪里**：`web/ui/src/components/TextCompare.vue` 拆成三个组件、`web/api/reader.py` 的字段

2026-09-11 当时的界面是一个大 textarea 左右对照。三个需求（优化指令、#tag、短链）塞进同一个
textarea 会互相干扰，所以拆开：

```
┌─ 主文案 ───────────────────────────────────────────────┐
│  英文原文            │  德语译文  [编辑] [✨ 优化指令…]  │
│  ……                  │  ……                              │
│  🔴 2 处  ⚠ 3 处          [下一处 →]                     │
└────────────────────────────────────────────────────────┘
┌─ 话题标签 ─────────────────────────────────────────────┐
│  #CatLover → #Katzenliebe ✓映射   #PetCare → ⚠ 待确认   │
│  #Neakasa → #Neakasa ✓品牌保持      [+ 添加] [查热度]    │
│                                              6 / 30 标签 │
└────────────────────────────────────────────────────────┘
┌─ 链接 ─────────── 本篇是 Facebook 帖 ──────────────────┐
│  原文  https://dada.link/mKbGrw                         │
│  德语  https://de.neakasa.com/…  ✓映射表  [打开检查]     │
└────────────────────────────────────────────────────────┘
                                    正文 1,842 / 2,200 字符
```

IG 帖时第三块自动变形：

```
┌─ 链接 ────────── 本篇是 Instagram 帖（不支持内联链接）─┐
│  原文里有 1 个链接：https://dada.link/mKbGrw            │
│  ⚠ IG 文案里的链接不可点击，已从正文中移除               │
│  引导话术  ○ Link in Bio 🔗   ○ Mehr dazu im Profil…    │
│            ● 自定义：[                              ]   │
│  当前 bio 指向：https://linktr.ee/neakasa_de （只读）    │
└────────────────────────────────────────────────────────┘
```

**为什么值得拆成三块**——三条都是真实的：

1. **短链留在正文里会被模型顺手"翻译"。** [HANDOFF §6](HANDOFF.md) 说优惠码是最危险的
   一类，理由是"任意字符串却长得像单词"，**链接完全同型**。拆出去之后它根本不进翻译的输入。
2. **`hashtags_preserved()` 那道确定性检查要换语义**（从"逐个原样照搬"改成"映射/推荐已确认"），
   分区之后它不会和正文的金额检查搅在一起——[风险与标记约束](../web/DESIGN.md#风险、标签与运行状态)
   那条"两种标记不能混成一种颜色"的原则在这里同样适用。
3. **两个计数器有了明确归属**，接近上限时能指出是哪一块。

#### F3-1　短链映射表

**改哪里**：`config.toml` 新增 `[publish.link_map]`、`core/translated.py` 新增链接抽取与回填、
`publish/compose.py` 的离线闸

语义**照抄 `price_map`**：一张业务维护的「英文落地页 → 德语落地页」映射表，
**没映射过的链接第一次出现时停下来问人，已过目的直接放行**。这个模式业务已经用过一次
（金额），不需要重新解释。

它**不需要业务预先给一份清单**——`price_map` 那 46 条就是这么长出来的：
第一次遇到一个新金额就停下来问，问过一次就长一条。链接同理。

| | |
|---|---|
| 落点 | `config.toml` 的 `[publish.link_map]` |
| 分类 | 按 [REQUIREMENTS §5.3](REQUIREMENTS.md) 属于**业务决策**，与 `price_map` 同级 → Web 上只读 |
| 未命中 | 进人工队列，**不是丢弃**，也不是自动直译 |
| 附加校验 | 审校台提供「打开检查」按钮，人工确认落地页真的存在且是德语站 |

Facebook 运营可在正文光标处插入 `{{link1}}`、`{{link2}}` 等对应链接占位符。最终正文按链接区已选定的德国 URL 替换，未插入的有效链接仍追加到末尾，已插入的不会再追加一份。未知编号、缺落地页或损坏的占位符阻止通过；计数与预览使用替换后的完整文案，不能按短占位符低估长度。Instagram 不支持这种占位符，继续使用稳定 bio 话术。

#### F3-2　IG 的 bio 引导话术

**改哪里**：链接区组件的 IG 分支、`config.toml [publish].ig_bio_url`（只读展示用）

IG 帖的链接区变成话术选择器：几个预设话术 + 自定义输入。

**不做「这篇要求 bio 指向 X」的动态提醒**，因为它和定时发帖是硬矛盾：

```
9/10  她审完，排期到 9/15 10:00 发布
9/15  10:00 帖子自动发出，文案写着"Link in Bio"
      ↑ 谁在这个时刻去把 bio 改成这篇对应的落地页？
```

帖子是排到未来自动发的，bio 是账号级的、一次只能放一个。要让每篇帖子的 bio 都对，
就得有人在每个发布时刻手动去改 bio——那等于把定时发布的价值抵消掉。

**所以 bio 必须是一个稳定的聚合页**（Linktree，或 `de.neakasa.com` 上一个入口页）。
系统只在链接区**只读显示**当前 bio 指向（从配置读），不产生任何要求她去做的动作。

⚠️ 聚合页是业务要先建的东西，不是系统功能。没建之前这一行显示"未配置"。见 §8。

#### F3-3　单篇优化指令 vs 模板提示词

**改哪里**：`localize/text.py` 与 `localize/images.py` 的提示词组装、
`translated.jsonl` / `images_de.jsonl` 新增 `refine_instruction` 字段

`prompts/translate_de.md` 和 `prompts/image_de.md` 已经存在且可直接编辑。
要加的是**单篇的临时优化指令**，它**追加在模板之后，不改模板**。

| | 模板提示词 | 单篇优化指令 |
|---|---|---|
| 影响范围 | 全部帖子 | 一篇 |
| Web 上 | **只读展示** | 业务可输入 |
| 留痕 | `PROMPT_VERSION` / `IMAGE_PROMPT_VERSION` +1 | 写进 `translated.jsonl` / `images_de.jsonl` 的 `refine_instruction` |

⛔ **模板提示词在 Web 上只读。** 按 [REQUIREMENTS §5.3](REQUIREMENTS.md) 的二分，
它属于"改错会静默影响全部产出"那一类。要改走显式申请。

**注释必须跟着上界面。** `prompts/*.md` 和 `config.toml` 的注释是这个项目最有价值的
资产之一（每个参数为什么是这个值、改了会怎样），Web 表单会把它们扔掉——
只读展示时要带上原文注释。

本轮设置页的两个可写项为 `default_times`（默认 `10:00`、`17:00`，只作柏林预填值）和 `snooze_default_days`（默认 3 个上海工作日）。版本冲突拒绝保存，并保留原注释和其它配置；频率、账号、预算、许可、映射表及模板等受控参数保持只读且有原因说明。

#### F3-4　文案重生成与图片重生成的成本差两个量级

**改哪里**：`web/api` 新增异步任务端点、`core/paid_requests.py` 的预算闸调用点、
`config.toml [image].max_refine_per_media`

| | 文案重生成 | 图片重生成 |
|---|---|---|
| 历史单次成本（2026-09-11 估算） | DeepSeek，当时全月约 US$1 | **当时约 US$0.211 / 张**；本次按当前报价与 usage 留账 |
| 历史耗时（2026-09-11 样本） | 秒级 | **当时约 2.5 分钟 / 张**；不是当前耗时保证 |
| 界面 | 直接点，无需确认 | **按钮上直接显示本次预计花费** |
| 限制 | 无 | **3 次 / 张**；走已有 `RequestController` 预算硬闸 |
| 执行方式 | 持久化任务，返回 job ID | **异步任务**，刷新继续查询同一 job ID |

⛔ **重生成不得覆盖人工放进 `media_de/` 的图。** [README](../README.md) 明写
"人工放进去的文件程序不得覆盖——设计同事手工修的那张一定比模型那张对"。
重生成产出落到新版本号，人工图仍然优先渲染。

⚠️ **这是本项目第一次让非开发者触发付费调用。** 预算闸从"防止脚本跑飞"变成
"防止有人反复点"——两者的触发模式完全不同，闸的位置要重新检查。
3 次/张的上限意味着单张封顶 US$0.63，月预算 US$60 撑得住。

上面的美元数是历史估算，预算判断始终使用当前配置和统一账本。**每图最多受理三次优化**，在受理入口计数，并发点击也不能超过；失败和不确定请求不能用删 job 或换入口绕过。

模型任务必须关联来源版本、提示词版本、拥有进程身份、paid request ID 和更新时间。恢复要区分仍在执行、进程已中断、请求未发出、结果已落盘、远端可能已计费；有 owner 在运行时不能抢占。恢复入口先对账并以 job 版本做并发检查，返回可执行下一步，**恢复本身不隐含再次付费请求**。不确定项保留需人工核账状态，旧候选不再允许应用，已存在人工文案/图片保持优先。费用统计包括首次处理、重生成、风险扫描、已知用量和不确定费用，不能用任务次数代替账单。

“源文没变”与“模型产物仍为当前版”是不同判断。`stale: false` 只说明源文哈希关系，不能保证旧 prompt 的机器译文/图片仍有效；页面须给出 machine_current、机器 prompt 版本与当前 prompt 版本。本轮已核实 FB 旧机器译文 prompt 5、当前 prompt 6，当前读取没有可接受的德语图，原 FB 目录未发现 media_de。冻结 `.tech` 保留 3 张历史德语图，不作 FB 或新 `.global` 素材；不能据版本差异推断曾有 FB 德语图，也不自动付费重做。

#### F3-5　德语 #tag 热度推荐

**改哪里**：新建 `routes/hashtags.py`（采集）、`core/hashtag_rank.py`（排序）、
`state/de_hashtags.jsonl`、常驻调度进程挂一个周更任务

先说清楚一件事：**IG / FB 不存在"热搜榜 Top-N"这种接口。** 能采到的是三个可计算的量，
合起来才构成这个系统里"热度"的定义：

| 信号 | 采什么 | 来源 | 频次 |
|---|---|---|---|
| **量级** | 标签累计帖子数 `media_count` | IG 搜索接口（登录态，探测号） | 按需，只查候选词 |
| **当前热度** ⭐ | 同类德语账号近 14 天用了哪些标签、各用几次 | 一组德语宠物 / 清洁类账号的公开时间线 | 每周一次 |
| **趋势方向** | 同组德语候选的相对兴趣随时间变化 | Google Trends 公开页面导出的 CSV，`geo=DE` | 每周一次 |

第二个是主信号，也是这个方案里最值钱的一条：它拿到的是"德语圈这两周实际在用什么标签"，
比任何通用热搜榜都更贴我们的品类。而且它每周跑一次就够——标签热度不是按小时变的。

**本轮先跑降级形态。** 主信号需要一份德语同类账号名单，业务暂时给不到（见 §8）。
所以本轮允许主信号暂时缺数据，**三类采集器及业务接线都在范围内**；名单为空时只跳过该来源。实现一个来源不能关闭另两个来源：

```
名单为空  →  跳过周更采集，不报错
          →  推荐仍然产出（LLM 候选 + media_count + Google Trends 排序）
         →  界面上标明「缺少同类账号采样，排序依据不完整」
```

Google Trends 使用已确认的公开 CSV 路线：同一个英文标签的 3–5 个德语候选须在**同一候选组、同一个 `geo=DE`、相同时间范围与同批比较**内采样。它是组内归一化相对兴趣，不能把不同组/不同时间批次的 0–100 分数横排，也不能宣称为 IG 德国热搜。记录原始 CSV/哈希、候选组、地域、时间范围和采样时间；无可比数据则明示降级。

公开导出用请求专属的被动控件证据，绑定实际 CSV 下载按钮；任意登录按钮/链接不是导出证据。导出/导入保留原始 BOM/CRLF 字节并核 context 摘要，支持周/月 CSV。429/challenge 持久停止；只读状态给版本，人工核对恢复后在共享锁内做版本 CAS，恢复不代表已经导出。2026-09-12 的公开页已 429 停止，新适配与离线测试不算真实采样。

IG `media_count` 是**全球累计量级**，不是德国本周热度；同类德语账号信号是配置名单近 14 天实际用词频次，按周采集。两者从人工登录的探测 profile 走受 C7 限制的真实页面路径，分别保留来源、原始值、时间和失败原因。每个来源都要有 fresh/stale/failed/missing/空名单跳过的可解释结果；过期旧值不能作为当前新数据。标签采样、候选生成、排序与手工选择的证据分开记录。

**单篇的推荐流程**：

```
英文原帖 tag
   ├─ 品牌 / 型号（#Neakasa #M1Pro）→ 原样照搬，不进推荐
   │                                    （[image.keep_verbatim] 已有表）
   └─ 语义标签（#CatLover #PetCare）
         ↓  LLM 给德语候选词（每个英文 tag 给 3–5 个）
         ↓  在热度库里查这些候选的信号；库里没有的当场补查
         ↓  按热度排序
      推荐 Top-N 给业务勾选（默认预选与原帖等量，上限 30）
```

**四条必须钉死的规则**：

1. ⛔ **热度采集失败不得阻塞发帖。** 采不到就退回"LLM 德语候选 + 业务手选"，
   只是少了排序依据。它是增强，**不能变成发布链路的硬依赖**。
2. ⛔ **标签数默认与原帖等量。** 踩过"最多 3 个标签"静默删掉发布内容的坑，
   不能重犯。实测原帖标签中位 6 个、最多 11 个，IG 的 30 上限从未触发。
3. **推荐时必须显示热度的采样时间。** "上周的热搜"和"今天的热搜"是两回事，
   不标出来就是在骗人。
4. **标签查询由探测号兼做**，不新开第四个号。探测号本来就是可牺牲的那个，
   而且混入搜索行为反而让它的行为画像更像真人——纯时间线轮询是很机械的模式。

#### F3-6　付费边界：抓全部，但不为所有内容花钱

**改哪里**：`pipeline/engine.py` 的分流判定、审校台列表的「翻译这篇」按钮与端点

业务规则是“抓全部，发不发由她定”。`[publish.trusted_owners]` 控制可自动进入付费的作者，第三方默认人工内容级许可；本地化后的正式内容审校仍是另一阶段。被信任必须是当前配置中明确列出的作者，不按 `neakasa.*` 前缀自动扩大范围。

所以这道闸保留，但它的位置变了：

```
原作者在当前受信名单       →  预算允许时翻译 + 出图 →  进队列（德语成品）
原作者是第三方创作者       →  只抓不花钱           →  进队列（英文原帖 + 「翻译这篇」按钮）
```

理由不是省钱（2026-09-11 旧归档样本中 `.global` 的 31/31 合作方为 `.tech`，不是今天的全量统计），
是**她做这个判断需要的信息在翻译之前就齐了**——"这是别人拍的猫，我们能不能二次发布"
看英文原帖就够了，不需要先付 US$0.211 × N 把它变成德语。而且这本身是个信号：
**这一篇系统没敢自己处理**。

审校台上第三方作者的帖子必须显眼标出（[界面信息规范](../web/ui/DESIGN.md#操作与信息) 的
"常态不显示，异常才显示"原则——近期 IG 帖 35/36 是合作帖，那是常态，只标第三方作者）。

#### F3-7　两个计数器

**改哪里**：标签区与主文案区的组件

| 计数器 | 上限 | 实测触发情况 |
|---|---|---|
| 正文字符数 | IG **2,200 字符**（不是字节） | 最长一篇 1,647，德语 +20% 后 1,976，**0/21 触发** |
| 标签数 | IG 30 个 | 中位 6，最多 11，**0/21 触发** |

**只做计数器，不做超限硬闸、不做自动压缩。** 这条约束在真实数据上不成立，
为它建一整套处理流程（截断？让模型压缩重写？拒绝提交？）等于凭空多一条要维护的路径。

但计数器必须有：最长那篇余量只有 10%，德语翻译波动一下就可能真的顶上去，
到那天她需要当场看见。接近上限（≥ 90%）时变黄。

⚠️ **注意是字符不是字节。** 这批正文里 emoji 让字节数比字符数多 4%，按字节算会把余量
白白吃掉；如果哪天文案变得 emoji 密集，差距会更大。

编辑时 `/check` 按正文、标签、链接或 CTA 的完整当前草稿计算最终发布字符数；Facebook 先替换 `{{linkN}}`，再计入未使用链接和标签。后端响应未到时的本地近似数必须明确显示“约”，收到当前草稿的结果后显示准确数；旧响应不能覆盖后来编辑的计数或问题。数字/金额提示与结构性问题仍分开，失效占位符不能通过。

#### F3-8　英文语义风险预扫描

在翻译前对英文源文做真实风险扫描，覆盖 `pun`（俚语/双关）、`ambiguous`（歧义）、`us_only`（美国限定语境）。每份结果绑定账号、post ID、源文哈希、提示词哈希/版本、模型和生成时间，保留风险位置与中文解释。改源文或提示词后旧结果过期；人工优先内容展示不被旧候选覆盖。

`not_scanned`、`failed`、`succeeded` 且风险列表为空是三个不同事实；失败或没扫过不能写“安全/无风险”。红色本地确定性检查与黄色模型提醒分开，风险不是自动拒绝发布的事实判定。扫描共用来源许可、日/月预算与付费账本；缺本地凭据时先明确失败，不能制造“已向远端发出”的假账。页面只读取与当前内容绑定的实际扫描状态和来源。

### 3.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|

## 4. 阶段四 · 飞书推送

### 4.1 业务诉求

- 在企业飞书建一个 bot，处理完新帖后即时推送待审信息给对应运营人员；
- 没有新帖则不推；
- 为防止待审积压被遗忘，还要定时推送当前待审任务情况；
- 推送内容包括原帖基本信息、待审帖基本信息、可直接点击的审核页面跳转链接。

### 4.2 这一步谁在做什么

**飞书卡片是这个系统的主入口，不是通知。** 她的审校时间是随机的，完全跟着推送走——
没有推送她就不会想起来打开审校台。

这句话有两个后果，整节设计都从它们来：

- **卡片必须够她判断"现在开还是等会儿开"**。信息不足她就得先点进去看，那这条推送就白推了；
- **推送一旦被她静音，整条通道就死了**，而且是静默地死——她不会告诉你她静音了。
  所以推送频率与措辞是功能的一部分，不是文案润色。

### 4.3 历史缺口与当前外部依赖

2026-09-11 的问题是通知只有本地 toast/弹窗/log（S2-3），运营收不到。当前内容卡片、按帖去重/晨间摘要、固定尝试与人工核对恢复的离线行为都已具备，多收件人部分失效漏发也已复审修复。

**2026-09-15 起消息走群自建机器人（F4-1），不再等应用权限。** 需要人做的只剩：在两个群各建一个机器人、开签名校验、把四个值填进本机 `.env`（[MANUAL_STEPS 第 2 节](MANUAL_STEPS.md#2-配置本机凭据)），再跑一次 `notifications --self-test`。云盘镜像仍然要应用凭据，外部心跳仍未启用。

**一条没被这次改动碰到的缺口**：审校台还跑在 `127.0.0.1:8765`，卡片里的「去审校」在运营机器上大概率打不开。这是可达性问题，和传输层无关；运行机器的方案在配机器时定（§7）。

一个附带影响：`recipients` 从数组变成固定单标签，所以 F4-3 那套"聚合卡部分失效只补给漏收者"的**多收件人**逻辑在生产里不再被触发。代码和测试都留着，将来加第二个群就是再加一个角色标签。

另一个阻塞点：审校台现在跑在 `127.0.0.1:8765`，卡片里的链接她点不开。
本轮在开发机上调试，链接先指向开发机的内网地址；运行机器的可达性方案在配机器时定（§7）。

### 4.4 要实现什么

#### F4-1　Bot 形态：群自建 webhook 机器人

**改哪里**：`core/feishu.py::WebhookBot`、`config.toml [feishu]`、本机 `.env` 的四个变量

⚠️ **2026-09-15 推翻了原来的"自建应用"决定，走的是当时写下的退路。**
原判断没错——私聊、按人聚合、卡片回调确实只有自建应用做得到。但那条路卡在
"企业飞书管理员开 AppSecret"这个**你控制不了的外部依赖**上，卡到整个阶段四一条消息也发不出去，
而飞书卡片按 §4.2 是这个系统的主入口。入口发不出消息，前面三个阶段跑得再对也没人看得见。

群自建机器人只要一个 URL，人自己在群里就能建。换来今天能跑，代价是下面四项：

| 丢掉的 | 后果 |
|---|---|
| 私聊 | 消息发到群，组内可见。待审卡带德语文案和风险提示，等于组内都看得到 |
| 卡片缩略图 | 机器人没有图片上传接口，`img_key` 必须先由应用上传。F4-4 把首图写成"现在开还是等会儿开"的唯一依据，这条**已降级** |
| 远端 uuid 去重 | `im/v1/messages` 的 `uuid` 参数机器人不支持。回执不确定后重试可能在群里重复一条 |
| 远端 message ID | 响应里**没有** `message_id`（已核官方文档）。人工核对"已送达"填的是自己写的说明，不是平台 ID |

前两项是真实功能降级，不是等价替换。缩略图的代码位仍然留着（`notification_card` 认
`image_key`），将来拿到应用凭据可以补回来；`prepare_preview` 也仍然在发送前重读当前有效稿，
只是把首图状态写成文字（"德语首图（未随卡片投递，请在审校台查看）"）。

**`FeishuClient` 不能删。** `core/mirror.py::DriveClient` 是它的子类，云盘镜像（F2-4）
仍然依赖自建应用的 tenant token。所以"放弃自建应用"只针对**消息通道**。

**两个群，都必填。** 接收方在代码里是固定角色标签 `ops` / `tech`，URL 由 `WebhookBot`
按标签从环境变量解析：

| 角色 | 环境变量 | 收什么 |
|---|---|---|
| `ops` | `FEISHU_WEBHOOK_OPS`（+`_SECRET`） | 待审、积压、排期成功/失败、晨间摘要 |
| `tech` | `FEISHU_WEBHOOK_TECH`（+`_SECRET`） | 系统告警、F1-9 的监测与落档播报 |

⛔ **发件箱里落的是 `ops` / `tech` 标签，不是地址。** 群机器人地址本身带 token，
写进 `feishu_outbox.json` 就等于把凭据写进状态文件（红线 10）。两个地址填成同一个群时，
运行页会显式标出"两组已合并"，不静默生效。

⚠️ **签名校验推荐开。** 不开就必须在群里设关键词，那时卡片标题里的 "Neakasa" 要当关键词用——
而这个约束不在代码里，只在群设置里，改标题会静默失效。

#### F4-2　五类消息，两个接收组

**改哪里**：`core/feishu.py` 的消息模板、`config.toml [feishu].recipients`

既然要建这条通道，它应该同时解决 2026-09-11 旧优化清单里
S2-3 / S2-4 / S2-5 / S2-6 那四条——它们本来就在等一个网络推送通道。

| 消息类型 | 收件人 | 时机 | 对应缺口 |
|---|---|---|---|
| **监测与落档播报** | 德国运营 | 一轮两张，抓取落地即推，**24 小时不受静默窗限制** | §1.4 F1-9 |
| **待审提醒** | 德国运营 | 在岗窗内即时；离岗窗积压到次日 08:00 合并 | 新增 |
| **待审积压提醒** | 德国运营 | 上海 14:00 与 18:00，**只在有积压时推** | 新增 |
| **排期成功回执** | 德国运营 | 提交回读确认后，带 Planner 卡片关键字段供扫一眼 | S2-6 |
| **排期失败回执** | 德国运营 | 提交失败或回读不确定时 | **本轮新增** |
| **系统告警** | **技术群，独立分组** | 会话过期、抓取失败、预算超限、`doc_id` 轮换 | S2-3 / S2-5 |

**第四类是本轮补的缺口，也是最容易被漏掉的一类。** 她点了「通过」，系统半小时后在
浏览器里提交失败——2026-09-11 的旧链路没有业务侧回执。她会以为已经排上了，直到那天德国站没帖子。
这是业务事件，不是技术故障，不能归进推给开发者的系统告警。

失败回执的措辞必须**给出下一步**，不要只报错误码：

```
❌ 排期失败：日期选择器不允许跨月
   你选的是 10/02，而 Business Suite 当前只能排到 9/30。
   请改选 9 月内的日期重试。           [重新选时刻 →]
```

⛔ **业务消息和开发者告警必须分成两个接收组。** 运营同事不该收到"IG `doc_id` 轮换了"，
开发者不该被待审淹没——混在一起的结果是**两边都静音**，然后"沉默有歧义"
这个老毛病换个地方复发。

#### F4-3　静默时段与合并推送

**改哪里**：`core/feishu.py` 的投递队列、`config.toml [delta].on_duty_window`（静默时段共用在岗窗，没有独立的 `[feishu].quiet_hours`，理由见 §0.5）

**这是时区错位带来的硬约束，不是体验优化。** 美国站发帖峰值落在上海 20:00–23:00，
流水线跑完约 01:00 —— 而她上海 08:00–19:00 在岗。83% 的帖子处理完的时候她在睡觉。

**规则**：

- 在岗窗内（配置项，默认上海 08:00–19:00）→ 即时单条推送；
- 离岗窗内 → 积压，不推；
- 次日在岗窗开始 → **合并成一条**（"昨夜新增 3 篇待审"）；
- 紧急告警（会话失效、预算超限）**不受静默时段限制**，随时推给开发者组。

队列按**帖子/业务事件**汇总；一篇既有发现又有处理事件只计一次。发送前重新读取当前状态、人工优先文案、检查结果和首图；已排期、不发、接管或仍挂起的条目退出待审推送。晨间摘要包括夜间新增与兜底补抓、按视频/混合/无媒体/无正文分类跳过、处理延迟与失败、当前待审和最早等待时间。无新增、积压、失败或可行动变化时不推空日报。

**发送尝试前冻结消息。** 未尝试条目允许根据当前内容组卡；一旦可能已送到飞书，UUID、收件组和正文都固定。**签名信封不在冻结范围内**——`timestamp`/`sign` 每次尝试重算，否则超 1 小时就被拒。超时或回执丢失记为不确定，先核对；允许补送时重用同 UUID/同内容，不能重新组当前文案形成重复消息。⚠️ 机器人没有 `uuid` 远端去重，补送**可能在群里多出一条**；这个代价已接受（群里重复 vs 漏推）。群地址缺失、当前稿重读失败、明确失败、不确定结果分别在运行页可见。

人工核对通过 delivery ID、版本及“已送达/未送达”结果收敛。机器人不返回 message ID，所以“已送达”填的是人写的核对说明（接口字段名仍是 `message_id`）。有效原卡重试不换 UUID/内容；若合并卡部分失效，原尝试保留 cancelled，再仅对漏收者生成仍有效帖的新提醒，不能覆盖旧记录、让失效内容复活或重发给已收者——单群配置下这一支不会被触发，但逻辑保留。

⚠️ **静默时段按她的作息配置，不是按机器所在地的作息。** 这两件事今天恰好都在上海，
将来她换时区或换人时，改的应该是一个配置项，不是一堆硬编码。

不做这一条，第一周就会被静音，之后所有推送一起失效。

终态消息的在线保留期默认 `keep_delivered_days=30`。超过期限后，只能把全部关联事件/投递均已终结的完整组件按内容 SHA 归档，再收缩主 outbox；原卡片、UUID、收件人和回执仍可追溯，主状态保留事件去重索引，重启后不重发。`uncertain`、`retry`、`pending`、离岗未发或仍缺收件回执的内容不归档，不能按事件创建时间直接删掉。归档是保留旧证据的方式，不是抹掉投递历史。

**这两张卡回答的是「监测链路还活着吗」和「这一轮抓全了吗」，不是「该审了吗」。** 阶段一单独打磨时它们是唯一的出口——
那时没有译文也没有德语图，晨报一天只响一次。所以它走英文原文和原图，卡片上明写
「原帖预览，德语稿尚未开始」，不伪装成成品；内容为平台 · 账号 · 原帖时间 · 图片数、
正文前几行 + 首图、原帖链接 + 本地归档路径、预填产品 tag + 作者/合作方。

⛔ **回填帖不推。** 判据是 `post.json` 的 `source_route`：只有 `delta`（含复用同一路径的
兜底补抓）才推，`backfill` 是人主动滚出来的历史，逐篇推等于上线第一天刷屏。

⚠️ **静默窗有两道闸**——组卡时一道、实际发送时一道。只豁免其中一道，卡片会在离岗窗
悄悄消失且不报错。

#### F4-4　卡片内容

**改哪里**：`core/feishu.py` 的卡片模板

```
┌ Neakasa 德国站 · 新的待审 ───────────────┐
│ [缩略图]  Instagram · 4 张图              │
│           原帖 8/24 22:07                 │
│                                           │
│ Entdecke den neuen Neakasa M1 Pro –       │
│ jetzt mit noch mehr Saugkraft …           │
│                                           │
│ 🔴 新金额 $89.99 未收录                    │
│ ⚠ 3 处需注意                               │
│                                           │
│ 当前共 2 篇待审                            │
│                        [去审校 →]          │
└───────────────────────────────────────────┘
```

那两行告警是"现在开还是等会儿开"的唯一依据，必须在卡片上。

⚠️ **上面那张图是自建应用时代的形态；`2026-09-15` 起卡片里没有缩略图**（F4-1）。
当前有效首图是德语图还是原图仍然写在卡片上（"德语首图（未随卡片投递，请在审校台查看）"），
因为那句话本身就是"现在开还是等会儿开"的部分依据；但图片要到审校台才看得到。

摘要来自发送时**当前有效**的人工/机器德语文案，并显示来源渠道、图片数、原帖时间、确定性检查、
风险扫描状态/提示和直达该帖的审校链接。不能把原图、旧机器文案或未扫描伪装成当前成品。
重读当前稿失败时卡片标 `preview_error`，正文明说"内容可能不是最新"，而不是静默发旧快照。

积压提醒的措辞用**「最早一篇已等待 X」**，不要用「你还有 N 篇没做」。前者是事实，
后者是催促——她的审校时间本来就是随机的，催促推几次就会被静音，
然后整条通道一起失效。

#### F4-5　心跳仍然走外部服务，不由飞书承担

**改哪里**：常驻调度进程增加心跳推送、`config.toml [heartbeat]`

⛔ **不能让被监控的机器自己推心跳然后只在出事时告警。** 那样的话：

```
机器关机 / 断网 / 计划任务被禁用  →  监控也没跑  →  飞书上什么都没有
机器一切正常，只是今天没新帖      →  监控跑了     →  飞书上什么都没有
```

两种情况在飞书上完全一样。

**做法**（= S2-4）：机器定时往外部心跳服务（healthchecks.io 之类）推心跳，
**缺席由外部服务来叫**。飞书日报作为补充。外部服务是唯一一个
"被监控方挂掉时观察者还活着"的选项。

提频让这条更重要：每小时一次的东西停了，比每天一次的停了更难被人注意到。

**会话过期用被动推断，不主动探测**（= S2-5）：每一轮正常探测本来就会碰接口，
失败了就是会话出问题了 → 直接推飞书。发布号同理，从提交结果推断。

⛔ **不要写定时主动探测。** 它会给探测号加上一条稳定的、有规律的请求节奏，
正好是 C7「随机化触发时刻、频率可降级」要避免的东西。被动推断是零额外敞口。

### 4.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|
| 无新帖不推送 | 空轮次不产生任何飞书消息 |
| 静默时段不打扰 | 上海 23:00 产生的待审在次日 08:00 合并推出（注入时钟） |
| 合并推送不丢条目 | 夜间 3 篇，次日那一条里 3 篇都在 |
| 两个接收组不串 | 系统告警不进业务组，待审不进开发者组 |
| 失败回执会发出 | 提交失败与回读不确定两种路径都产生业务侧消息 |
| 积压提醒只在有积压时推 | 队列为空时 14:00 / 18:00 不产生消息 |
| 静默时段按共同作息走 | 改 on_duty_window 后探测与飞书同时采用新窗口，没有独立 quiet_hours 或硬编码 |
| 按帖聚合与当前内容 | 夜间重复发现/处理同帖只计一次；排队后人工修改、挂起、不发、接管、源变更均重新计算 |
| 晨间摘要与首图说明 | 补抓/分类跳过（四类中文标签）/延迟单列；首图是德语图还是原图写成文字并注明未随卡片投递；无事不推 |
| 不确定重试保持身份 | 远端可能成功后重启，UUID、两接收组路由和已冻结内容不变，不盲重放 |
| 请求信封契约 | `card` 是 JSON **对象**（`content` 那套要 `json.dumps`，机器人相反）；签名每次尝试重算；`code` 与旧版 `StatusCode` 两种成功响应都认，`19021`/HTTP 5xx/非 JSON 一律失败闭合 |
| 凭据不落盘 | 群地址与签名密钥不出现在 `feishu_outbox.json`、`status()` 或任何异常文案里 |
| 两组不串 | 监测/落档/待审都进业务组，`system` **只**进技术组；两地址相同要显式标"已合并" |

**人工验收一次**：`notifications --self-test` 在两个群各收到一张自检卡且角色不同；
卡片链接在她机器上能打开对应帖子详情页；手动停掉调度进程，外部心跳服务在阈值内告警。

## 5. 阶段五 · 审校结果、排期与月历

### 5.1 业务诉求

- 审核通过 → 业务选定发布日期 → 系统在 Business Suite 后台自动创建定时发帖任务
  → 核验成功后推飞书 → 同步更新任务列表状态；
- 系统页面里要有一个 Calendar，展示当月所有已在 Business Suite 排期的任务；
- 审核不通过 → 业务可调整（译文 / #tag / 短链 / 按自输入指令重生成图片）直至满足条件；
- 也允许暂时不发送这篇，并提供便利的按钮下载文案与图片，自行调整或手工去后台发帖。

### 5.2 这一步谁在做什么

她在这一步做的每个动作都是**不可撤销或很难撤销**的：排期一旦提交，撤下来要去
Business Suite 手动删；发出去的帖子撤不回来。

所以这一节的设计原则是：**把不可逆的动作前面那一步做厚**（空档提示、跨月置灰、
提交前实时复核），**把可逆的动作做薄**（挂起、改 tag、重生成随便点）。

还有一条：**系统做不了的时候，要让她能顺畅接手**。
[HANDOFF §1](HANDOFF.md) 写着"硬拦人工是这个项目的反模式"——
下载按钮和 `handed_off` 状态就是为这句话服务的。

### 5.3 排期时刻改成任意时刻

`[publish.schedule_rule].times = ["10:00", "17:00"]` 从"固定槽"降级为**默认预填值**。
业务可以选任意不冲突的时刻。

### 5.4 要实现什么

#### F5-1　撞槽检测改成时间窗重叠判定

**改哪里**：`publish/business_suite.py:1495` 的 `read_scheduled_baseline` 筛选条件、
`config.toml [publish].min_channel_gap_min`

2026-09-11 的历史现状（S2-2）：按「同时刻 + 同正文 + 同渠道 + 同图数」筛，做的是**同帖去重**
（防同一篇排两遍），不是槽位占用检测——别人的帖子在同一时刻，正文不匹配就被放过了。

**改成**：同一渠道内，目标时刻**前后 90 分钟**内已有任何卡片 → 判定为冲突。

不能只判精确同刻——Planner 上差 5 分钟的两条帖，在粉丝 feed 里就是同时发两条，
是运营事故。90 分钟这个数是按"德国站一天 1 条左右"定的：足够挡住"看起来像同时发"，
又不会把同一天的两条堵死。

**同帖去重仍然保留**，它和撞槽是两个检查，不要合并（[附录 A 术语表](#附录-a-术语表)把它们分开定义
就是为这件事）。

**必须先证明月历完整和渠道可识别。** 2026-09-11 曾按“已有枚举器，改筛选即可”估计；2026-09-12 的实施要求明确补录单渠道和整月读取证据。只读到可见周、未加载完的格子或只有月份标题时，不能把未见到卡片解释为空档。

#### F5-2　顺延规则按"谁选的时刻"分两种

**改哪里**：`publish/workflow.py` 的撞槽分支

S2-2 原本确认的规则是"撞槽 → 自动顺延"。但那是**系统自己排时刻**时的规则。
业务已经手动选了时刻，系统再自动顺延，等于**改了她的决定**。

| 场景 | 撞槽时怎么办 |
|---|---|
| **人工选时刻**（当前的 assisted 档） | **当场拒绝并给出最近的 3 个空档**，让她自己改。不自动顺延 |
| **系统自排**（未来的 supervised / autonomous 档） | 走原规则：自动顺延，超过最大次数则停止并推送通知 |

#### F5-3　日期选择器必须表达 UI 上限，且要在正确的时区里判

**改哪里**：审校台的日期选择器组件、`publish/compose.py` 的离线闸

[HANDOFF](HANDOFF.md) 保留的 **2026-09-01 历史实测**为：当时日期选择器不能翻到下一月。这是当时观察，不是永久业务上限；2026-09-12 要按当前页面的实际可见范围、可操作控件和月份完整性动态计算，不能一直写死“同月”。

两条必须做对：

1. **不可选的日期直接置灰**，不要让她选了才报错；
2. **页面日期范围先按已观测的 UI 时区解释**，再与柏林选时互相转换；历史探查为 `America/Los_Angeles`，每次联调重新确认，不按机器位置心算。

下面保留 2026-09-01 同月上限下的时区算例，用来验证换算，不把“下月禁止”写成永久规则：

```
界面给业务看的是柏林时间，可选范围要按美西自然月算。

  柏林 10-01 06:00  =  美西 09-30 21:00  →  美西还在 9 月，允许
  柏林 10-01 10:00  =  美西 10-01 01:00  →  美西已进 10 月，不允许
```

而且柏林与美西的夏令时切换日**不是同一天**（2026：柏林 03-29 / 10-25，
美西 03-08 / 11-01），一年里有两段约一周的窗口时差从 9 小时变成 8 小时。
**手算必然在那两段里错。** 必须用 `ZoneInfo` 显式换算，两个方向都要有断言。

#### F5-4　状态模型：七态

**改哪里**：新建 `archive/<账号>/review_items.jsonl`、`web/api` 的状态端点、
[接口状态契约](../web/DESIGN.md#编辑与状态) 同步更新

```
pending_review ──编辑──> edited ──通过──> approved ──回读确认──> scheduled
      │  ▲                                    │
   挂起│  │到期自动唤醒 + 推飞书              └──明确失败──> pending_review + 失败回执
      ▼  │
   snoozed(wake_at)
      │
      ├──不发──────> skipped     （终态，要填理由）
      └──自己处理──> handed_off  （终态，可选回填原帖链接）
```

| 状态 | 含义 | 界面表现 |
|---|---|---|
| `pending_review` | 待我审 | 正常显示 |
| `edited` | 我改过（存在人工版译文） | 标「已修改」小标记 |
| `snoozed` | 挂起，到期回来 | 移出主列表，单独一个「挂起」页签，显示 `wake_at` |
| `approved` | 已通过，等系统提交 | 整行变灰 |
| `scheduled` | 已排期 | 同上 + 排期时刻加粗 |
| `skipped` | **不发**（终态） | 移出列表，**必须填理由** |
| `handed_off` | **已交人工处理**（终态） | 移出列表，可选回填原帖链接 |

**为什么「挂起」和「不发」必须是两个动作**：语义完全不同。挂起是"我现在不想处理"，
不发是"这篇不该发"。混成一个的结果是**挂起的帖子永远没人管**——而这正是
早期设计拒绝无到期机制的"退回"的理由。
带到期提醒的挂起不是死信箱，因为它会自己回来。**默认到期 3 个工作日**：
比"明天"长，够她真的去问清楚；比"一周"短，不至于忘了这回事。

**为什么 `handed_off` 不能记成 `skipped`**：[附录 A 术语表](#附录-a-术语表)里 `不发` 的定义是
"决定不发"，而这里是"决定不用系统发"。记成同一个状态，"这个月发了几篇"就会算错，
云盘留证里也会永远缺这一篇。回填框**不强制**——她不填我们就只知道"交出去了"，
那也比记成"决定不发"诚实。

**落点**：`review_items.jsonl` 追加式，每次状态流转一条记录，带时刻、动作、理由、
`wake_at`（挂起时）。本轮**不记操作人员**（§0.3）。

每条事件都保留 `actor: null`，不是省略字段。批准期间冻结并锁定内容；点击后的回执不确定需保持阻塞并核对，不能当成明确失败立即回到可再提交状态。恢复只补齐有证据的状态、快照、镜像和通知，幂等运行不能产生第二次远端提交。

到期检查挂在 §1.4 F1-5 那个常驻调度进程上，不新开进程。

#### F5-5　月历：后台定时读 + 手动刷新

**改哪里**：新建 `publish/planner_cache.py`、`state/planner_cache.json`、
审校台新增月历页

同一份 Planner 数据同时服务三处：**月历展示**、**撞槽检测**（F5-1）、
**提交后回读核对**（S2-6）。读一次，三处用。

月历展示的是**当月在 Business Suite 里的全部排期**，包括运营同事自己用手机发的
——那正是业务想要的"掌握当月所有任务状态"。

读取须覆盖**完整可见月份的所有日期格、每个格子的全部带时刻条目、手工 Planner 项和延迟加载内容**。日期格数量只能证明控件存在；标题出现、首屏稳定或读取一周均不能宣称整月就绪。每张卡片需带业务日期、UI 时刻、渠道、任务/远端标识和观察来源；平台给出的 active-time/活跃时间建议不是帖子，不计占用或已排期数。无法判定是否完整时返回 unknown/incomplete 并禁用空档保证，不能把未知当 0。

**公开状态只读观测。** `scheduled` 仍是已回读确认排期；另以观测时间、远端状态/公开链接记录 `published/public`、仍排期或 `unknown`。到了计划时刻也不能自动宣布公开；未看到明确远端状态时如实显示未知，不点击 `Publish now` 验证。

⚠️ **后台读和人工提交争同一把发布锁**（两者都要驱动发布 Chrome）。所以后台读必须
**低优先级、可放弃**：try-acquire 拿不到锁就跳过这一轮，下一轮再读。
**人工提交永远优先。**

页面上必须显示**「数据截至 HH:MM」**——不显示的话业务会以为看到的是实时状态。

#### F5-6　冲突判定做成两段式

**改哪里**：审校台的时刻选择端点、`publish/workflow.py` 的提交前检查

缓存可能是一小时前的，这一小时里别人可能用手机发了一条。历史观察表明手机手工项可能出现在 Planner，当前仍须按完整月份读取和实际状态观察验证；不能笼统宣布没有盲区。

| 阶段 | 数据来源 | 作用 |
|---|---|---|
| **选时刻时** | 缓存（快） | **乐观提示**："这个时刻可能和 X 冲突"，并给空档 |
| **提交前** | **实时读一次 Planner** | **悲观裁决**：最终判定，冲突则拒绝 |

这样既不牺牲交互体验，也不会因为缓存过时而排重。

#### F5-7　驳回后的修改循环

**改哪里**：审校台的四个编辑入口、`translated_human.jsonl`

业务不通过时，可以在同一个页面上改四样东西，改完直接通过——**不做"退回"**
（能直接编辑之后，无到期机制的退回会成为没人处理的死信箱）：

| 可改的 | 落点 |
|---|---|
| 德语译文（直接编辑） | `translated_human.jsonl`（人工版真相源，S1-4） |
| 德语译文（让模型按指令重生成） | `translated.jsonl` 新记录，带 `refine_instruction` |
| #tag | 帖级的标签选择记录 |
| 短链 | 帖级覆盖 + 是否回写 `[publish.link_map]` 由人决定 |
| 德语图（按指令重生成） | `images_de.jsonl` 新记录，带 `refine_instruction`；**不覆盖人工图** |

⛔ **必须区分"人直接改的"和"模型按人的指令改的"**：前者进 `translated_human.jsonl`
（永不被机器覆盖），后者进 `translated.jsonl`（仍是机器产物，可被更新版本取代）。
混成一个会导致“重跑一次把人工修改冲掉”——这是 S0-3 在 2026-09-11 的历史复现，当前人工真相源和回归专门守住这个边界。

#### F5-8　资源下载

**改哪里**：`web/api` 新增打包端点

业务选择自行处理时，一键打包下载该帖的：德语文案 `.txt`、德语图
（缺德语图的用原图并标注）、元信息 `.json`。下载后状态转 `handed_off`。

这个功能的真正价值是**给系统留一个体面的失败出口**。[HANDOFF §1](HANDOFF.md)
写着"硬拦人工是这个项目的反模式"——当系统做不了的时候，
让人能顺畅接手比让人被困住重要得多。

#### F5-9　提交并发保护

**改哪里**：新建 `publish/lock.py`（复用 `core/paid_model.py` 的 `FileLock`）

2026-09-11 原始盘点时只有 `paid_requests.lock` 与 `ImageRunLock`，这是当时补发布锁的原因。当前是否满足共享锁、僵死进程辨识和恢复，以对应实现和测试为准，不沿用旧“没有锁”的状态描述。

本轮只有一个审校人，"两个人同时点批准"不会发生。但**锁仍然必须做**，
因为竞争方换了：**F5-5 的后台定时读 Planner 会和人工提交争同一个发布 Chrome**。
提交前那道基线检查是「读 Planner → 确认无冲突 → 点提交」，
后台读插在中间就是典型 TOCTOU，后果发生在**不可回滚**的发布侧。

⚠️ 给未来的人：**不要因为"只有一个人用"就删掉这把锁。** 它防的不是人，是进程。

**规则**：人工提交优先；后台读 try-acquire 失败就跳过本轮。
将来多人时第二个请求**直接被拒绝**，提示"有人正在提交，稍后再试"。

**不做排队。** `pipeline` 的设计原则明写「每次从各阶段真相源对账，
**不建立发布任务队列**」，排队会破坏这条。

### 5.5 验收判据

**离线测试**：

| 判据 | 怎么验 |
|---|---|
| 可选日期随实际范围变化 | 历史同月夹具只允许已读范围；新月份刷新成功后更新上下界，读取不完整时不承诺空档 |
| 月边界按已观测 UI 时区换算 | 历史美西夹具含柏林 10-01 06:00，两个方向都测；新证据时区单独记录 |
| 夏令时两段窗口正确 | 2026-10-25~11-01 与 2027-03-14~03-28 的换算有断言 |
| 撞槽能拦住别人的帖 | Planner 上有一条正文不匹配的卡片，90 分钟内排期被拒 |
| 撞槽与同帖去重不混 | 同一篇排两遍报"重复"，别人的帖同时刻报"撞槽"，两条路径分开 |
| 人工选时刻不自动顺延 | 撞槽时返回拒绝 + 3 个空档，不产生任何提交 |
| 挂起会自己回来 | `wake_at` 到期后重新进待审列表并推飞书（注入时钟） |
| `handed_off` 不计入跳过 | 统计口径里 `skipped` 与 `handed_off` 分别计数 |
| 并发提交被拒 | 两个请求同时提交，第二个收到拒绝 |
| 后台读会让路 | 锁被占用时后台读跳过本轮且不报错 |
| 月历真正完整 | 整月日期格、带时刻徽标、手工任务、延迟加载、无条目和读取失败分别验证；活跃时间建议不计帖子 |
| 冻结与恢复不重提 | Web/CLI/人工结转统一快照，receipt 绑定指纹；批准中断/回读不确定后只补证据充分的本地投影 |
| 公开状态诚实 | 排期到点没有公开证据仍为 unknown；真实公开状态观察不触发写平台 |

**`preflight`**：Planner 数据截至何时、完整月份范围、排期数、已观察公开数、公开状态未知数、`handed_off` 篇数。没有公开观察证据时不算成“0 篇发出”。

**真实验收分别留证**：长正文完整回读、多图数量/顺序/最终字节、FB 德国落地页链接、IG 稳定 bio 聚合页 CTA、手工 Planner 条目、月历延迟加载、同渠道 90 分钟冲突、任意柏林时刻及月界/DST。提前准备两篇具体内容给用户审查，确认后各完成一个 FB-only 和 IG-only 排期，分别取得目标账号/渠道/时刻/remote ID 回读。最终还要由运营从飞书卡片打开审校台、修改/检查、选期确认并收到回执，不能以两个独立脚本提交代替完整操作流程。

### 6.2 S2-1 是阶段三与阶段五的共同地基

短链要分平台、#tag 要分平台、排期要分渠道，**全都压在"两条独立车道"上**。

它原本是返工成本最大的一项，完整路径是：

```
1. 重录 probe 探查（人工约 15 分钟，需要开发布 Chrome）
2. 补渠道勾选的交互证据 —— 当前 dump 里没有这项记录，代码注释明说是刻意不点的
3. 重跑 G8 真机验证
```

红线 5 由 `publish/evidence.py::verify` **机器强制**：每条定位必须能回查到真实 dump
的具体交互编号。**没有证据就写不出选择器**，这一步绕不过去——不用靠人记，测试会变红。

换机器或丢失绑定的 dump 时，证据闸会阻止真实提交，须重新录证；本轮只在开发机联调，运行机器迁移仍延期。2026-09-12 已记录单渠道控件及被动 probe，选择器仍须对应真实证据；控件录证不等于长文、多图或单渠道提交回读通过。

重录时要顺手做的两件事（否则还得再录一次）：

1. 记录**渠道勾选区的交互**（S2-1 需要）；
2. 抄下**德国站 IG 在勾选区的显示名**（F5 需要，见 §8）。

完成后的收益不只是解锁本轮需求：跨平台配对那道人工闸消失（近 90 天有 12 篇卡在
"只是相似，停下来让人选版本"），可发单元从 48 涨到 62。

### 7.1 刻意接受的三处代价

**① 两条独立车道 → 同一条内容各做一遍。** 实测重叠期（2026-07-10 ~ 08-27）
IG 19 篇纯图文里 **6 篇（32%）与 FB 某篇是同一条内容**（4 篇正文相似度 1.00）。
拆车道之后这 6 篇会被翻译两次、图片德语化两次、她审两次，约占她工作量的 17%，
而且**两个平台会产出两个不同的德语版本**——同时关注德国站 FB 和 IG 的用户会看到
同一个活动有两套说法。

曾提过一个方案（保留配对逻辑降级为"孪生提示"，一键沿用另一平台的译文与德语图），
**业务决定不做，两个平台各自独立处理。** 记在这里是为了以后德语版本不一致时，
不用重新排查原因。

**② 本轮不记操作人员 → 这段时间的留痕事后补不回来。**
[REQUIREMENTS §4.3](REQUIREMENTS.md) 原本要求"必须在多人使用之前加"。
本轮单人使用，这条的实际风险是零；但加权限管理那一轮开始之前的所有记录，
**永远不知道是谁做的**。这是接受的，不是漏的。

`review_items.jsonl` **必须保留 `actor` 字段位（本轮值为 `null`）**，
这样加人时不用改 schema，也不用给旧记录写兼容分支。

**③ 2026-09-11 的回读缺口会连带阻止云盘回执归档。** F2-4 规定回读确认后才能落 `03_已发布/`；这是当时 S0-2 的影响，保留为历史依赖。当前目录是否有内容以冻结快照和真实回执为准，目录名不代表公开状态。

### 7.2 运行机器迁移：本轮不做，但三条事实先记下

配机器那天才会疼，而那天再翻这五轮的结论就晚了。

| 事实 | 出处 |
|---|---|
| **换机器必须重录 probe 探查。** dump（1.97 MB + 117 张截图 / 134 MB）不进版本库，换机器后 `--submit` 永久失效 | [HANDOFF §8](HANDOFF.md) |
| **三个 Chrome profile 必须在新机器上各人工登录一次。** 会话不可迁移，红线 1 禁止自动登录 | 红线 1 |
| **`state/published.jsonl` 不可重建。** 丢了会导致幂等失效，已发过的帖子可能被再发一遍 | [REQUIREMENTS §8.1](REQUIREMENTS.md) |

配机器时要一起定的还有：出口 IP 必须是住宅/普通宽带（红线 2），以及
**飞书卡片里的链接指向什么**（固定内网 IP / 内网域名 / Tailscale 三选一）。
不定最后一条的话，阶段四做出来也是一个点不开的链接。

操作步骤写在 [MANUAL_STEPS.md](MANUAL_STEPS.md)，不在这里。

| 当前内容 | 发送、展示或提交那一刻，从本地真相源重新解析出的人工优先文案、图片、状态和来源版本 |
| 冻结内容 | 某次批准、镜像或补送已固定的内容快照；后续文件变化不能改变它 |
| 静态图文 | 有正文、至少一张媒体、所有媒体都是图片；本轮唯一可加工/发布范围 |

### A.2　浏览器与抓取

| 词 | 定义 |
|---|---|
| 回填浏览器 | 端口 9222；人工登录、人工滚历史；一次性深度抓取 |
| 发布浏览器 | 端口 9223；Business Suite 提交与 Planner 回读 |
| 探测浏览器 | 端口 9224；低深度增量与兜底对账 |
| 人工登录 | 人在专用 Chrome 完成登录和二次验证；代码不得自动登录 |
| C7 预算 | 对抓取频率、深度、会话时长、失败次数和重试的累计风险限制 |
| 增量 | 读取最近内容，找出本地没有的新帖；不是历史回填 |
| 兜底对账 | 07:00 上海时刻附近的有限深扫，用于发现首屏遗漏；不是自动滚全历史 |
| 接近实时 | 在运营需要审校前准备好内容；不等于无限提高抓取频率 |
| 月度发帖窗 | 上一个完整月的来源时刻分布，附两平台样本/覆盖；不足保留既有计划，不自动提频 |
| 整批截止预算 | 双平台扫描及同批全部翻译/风险/图片与余量，决定前移兜底及同一 08:00 截止点 |
| 扫描事实/处理事实 | 发现内容和完成本地化的两套开始/结束/结果；扫描成功不等于处理完成 |
| 兜底中途过期 | 前序耗时导致开扫前已超截止时，跳过深扫但保留普通探测，跳过事实进入技术告警/晨间摘要；仅实际深扫能合并普通探测 |
| 源发帖至待审时效 | `source_created_at` 至同一来源首次 `post_content_ready` 的 P50/P95，包含发现等待；缺历史事实不补造 |
| 批次处理时效 | `requested_at` 至 `content_ready` 的 P50/P95；与源发帖时效分开，不能拿它替代端到端指标 |
| 晨间就绪率 | 有截止事实的晨间批次中，在上海截止点前准备好的比例；同时展示样本数，缺数不报 100% |
| 出口证据 | ASN 类型、近期出口/ASN 变化、时间/稳定性/过期；未知不能当预检通过 |

### A.3　本地化与付费

| 词 | 定义 |
|---|---|
| 机器译文 | `translated.jsonl` 中与来源哈希绑定的模型结果 |
| 原文未变 / 机器结果当前 | `stale=false` 只说明原文未变；`machine_current` 还检查提示词版本，API 同时给机器版和当前版。当前旧 FB 译文为 5、现版为 6；德语图是否存在/可用需另查，不能据版本差异推断文件历史 |
| 人工文案 | `translated_human.jsonl` 中的追加式修订；优先级高于机器译文 |
| 人工图片 | 人工放入/确认的德语图片；机器重跑不得覆盖 |
| 确定性检查 | 本地规则可明确判断的金额、受保护标签、@提及、数字/单位等问题 |
| 风险预扫描 | 模型对俚语/双关、歧义、美国限定语境的提示；允许误报，不能当硬事实 |
| hashtag sampler | 从真实来源采集带时间戳信号的实现；排序器或静态样例不算 sampler |
| 三类标签信号 | Trends DE 同英文标签候选组/同时间 CSV 相对兴趣、IG 全球累计、德语同类账号近 14 天用词周更；各自新鲜度/降级 |
| Trends 控件 proof | 被动记录的本次候选组/DE/起止日对应 CSV 按钮证据；Sign in 或任意链接不能代替 |
| Trends 持久停机 | 429/challenge 后保存 blocked；`trends-status` 只读取得 revision，人工核对后带该版本 CAS 恢复，恢复不自动导出 |
| 风险扫描状态 | 未扫、失败、成功零风险、来源/提示词变化后过期分别可见，失败不称安全 |
| 统一预算 | 所有文本/图片入口共用日/月额度和同一付费账本 |
| 来源许可 | 第三方内容进入付费处理前需要的内容级同意 |
| 孤儿模型任务 | 账本仍显示 pending/running，但拥有它的进程已退出；必须恢复或转人工核账 |
| 不确定请求 | 远端可能已经计费/处理但本地没有确认终态的请求；先核账，不自动重放 |
| 模型恢复 | 按进程/job/request/source/prompt/任务版本核账和收敛状态；动作本身不再请求付费模型 |
| 批次 operation_id | 把某次后台处理与同次 paid request/费用关联的标识；人工恢复还需当前批次版本，不能用 ID 绕过核账 |
| 两个运营设置 | 仅默认柏林预填时刻（10:00/17:00）和挂起工作日（3）；CAS 保存、保留注释，其它受控项只读附说明 |
| FB 链接占位符 | 在正文光标处插入 `{{linkN}}`，最终换成对应德国 URL；未插入链接末尾追加，计数按最终正文，非法 token 阻止通过；IG 不支持 |

### A.5　数据与恢复

| 词 | 定义 |
|---|---|
| 真相源 | 能决定业务事实且不能被索引反向覆盖的追加式记录或来源文件 |
| 派生物 | 可由真相源重建的 manifest、SQLite、HTML、Planner cache 或云盘视图 |
| 单向镜像 | 只从本地写到飞书云盘；远端内容不回写本地 |
| 版本追加 | 内容变化产生新版本目录/记录，旧版不覆盖 |
| 冻结补送 | 云盘缺某个旧版本时，用该版本已经保存的快照补送；不用当前内容伪造 |
| 激活边界 | 自动流水线开始处理新内容的时间/标记；接续数据时必须保留，避免补发旧帖 |
| 发布账本 | `state/published.jsonl`；不可重建，丢失会破坏幂等 |
| 审校账本损坏 | `review_items.jsonl` 存在非空坏行；必须失败闭合，不能静默跳过 |
| 90 天窗口 | 默认待办/查询范围，不能限制更早历史访问或删除底层归档 |
| 历史查询 | 服务端分页/total/range、平台/月/tag/状态筛选；按 ID 的详情不受 90 天限制，查询不翻译 |
| 来源内容指纹 | 源文及每张原图实际字节哈希、数量和顺序；同名同大小并不意味着没变 |
| 规范来源文字摘要 | `source_text_sha256` 全链路同算法并由 AST 守卫；风险 raw `scan_text_sha256` 另保留偏移，最终提交字节摘要不受该规范影响 |
| 运行绑定 | 让 Web/CLI/批处理/调度共享同一份 archive/state/.env/解释器与锁的配置；主干直接用 `config.toml`，副本工作区用忽略入库的 `config.local.toml` 指回同一份数据 |
| 核验备份 | 包含 archive/state/运行配置与本地环境受控副本的文件数/大小/哈希及恢复验证；一次备份不等于周期能力 |
| 周期账本包 / 独立证据版本 | 主配置与不可重建账本定期封装；大图/probe/截图按路径及内容 hash 单独保留版本，不在每包重复复制；密钥另受控保存 |

|---|---|
| 当前内容卡片 | 未尝试消息发送前读取当前有效德语首图/人工优先摘要/检查；原图回退明示 |

| 外部心跳 | 独立于被监测机器的服务检查缺席；飞书日报不是外部心跳 |
| 常驻调度器 | `pipeline.scheduler`，按窗口运行 delta/reconcile |
| 旧安装 CLI | `tools.schedule install` 所装的旧每日任务；不用于当前常驻调度器 |
| 常驻任务生命周期 | scheduler-install/status/disable/enable；安装/恢复检查旧每日任务，停用结束实例，恢复启动实例 |
| 五阶段只读状态 | `/api/runtime` 与 `preflight --json` 共用运行 snapshot；进程/扫描/处理/投递/镜像/发布/未知分开，无外部调用 |
