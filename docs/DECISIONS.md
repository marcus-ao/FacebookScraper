# 决策与教训

这份文件回答两个问题：**为什么是这样做的**，以及**哪些坑已经踩过了**。

它取代了原先的 `CODE_REVIEW.md`（2,649 行）、`HANDOFF.md`（1,447 行）和五份
`*_PLAN.md`（2,283 行）。那些是**过程性记录**——任务清单、逐轮交接、第几轮
做到哪了——任务做完之后它们就只剩考古价值，却仍在每次提交时被同步维护：
45 个 commit 里 `IMPLEMENTATION_PLAN.md` 和 `HANDOFF.md` 各改了 24 次，
比任何一个源码文件都频繁。2026-09-03 全部清理，内容留在 git 历史里。

## 1. 不可逾越的红线

违反其中任何一条会导致封号、烧钱或大面积返工。它们不是风格偏好。

1. **不得实现自动登录。** 项目里只允许存在一条登录路径：人工在
   `scripts\start_chrome.bat` 起的专用 Chrome 里登录一次，会话留在该
   Chrome 的 profile 目录，由 CDP 附着复用。多一条登录路径就多一份被
   checkpoint 拦截的机会，且两份会话状态必然漂移。
2. **回填由人工滚动，不许脚本自动滚。** 滚动的确实是人，没有可识别的
   自动化行为特征。代价是每次要花 20 分钟。
3. **增量的 C7 缓解措施是方案的组成部分，不是锦上添花。** 随机化触发时刻、
   抓取深度上限（只滚几屏不滚到底）、滚动节奏拟人、异常即停不重试、
   频率可降级、失败预算——**不要因为"跑得挺好"就把它们优化掉**。
   这类风险的反馈是延迟的，且只反馈一次。
4. **抓取小号与发布账号必须在两个 Chrome、两个 profile、两个端口上。**
   把持有 DE 发布权的账号和抓取小号放进同一个浏览器指纹里，等于把两件事
   绑成一件；而抓取小号被封是本项目唯一不可恢复的失败模式。
5. **不得凭猜测编写 Business Suite 的选择器。** 每一条定位都必须能回查到
   一份真实 probe dump 的具体交互/快照编号。这条由
   `publish/evidence.py::verify` 机器强制，不靠人守。
6. **密钥不进 config.toml。** 那个文件进版本库。走环境变量或 `.env`。

## 2. 刻意接受的边界

**自动发布是单机工具。** 证据 dump（1.97 MB + 117 张截图，134 MB）不进
版本库，因此换机器或 dump 丢失后 `--submit` 永久失效，必须重录一次探查。

2026-09-03 评估过两个替代方案，都不选：
- 导出脱敏摘要进版本库 → 摘要证明不了 final 截图存在，等于把闸调松一档；
- 原始 dump 连截图进版本库 → 撑爆仓库，且截图有漏内容风险。

代价写在明面上：`publish/evidence.py` 的模块说明、dump 缺失时的错误文案
（直接给出重录命令）、以及 `README.md` 都记了这件事。

## 3. 已经被自己推翻的判断

**留着是因为它们看起来仍然成立。** 每一条都曾经写进代码并跑了一段时间。

| 曾经的判断 | 真相 | 结果 |
|---|---|---|
| 增量可以完全登出，"没有账号可封" | FB/IG 在没有登录态时直接报错（`web_profile_info` 首次即 429） | 改走登录态；登出实现 2026-09-03 删除 |
| IG 首屏时间线随 HTML 下发、不走 XHR（CR-16） | 时间线**就在 XHR 里**，是归属判定把 39 个节点中的 35 个当成他人帖丢了（CR-19） | `harvest_embedded` 2026-09-03 删除 |
| 滚动很可能一直没生效（CR-17） | 未能证实 | 保留了"滚了没动要报出来"的可见性 |
| dHash 能检出"整张重画" | dHash 是**横向梯度**哈希。左右分割图与上下分割图的哈希**都是全 0**，它分辨不了 | 测试夹具改用梯度翻转；`dhash_max_distance` 至今是 -1（闸关着） |

## 4. 架构约束

- **`core/` 是叶子层。** 不许 import `translate` / `pipeline` /
  `pipeline_assisted`。（`core/paid_requests.py::default_budget_preflight`
  目前还在违反，用函数内延迟导入躲循环——已知债。）
- **付费模型调用的共用逻辑只能有一份**，在 `core/paid_model.py`。
  凭据读取、端点/费率校验、客户端构造、整批性错误判定、文件锁、原子写、
  JSONL 追加都在那里。CR-53 就是双份实现漂移的代价：修复只落到了两个
  副本中的一个，同一次 429 在两个阶段行为不同，持续了两天没人发现。
- **`tools/_scaffolding/` 不是生产链路。** `publish/` 不许 import 它。
  它一年最多用一两次（Meta 改版后重录）。
- **dHash 只有一份实现**，在 `core/imagehash.py`，用 BILINEAR。
  依据是 8/27 那组真实配对的实测（BILINEAR `[0,0,0,0,0]`、
  LANCZOS `[0,0,1,0,0]`，而配对闸是 `DHASH_DISTANCE = 1`）。

## 6. 这次清理动了什么（2026-09-03）

一次架构审查后的集中回收。完整分析见
`docs/architecture-review-20260902_190257.html`。

| 动作 | 结果 |
|---|---|
| 删登出增量、`_deprecated/`、`harvest_embedded`、死配置键与零引用符号 | −1,528 行 |
| 付费模型调用收进 `core/paid_model.py`（锁 6→1、凭据 2→1、原子写 6→1…） | 修掉 CR-53 的半边漂移 |
| dHash 收进 `core/imagehash.py` | 修掉两份实现给同一张图不同值 |
| 探针移入 `tools/_scaffolding/`，删 1,707 行脚手架测试 | 主干不再背 3,200 行录制器 |
| `verify_publish_chain` 五层嵌套改线性；dump 契约两份合一 | 结论不变，三道生产闸复核通过 |
| 文档从 13,766 行降到约 2,000 行 | 就是这份文件 + README + MANUAL_STEPS + PROBE_FINDINGS |

**没做的部分**：`tools/_scaffolding/probe_publish.py` 里 471 行 CDP 进程管理
没有精简。它需要真实 Chrome + Business Suite 会话才能验证，改坏了只会在
