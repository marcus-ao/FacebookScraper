# 界面清单

**成文日期：2026-09-13。** 六个界面全部在本机实际打开过：一次连**真实归档**（26 篇待审、1,067 篇历史），一次连隔离夹具（20 篇造好告警/风险/人工稿/多图/IG 的样本）。截图与量值在 `screenshots/`，用 `tools/capture_baseline.py` 可复现。

真实归档那一次只做 GET；写入动作全部在夹具上观察，夹具的 ASGI 层会把非 GET 请求挡成 503。

## 怎么读这份清单

每个界面五段：**她来这里干什么** → 路由与组件 → 控件与状态 → 量出来的尺寸 → 最主要的问题（详细分级在 [UI_AUDIT.md](UI_AUDIT.md)）。

截图命名 `<screen>@<宽>x<高>.png`，两套分辨率齐全：

```
screenshots/
  review-list@1920x1080.png           review-list@1366x768.png
  review-detail-risk@…                （有黄色风险 + 红色待确认标记的一篇）
  review-detail-money@…               （金额被改写，红色 error）
  review-detail-carousel@…            （6 张图的 IG 轮播）
  review-detail-editing@1366x768.png  （编辑态）
  decision-dialog@1366x768.png        （"这篇不发"模态框）
  history@…  calendar@…  settings@…  runtime@…
  measurements.json                   （每屏的行高、首屏条目数、按钮层级计数）
```

`measurements.json` 里每屏都有：`documentHeight`、`screensOfScroll`、`chromeBeforeContent`、`rowCount`、`rowHeights`、`rowsAboveFold`、`primaryButtons`、`dangerButtonCount`、`statusChips`、`borderedRegions`、`nativeSelects`、`sectionHeadingSizes`。下面引用的数都出自它。

### 最主要的问题

2. **有信号时信号也失效**：夹具里 12/20 有硬闸，10/17 可见行带红左边框，17 行各一个红色"这篇不发"。红色出现在 59% 的行上，它不再是"这行要注意"的意思。
3. **最该显眼的是"建议时刻"，它是 12px 灰字跑马行的第一段**，和"Facebook""1 张图"同权。
4. **一行四层文字**（摘要 / 告警 / 事实 / 分类），行高在 97 和 121 之间跳，扫描基线不稳。
5. **横向浪费**：1366 下摘要栏 974px 只放一行截断文字，右侧约 425px 空白。
6. **筛选一次性**：进详情再回来，页签/月份/分类/只看告警全部复位（[BASELINE_BEHAVIOR.md §6.3](BASELINE_BEHAVIOR.md) 有实测表）。
7. **没有批量动作、没有排序控制、没有全文搜索**。

## 2. 单篇审核详情

**她来这里干什么**：把一篇从"英文原文"变成"可以在德国站发的德语帖"。具体动作是：读一遍英文，读一遍德语，逐个看红黄标记，改正文，确认标签和落地页，逐张比对图片，最后选一个柏林时刻点通过。一篇大约要 3–10 分钟。

| 项 | 值 |
|---|---|
| 路由 | `/?task=<account_dir>/<post_id>`（id 自带一个斜杠，逐段编码） |
| 组件 | `TaskDetail.vue`（487 行）编排 9 个子组件：`RiskPanel`、`InitialTranslationPanel`、`TextCompare`、`HashtagEditor`、`LinkEditor`、`ImageCompare`、`MetaPanel`（内含 `TagEditor`）、`ApprovalPanel`、`RefinementPanel` |
| 数据 | `GET /api/tasks/{id}` + 三个子请求（`approval-options`、`initial-translation/task`、`refinements/task`）+ 两个轮询（1200ms / 1500ms） |
| 截图 | `review-detail-risk@*`、`review-detail-money@*`、`review-detail-carousel@*`、`review-detail-editing@1366x768.png` |

### 从上到下的实际顺序

|---|---|---|
| y=114 | 吸顶动作条（`position: sticky; top: 0`） | 43px |
| y=169 | 标记地图 | **10px** |
| y=187 | 英文语义风险预扫 | 80px（未扫）／189px（已扫 3 条） |
| y=285 | 英德双栏对照 | 437px |
| y=738 | 话题标签 ‖ 链接（两列） | 414px |

### 吸顶动作条的 13 个控件

`返回列表` │ `Facebook` `待我审` │ `2 处待确认` `3 处需注意` │ `共 5 处` `上一处` `下一处` │ `编辑德语` `稍后再审` **`这篇不发`** `下载并由我处理` `我已自行处理`

五类东西挤在一条里：返回导航、身份与状态、标记计数、标记内游走、业务动作 + 例外动作 + 转交动作。`flex-wrap: wrap`，窄屏会折成两行并把吸顶条撑高。

| 有未看图片 | 动作条下方灰框 `还有 N 张图没查看。`（**不禁用通过**） |
| 无标记 | 绿 chip `没有标记` |

| 指标 | 1920×1080 | 1366×768 |
|---|---|---|
| 整页高 / 屏数（有风险的一篇） | 2,168px / 2.01 屏 | 2,024px / **2.64 屏** |
| `btn-primary` 数量 | **2**（`通过并创建排期`、`生成文案候选`） | 2 |
| 编辑态 `btn-primary` 数量 | **3**（+`保存`） | 3 |
| 首屏内的 primary 数量 | **0** | 0 |
| `btn-danger` 数量 | 1（`这篇不发`，在首屏） | 1 |

| 标题总数 | 11（`h2`/`h3`/`h4`） | 11 |

### 最主要的问题

1. **首屏唯一有颜色的按钮是红色的"这篇不发"。** 两个 primary（通过并创建排期、生成文案候选）都在两屏以下。她来这里是为了"通过"，而"通过"要滚 1,500 像素。
2. **`共 5 处 / 上一处 / 下一处` 看起来像"上一篇/下一篇"**，实际是标记内游走。**真正的上一篇/下一篇根本不存在**——换篇只能返回列表（丢筛选）再点查看。
3. **红黄轻重反了**：chip 写"2 处待确认"（红色 `tag-error`），但那两处在正文里是全页最淡的标记（`mk-warn` 只有一条浅红下划线），而"3 处需注意"（较低严重度）是黄底 + 黄下划线，比前者显眼。
4. **风险面板把正文里已经标出来的东西再用散文讲一遍**：三条 bullet 引用的英文短语，就是下面正文里黄色高亮的那三处。同一信息两处，占 189px。
5. **未扫描时那块面板是满宽黄底**（`.status-not_scanned` 命中 `--risk-soft`）。真实归档 26 篇全是 `not_scanned`，所以**每一篇打开后第一眼都是一块什么都没发生的黄色警告**。
6. **标记地图 10px 高、`aria-hidden`、`tabindex="-1"`**：视觉上像装饰分割线，键盘与读屏取不到，而它是"标记扎堆在哪"的唯一入口。
7. **话题标签区把同一份标签列出两遍**：`原帖语义标签` 与 `本篇选择` 在未编辑过的帖子上内容完全相同（实测 9 个 / 4 个各两遍），占 414px。
8. **常驻系统说明**至少 6 句：`保存不会自动删减超出上限的标签。`、`建议不自动写入，采样不可用时可继续手动选择。`、`将编号标记插入正文可指定链接位置；未使用的链接会放在文末。这里保存本篇选择，不修改全局映射表。`、`这张没有程序生成记录（没跑过德语图，或当前用的是人工放置的图）。`、`指令只作用于本篇，不改写模板。`、`可选范围：… 至 …（柏林）。`
9. **实现细节外泄**：`{{link1}}` 占位符原样给运营看；风险面板脚注写 `prompt v1 · <provider> / <model>`；排期不可用时显示 `帖子 122100548013379375：机器与人工译文账本中都没有译文`（帖子 ID + "账本"）。
10. **编辑态几乎没有视觉提示**（见 `review-detail-editing@1366x768.png`）：德语栏的边框、底色、栏头文字与只读态一模一样，唯一的线索是 1,200px 外右上角换了两个按钮。
11. **图片对比在 y=1242**，而"还有 5 张图没查看"的提示在 y=150。提示和要做的事隔了一屏半。6 张图只能逐张点，没有一次看全的方式。
12. **两栏各 `max-height: 52vh`**：1366×768 下每栏约 400px。实测一篇 1,257 字符的英文原文在里面要滚 3 屏，两栏不同步。

## 3. 历史归档

**她来这里干什么**：查旧帖。要么是运营问"去年这条是怎么处理的"，要么是找一篇做参考。冻结账号 `in_neakasa.tech` 的 1,020 篇只读。

| 项 | 值 |
|---|---|

平台 / 月份 / 产品分类三个**原生 `<select>`** + `共 1067 篇` + 行 + 底部 `上一页 第 p / 36 页 下一页`。

行结构：56×56 缩略图（`v-if="row.image_count"`）│ 摘要 │ `2026-08-31 · Instagram · in_neakasa.tech · 待处理 · 冻结归档` │ 分类 │ `查看归档`。

### 量出来的

| 指标 | 1920×1080 | 1366×768 |
|---|---|---|
| 行数 / 行高 | 30 / 102px | 30 / 102px |
| 首屏可见 | **7** | **4** |
| 内容前固定高度 | 269px | 269px |
| 整页高 / 屏数 | 3,649px / 3.38 屏 | 3,649px / **4.75 屏** |
| 带边框区块 | 30 | 30 |
| 原生 select | 3 | 3 |

### 最主要的问题

1. **翻页器在 3,649px 处**。要翻到第 2 页得先滚将近五屏。36 页意味着这个动作要做 35 次。
2. **缩略图按 `image_count` 条件渲染**（`v-if="row.image_count"`），于是这一列的存在与否取决于数据。真实归档那一次**整列一张缩略图都没有**（展示索引里这些行的 `media` 为空），56px 的列位白占；夹具数据每行都有图时又全都有。两种数据混在一页时（真实场景迟早如此）有图的行文字左移 72px，列表左边界变成锯齿状。
3. **`冻结归档` 出现在 1,020/1,067 行上**。常态被当成标记。`in_neakasa.tech` 也在每行重复。
4. **状态用纯文字挤在灰行里**，和平台、账号、日期同权；这里没有任何 chip。
5. 与审校列表**两套行版式**：同一种东西（一篇帖子）在两个界面长得不一样（这边没有 chip、没有左边框分级、按钮文案是"查看归档"）。
6. **月份是 71 项的原生下拉**，没有分年分组。
7. 没有搜索。1,067 篇里找一篇只能靠三个下拉 + 翻页。

## 4. 发布月历

**她来这里干什么**：选时刻之前看一眼"这个月已经排了什么"，避免撞车。数据来自 Business Suite 的读取缓存，不是本地推算。

| 项 | 值 |
|---|---|
| 路由 | `/?view=calendar` |
| 组件 | `CalendarPanel.vue`（128 行） |
| 数据 | `GET /api/calendar`（进入即拉）；`POST /api/calendar/refresh` 需显式点 |
| 截图 | `calendar@1920x1080.png`、`calendar@1366x768.png` |
| 真实一次 | `cached_at 2026-09-13T05:01:33Z`、`status: stale`、4 张卡、覆盖 8/30–10/3 |

### 控件与状态

标题 `2026-09 发布月历` + 一句说明 + `刷新月历`（`refresh_available` 为假时 disabled）；元信息行：`数据截至 09/13 07:01（柏林时间）` / `数据可能已过期` / `4 条可见记录`；三种空态（没读过 / 缓存没覆盖本月 / 本月无排期）；`status === 'partial'` 时一条黄框；底部一句"月份按发布后台的美西自然月计算…"。

网格：`repeat(7, minmax(135px, 1fr))`，`min-width: 945px`，周一起始，日格 `min-height: 110px`。卡片是 `<details>`，`<summary>` 里放时刻 + 渠道 + 投递状态 + **`rendered` 全文**（`-webkit-line-clamp: 3`）。

### 量出来的

`documentHeight` 恰好等于视口高（1080 / 768）——`.calendar-panel { height: 100%; overflow: auto }`，整个月历在内部滚动。带边框区块只有 1 个。

### 最主要的问题

1. **135px 宽的日格里塞 500 字的正文**。实测 9/5 那格的 `rendered` 是 522 字符的德英双语全文，靠三行截断勉强收住。
2. **每张卡片重复一句投递状态文字**（`已观测到公开发布` / `已创建定时任务` / `发布状态待核验`），而这三种状态本该是一个视觉标记。
3. **空格子占满 110px**：9 月有 26 天没有任何排期，5 行网格里大部分是空的，而有内容的格子在溢出。
4. **`刷新月历` 与其它按钮同权**，但它持发布锁、驱动真实浏览器。
5. **没有"从这里选时刻"的路径**。看完月历要返回列表、打开某篇、滚到底部的排期区再选——月历与排期决策之间没有连接。
6. 一句永久脚注解释"美西自然月 vs 柏林月初"，这是系统内部换算口径。

## 5. 运营设置

**她来这里干什么**：改两件事——默认排期时刻（柏林）、默认挂起工作日数。其余全是只读核对。

| 项 | 值 |
|---|---|
| 路由 | `/?view=settings` |
| 组件 | `SettingsPanel.vue`（75 行） |
| 数据 | `GET /api/settings`；`PUT /api/settings` 严格 `{values, version}` |
| 截图 | `settings@1920x1080.png`、`settings@1366x768.png` |

### 控件与状态

两个 `<input>`（文本 + number 1–30）+ `保存设置`（`!dirty` 时 disabled）+ `重新读取`；七个 `<details>` 只读配置（监测来源账号 / 抓取控制 / 处理方式与预算 / 网络探查设置 / 发布账号核验名 / 价格映射 / 信任名单）；`saved && !dirty` 时绿字；离开守卫 + `beforeunload`。

### 量出来的

`documentHeight` 1,284px；`.settings { max-width: 900px }`，`form { max-width: 420px }`。1920 下 1,020px、1366 下 466px 横向不用。带边框区块 1 个。

### 最主要的问题

1. **`editable_help` 直接把 `config.toml` 的开发者注释渲染给运营看**，实测包含源码路径：

   > 这是 REQUIREMENTS 第 5.3 节二分里的「运营」类参数，可以改；代码三处默认值（web/api/reader.py、writer.py、ReviewActions.vue）只是兜底，真正生效的是这里。

   一个非技术业务同事被展示了三个源文件名和一份内部需求文档的章节号。
2. **两个字段的表单占了 1,284px 高**，因为每个字段下面挂两条 `<small>`（一条固定文案 + 一条 `editable_help`）。
3. **七个只读配置折叠块与可编辑表单同级并列**，"我能改的"与"我只能看的"没有结构区分。
4. **`默认排期时间` 是自由文本**，靠 `split(/[,，\s]+/)` 解析，没有时间选择器，格式错误只能靠服务端拒绝。
5. 900px 居中版心在 1920 下留大片空白，但纵向还要滚——密度方向反了。

## 6. 运行状态

**她来这里干什么**：出问题的时候来看一眼是哪一段卡住了。日常不该来。

| 项 | 值 |
|---|---|
| 路由 | `/?view=runtime` |
| 组件 | `RuntimePanel.vue`（101 行） |
| 数据 | `GET /api/runtime`，**每 30 秒自动重拉** |
| 截图 | `runtime@1920x1080.png`、`runtime@1366x768.png` |

### 控件与状态

`刷新状态` + 两块事实（调度进程 / 最近业务成功）+ 处理时效 P50/P95 + 五个阶段 `<article>`（阶段 1 探测、2 归档/镜像、3 德语本地化、4 飞书 outbox、5 审校与排期），其中：

- 阶段 3 有 `核对后关闭中断批次` 按钮（`window.confirm`，带费用时换更长提示）；
- 阶段 4 的 `<details>` 里每条不确定投递有 `登记已送达`（`window.prompt` 要消息 ID）与 `核对未送达后恢复`（`window.confirm`，**会重发飞书消息**）；
- 阶段 5 有九项 `✓ / 待补齐` 检查清单与 FB/IG 验收结论。

两份 label 映射表：`labels`（18 个运行码 → 中文）与 `checks`（9 个检查名 → 中文），都在组件里硬编码。

### 量出来的

`documentHeight` 1,487px / 1.94 屏（1366）。带边框区块 5 个（五个阶段卡）。段落 14 个，`.warning` 黄字 2 处。

### 最主要的问题

1. **工程语言直接给业务用户**：实测页面上有 `detect Chrome 9224 打开 Instagram neakasa.global 返回 HTTP 429`、`浏览器隔离`、`远端回读证据`、`FB 单渠道控件`、`Google Trends 采样已暂停：公开 Trends Explore 首次受控访问返回 HTTP 429`。Chrome 调试端口号和 HTTP 状态码出现在运营界面上。
2. **有行动的信息没有行动路径**："1 次提交结果需要核对，请在对应帖子中查看恢复入口。"——没说是哪一篇，也没有链接。
3. **这是诊断页，却和"审校列表"在导航里同级**。她一天要用的界面和一个月用一次的界面放在同一排。
4. **危险动作藏在折叠块里**："核对未送达后恢复"会真的重发飞书消息，它在阶段 4 的 `<details>` 内部，和只读文字混排。
5. **每 30 秒自动重拉**，页面内容会在她读的时候变。
6. 五个阶段卡结构相同但内容形态各异（有的是段落、有的是清单、有的是折叠块），没有统一的"状态 + 证据 + 行动"骨架。

## 7. "这篇不发"决定框（唯一的模态框）

| 项 | 值 |
|---|---|
| 触发 | 列表行、详情吸顶条 |
| 组件 | `ReviewActions.vue` 内的 `<Teleport to="body">` |
| 截图 | `decision-dialog@1366x768.png` |
| 尺寸 | 470×281 |

六种动作共用一个框（`snoozed` / `skipped` / `handed_off` / `handoff_link` / `export` / `woke`），按 `form.action` 切换标题、说明段、输入字段与确认按钮文案。

### 实测缺陷

1. **打开后焦点仍在触发按钮上**（被遮罩盖住）。`<textarea autofocus>` 对动态插入节点不生效。
2. **Esc 不起作用**：`@keydown.esc` 绑在 `<section>` 上，焦点不在框内就收不到;同时 `TaskDetail.onKey` 检测到 `[role="dialog"]` 会早退，所以 Esc 既不关框也不返回。
3. **无焦点陷阱**，Tab 会走到遮罩后面。
4. **破坏性动作的确认按钮是 `btn-primary`（靛蓝）**，不是 danger。
5. 做对了的：`skipped` 时理由必填，确认按钮在理由为空时 disabled；`@click.self` 点遮罩关闭；`busy` 时所有控件 disabled。

## 8. 两个分辨率的总账

| 界面 | 1920×1080 首屏内容 | 1366×768 首屏内容 | 1366 下要滚几屏 |
|---|---|---|---|
| 审校列表 | 7 条 | **4 条** | 2.95 |
| 历史归档 | 7 条 | **4 条** | 4.75 |
| 审核详情 | 吸顶条 + 风险面板 + 双栏上半 | 同（更少） | 2.49–2.67 |
| 编辑态详情 | 同上 | 同上 | 3.04 |
| 发布月历 | 内部滚动 | 内部滚动 + 横向 945px 下限 | 1（内滚） |
| 运营设置 | 两个字段 + 说明 | 同 | 1.67 |
| 运行状态 | 两块事实 + 阶段 1 | 同 | 1.94 |

1366×768 下，**每个列表界面都只能看到 4 条**，而 115px 的全局外壳 + 100px 的页内工具/筛选条在两个分辨率上完全一样——窄屏没有任何密度补偿。
