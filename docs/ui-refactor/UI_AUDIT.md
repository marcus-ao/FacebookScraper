# UI / UX 审计

**成文日期：2026-09-13。** 依据：通读 `web/ui/src/` 3,169 行与 `web/api/` 2,307 行；真实归档只读 GET（26 篇待审、1,067 篇历史）；隔离夹具交互观察（20 篇造好告警/风险/人工稿/多图/IG 的样本）；两套分辨率各 9 屏截图与 `screenshots/measurements.json` 的量值。

## 0. 这份审计怎么来的，以及它不做什么

**先说结论**：这个界面的问题不是"不好看"。它的设计口径写在 `web/ui/src/styles.css` 的文件头注释里——Swiss 极简、高密度、内容区只准两种饱和色（红=错了，黄=注意看）、动效 2/10——这些口径是对的，代码也基本守住了。问题在**信息架构**：

1. 最该被看见的东西（下一篇打开哪个、这一篇该不该通过）不在最显眼的位置；
2. 只在异常时才有意义的东西（红色、黄色、告警框）在常态下也占着位置，于是失去了作为信号的能力；
3. 一天要做几十次的动作（列表 → 详情 → 决定 → 下一篇）中间有一段被迫重做的工作（重设筛选）。

**这份审计不做的事**：不给"用现代组件""更干净"这类结论。每条 finding 都带可量的现状值和一条能直接实现的方向。也不替产品定业务口径——那些进了 [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md)。

## 2. P0 — 阻碍任务完成或可能导致错误决定

### P0-1 审校列表在两个目标分辨率下都扫不动

**界面**：审校列表
**问题**：1920×1080 首屏 7 条、1366×768 首屏 **4 条**（夹具数据）；真实数据下行高 82px 时是 9 条 / 6 条。而提纲要求的是"能不能快速扫 15–30 条"。内容之前有 215px 固定高度（全局外壳 115px + 工具条 23px + 筛选条 31px + 间距），占 768 的 28%。同时横向：1366 下摘要栏 974px 只承载一行截断文字，右侧约 425px 空白。
**为什么重要**：这是她一天里进出次数最多的界面。首屏 4 条意味着"下一篇打开哪个"这个判断永远需要先滚动。
**当前后果**：选下一篇变成"滚 + 读 + 回滚"，而不是"扫一眼"。
**设计原则**：列表是扫描界面，纵向密度优先于单行表现力；横向空间用来分列，不用来留白。
**方向**：行高目标 **44–56px**，单行内完成「缩略图 · 标题 · 状态 · 时刻 · 平台/图数 · 动作」，把告警与风险压成定宽的标记列而不是换行的 chip 行。外壳三带合一（品牌 + 导航 + 页面头合成一条 ~56px 的顶栏 + 侧边导航或分段控件）。目标：1366 下 **≥12 条**、1920 下 **≥18 条**。
**改哪里**：`TaskList.vue` 的 `.row` 网格与 `.body` 三层结构、`App.vue` 的 `.topbar`/`.workspace-nav`。

### P0-2 红色被用在常态上，于是不再是信号

**界面**：审校列表（详情同理）
**问题**：夹具 20 篇里 12 篇有硬闸，可见 17 行里 **10 行带红左边框**、**17 个红色"这篇不发"按钮**、`btn-primary` 数量 **0**。红色同时承担三件事：硬闸告警、破坏性动作、错误标记。
**为什么重要**：`styles.css` 的文件头自己立了规矩——"混成一种颜色，用几次她两种都不信"。现在犯的是同一个错，只是换到了红色的三种用途上。
**当前后果**：红色失去"这行要注意"的含义；真正的硬闸和一个从不点的按钮在视觉上一样重。
**设计原则**：状态色只表达状态，不表达动作。动作的层级用形态（填充 / 描边 / 文字）表达。
**方向**：行内破坏性动作移出行（收进行尾 `Dropdown` 的 `danger` 项）；硬闸改用一个定宽的状态列（图标 + 短词），红色只留给它；行主动作用整行可点击（P1-5）替代"查看"按钮。
**改哪里**：`TaskList.vue:133-141`、`ReviewActions.vue:71-85`（`compact` 分支）、`styles.css:117-118`。

### P0-3 筛选状态在每次进出详情后被清空（实测）

**界面**：审校列表、历史归档
**问题**：`tab`、`onlyAlerts`、`selectedTag`、`selectedMonth` 是 `TaskList` 内部 `ref`；`App.vue:163` 用 `v-else-if="!state.openId"` 渲染，打开详情即卸载。实测：切到"已处理 + 2026-09"（2 条）→ 打开详情 → 返回 → 回到"待处理 + 全部月份"（17 条），`location.search` 全程为空。`HistoryPanel` 的三个筛选与页码同理。

### P0-7 标记的视觉轻重与语义轻重相反

**界面**：单篇审核详情
**问题**：三档标记的画法（`styles.css:150-152`）：

| 档 | 语义 | 画法 | 视觉重量 |
|---|---|---|---|
| `error` | 这里错了 | 红底 + 红下划线 | 最重 ✔ |
| `warn` | 这处数字要人确认 | **只有一条浅红下划线** | **最轻** ✘ |
| `risk` | 翻起来容易翻坏 | 黄底 + 黄下划线 | 中 |

**设计原则**：同一语义在计数、标记、说明三处必须同色同级；视觉重量排序必须与后果严重度排序一致。
**方向**：`warn` 提到与 `error` 同一色系但可区分的重量（例如红底 + 虚线下划线 vs 红底 + 实线），`risk` 降为仅黄下划线（去掉黄底）。计数 chip 三档三色，与正文一致。
**改哪里**：`styles.css:143-152`、`TaskDetail.vue:288-296`、`marks.js` 的 `PRIORITY` 保持不动（那是重叠裁决，与画法无关）。

## 3. P1 — 每天都在付代价的认知负荷与工作流问题

### P1-1 页面导航与页内筛选共用同一套视觉

**界面**：全局
**问题**：五个工作区导航（`App.vue:140-144`）与列表的三个状态页签（`TaskList.vue:60-61`）都是 `btn btn-sm`，选中都是 `.selected`（靛蓝填充）。两排胶囊上下相邻，形态完全一样。
**后果**：她分不清"换界面"和"筛列表"，也就无法形成"这一排是导航"的肌肉记忆。
**原则**：不同层级的切换用不同控件类型。
**方向**：工作区导航改左侧 `Menu`（或顶栏的 `Menu mode="horizontal"`）；列表状态页签改 `Tabs`（带计数 `Badge`）；月份/分类改 `Select`；"只看有硬闸"改 `Segmented` 或筛选 chip。
**改哪里**：`App.vue:139-145`、`TaskList.vue:58-70`。

### P1-2 列表行四层文字，第四层只放分类

**问题**：行内四层——摘要（14px）/ 告警 chip 行 / 事实行（12px）/ 分类 chip 行。第四层只承载 `tags`，且只在有分类时出现，所以行高在 97 和 121px 之间跳。
**后果**：扫描基线不稳；最低价值的信息拿到了独立一行。
**方向**：分类并入事实行末尾或改成一列；告警压成定宽标记列。
**改哪里**：`TaskList.vue:89-131`。

### P1-3 卡片是默认容器

**问题**：列表 17 行 = 17 个 `1px 边 + 圆角 + 白底 + box-shadow` 的卡；历史 30 行 = 30 个；详情 12–13 个平级卡。
**后果**：边框成了页面上最密的视觉元素，却不表达任何层级关系；卡与卡之间的 8px 间隙又切断了列的对齐。
**原则**：卡片表达"这是一个可独立处理的对象"，不表达"这里有一块内容"。
**方向**：列表改表格/列表行（行分隔线，不是卡）；详情用"区段 + 标题 + 留白"分组，只给真正独立的对象（图片对照、决策卡）用 `Card`。
**改哪里**：`TaskList.vue` `.row`、`HistoryPanel.vue` `li`、详情各子组件的 `.local-section`/`.approval`/`.refinement`/`.meta`。

### P1-4 同级标题有三种字号

**问题**：实测详情页 11 个标题里，同为区块标题的 `h3` 出现 12px（英文原文 / 德语译文 / 图片对比 / 元信息）、13px（话题标签 / 链接 / 审核与排期 / 单篇优化）、14px（英文语义风险预扫）。`h4` 12px（产品分类 / 操作记录）。
**后果**：字号不再表达层级，读者要靠位置猜。
**方向**：定三级并全站统一（见 [DESIGN.md §3](DESIGN.md)）：页面标题 20px/600、区段标题 14px/600、子区段 13px/600、正文 14px、次要 13px、元信息 12px。

### P1-6 筛选条不吸顶

**问题**：工具条与筛选条随内容滚走。滚到第 15 条时看不到当前筛的是什么。

### P1-7 L3 信息常驻

**问题**：`MetaPanel` 393px 的右栏里包含"操作记录 · 上海时间"（低频回溯）与"组装时的告警"；`RiskPanel` 脚注常驻 `prompt v1 · <provider> / <model>`；`ApprovalPanel` 常驻 `发布尝试：<attempt_id>`。

### P1-9 付费动作与通过动作同为 primary

**问题**：`RefinementPanel.vue:101` 的"生成图片 · 约 US$0.0xx"与 `ApprovalPanel.vue:85` 的"通过并创建排期"都是 `btn-primary`。
**后果**：一页上两个 primary，其中一个会花钱。
**原则**：一页一个主动作。付费动作要显眼但不能是主动作的形态。
**方向**：排期保留 primary；优化区的提交改 `default` + 金额前置（金额已经在文案里，保留），并把整个优化区收进折叠区段——它是可选加工，不是必经步骤。
**改哪里**：`RefinementPanel.vue:99-102`、`TaskDetail.vue:397`。

### P1-10 双栏高度策略在长短文案上都不合适

**问题**：只读态 `.body { max-height: 52vh; min-height: 160px }`；编辑态 `.editing { height: 52vh; min-height: 320px }`（固定高，因为镜像层与 textarea 都绝对定位）。1366×768 下 52vh ≈ 400px。实测一篇 1,257 字符英文在里面要滚约 3 屏；而短文案（最短 119 字符）在编辑态下面留一大片空白。
**后果**：审校的主要动作（对着原文读译文）在一个 400px 的窗口里做。
**方向**：双栏改成页面内的主工作区，占据"吸顶条以下到视口底"的全部高度（`calc(100vh - <吸顶高>)`），两栏各自滚动；其余区段移到右栏或该区域下方的分段。短文案时栏高仍由容器决定，不留空白。
**改哪里**：`TextCompare.vue:177-183,202-208`、`TaskDetail.vue` 的整页纵向结构。

### P1-11 风险说明与正文标记重复

**问题**：`RiskPanel` 用 bullet 列出 `kind + quote + label`；同样这几处在正文里是黄色高亮，点中后 `.explain` 条又给一次 `kind + label`。同一信息三处。
**后果**：189px 用来说下面已经说过的话。
**方向**：删掉散文列表，保留"3 处需注意"的计数（可点，跳第一处）+ 正文标记 + `.explain` 说明条。`failed`/`stale` 时才需要面板。
**改哪里**：`RiskPanel.vue:22-28`、`TaskDetail.vue:379-385`（`.explain` 保留并强化）。

### P1-12 图片提示与图片相隔一屏半

**问题**：`还有 N 张图没查看。` 在 y≈150（吸顶条下），`ImageCompare` 在 y=1242。
**后果**：提示可见但不可达；她要滚一屏半才能响应它。
**方向**：提示改成可点（滚动到图片区并聚焦第一张未看的）；或把图片核对提到双栏对照同一屏的右侧/下方。6 张图给一个缩略图接触表（已有 `.strip`，把它提到主位）而不是逐张点。
**改哪里**：`TaskDetail.vue:330-333`、`ImageCompare.vue:93-107`。

### P1-13 历史行重复常态标签

**问题**：`冻结归档` 出现在 1,020/1,067 行；`in_neakasa.tech` 同样每行重复。
**后果**：两个不变量占据每行的文字预算。
**方向**：账号改成一列（或在筛选里已选定时不重复显示）；冻结与否由账号本身表达（账号名旁一个小图标），不另起文字。
**改哪里**：`HistoryPanel.vue:41`。

### P1-14 "刷新月历"与普通按钮同权

**问题**：它持发布锁、驱动 9223 号真实 Chrome 读后台，样式是 `btn btn-sm`。
**后果**：看不出这是一个"会动真实浏览器"的动作；多人同时点会撞锁（后端返回 409"有发布操作正在进行"）。

## 4. P2 — 视觉与交互质量

### P2-1 "没有硬闸告警"占一行

`TaskList.vue:53-55`：`alertCount === 0` 时渲染一行绿色"✓ 没有硬闸告警"。代码注释的判断是对的（"一个永远是 0 的筛选器只是噪声"），但替代方案仍然是一行字。**方向**：什么都不渲染。没有问题就是没有问题。
**改哪里**：`TaskList.vue:53-55`。

### P2-2 吸顶条会折行并撑高

`.bar { flex-wrap: wrap }`。13 个控件在窄于约 1,200px 时折成两行，吸顶高度从 43px 变成 ~80px，同时 `mark.mk { scroll-margin-block: 96px }` 这个"跳转时不被吸顶条盖住"的补偿值是写死的 96px，折行后不够。
**方向**：动作条内容减少到不会折行（P0-6 之后自然满足）；吸顶补偿改成由实际吸顶高度算（CSS 变量或 `ResizeObserver`）。
**改哪里**：`TaskDetail.vue:409-417`、`styles.css:148`。

### P2-3 历史与审校列表是两套行版式

同一种对象（一篇帖子）在两个界面的行结构、chip 用法、按钮文案（"查看" vs "查看归档"）都不同。
**方向**：一个共享的 `PostRow`，用 props 控制列的显隐（历史多一列日期与账号，少动作列）。
**改哪里**：`TaskList.vue` 与 `HistoryPanel.vue` 合并出共享行组件。

### P2-4 设置页"能改的"与"只能看的"同级并列

`SettingsPanel.vue` 先是一个 `<form>`，然后是平级的 `<section class="controlled">`。
**方向**：两段用明确的区段标题与不同表面（可编辑在卡片内，只读配置在页面底部的折叠区），或分成两个 `Tabs`。
**改哪里**：`SettingsPanel.vue:45-58`。

### P2-5 原生 `<select>` 与自定义控件混用

列表 2 个、历史 3 个、详情 1 个（优化类型）、链接区 1 个（CTA 预设）都是原生 `<select>`，与自定义的 `.btn`/`.tag` 风格不一致，且 71 项的月份下拉没有搜索与分组。
**方向**：统一 `Select`（可搜索、可分组、可清除）。
**改哪里**：各组件的 `<select>`。

### P2-6 破坏性确认按钮是 primary

`ReviewActions.vue:109` 的"确认"是 `btn btn-primary`（靛蓝），无论当前动作是"稍后再审"还是"这篇不发"。
**方向**：按 `form.action` 决定按钮 `danger`（skipped）或 primary（其余）。
**改哪里**：`ReviewActions.vue:109-111`。

### P2-7 模态框不接管焦点、Esc 无效、无焦点陷阱（实测）

见 [SCREEN_INVENTORY.md §7](SCREEN_INVENTORY.md)。打开后 `document.activeElement` 仍是被遮罩盖住的触发按钮；`@keydown.esc` 绑在 `<section>` 上收不到键；同时 `TaskDetail.onKey` 见到 `[role="dialog"]` 早退，Esc 既不关框也不返回。
**方向**：改用 `Modal`（自带焦点管理、`keyboard` 关闭、焦点返回触发元素）。
**改哪里**：`ReviewActions.vue:86-115`。

### P2-8 六种动作共用一个对话框

`titles` 表 + 6 个 `v-if` 说明段 + 3 组条件字段挤在一个 `<section>` 里。"下载并由我处理"和"这篇不发"共用同一个框架，但一个是转交、一个是终止。
**方向**：拆成三种意图（挂起 / 终止 / 转交）三个组件，共用一个受控的 `Modal` 骨架。
**改哪里**：`ReviewActions.vue:13-14,86-115`。

### P2-9 加载态全是纯文字

七处加载提示全是文字（`正在读归档…` 等），没有骨架屏，页面在加载完成时整体跳变。
**方向**：列表用 `Skeleton` 行（行数与行高固定，避免跳变），详情用分区 `Skeleton`，按钮用 `loading`。
**改哪里**：各组件的 `v-if="loading"` 分支。

### P2-10 排期按钮的 disabled 原因不可见

`ApprovalPanel.disabled` 是六个条件的或：`editing || loading || submitting || !eligible || !options?.available || !when`。界面上只有一个灰按钮。
**方向**：按钮包 `Tooltip`，文案由当前命中的第一个条件决定（现有 `.help`/`.blocked` 文案已经覆盖大部分情形，只是没有挂在按钮上）。
**改哪里**：`ApprovalPanel.vue:28,85`。

### P2-11 `{{link1}}` 占位符原样暴露

`LinkEditor.vue:29` 用 `<code v-text="'{{link' + (index+1) + '}}'">` 把模板语法显示给运营。
**方向**：按钮文案改"把这个链接插到正文光标处"，正文里的占位符渲染成一个不可编辑的行内标记（`Tag`）而不是花括号文本。**注意**：正文存储格式必须仍是 `{{linkN}}`（`core/localization.py:185` 的 `LINK_PLACEHOLDER` 与 `render()` 依赖它），这只是显示层的事。
**改哪里**：`LinkEditor.vue:29-31`、`TextCompare.vue` 的镜像层渲染。

## 6. 审校列表专项结论

提纲第 10 节逐项：

| 项 | 现状 | 目标 |
|---|---|---|
| 列表密度 | 1366 下 4 条、1920 下 7 条 | ≥12 / ≥18 |
| 行高 | 97px 与 121px 两种 | 单一值，44–56px |
| 缩略图 | 56×56 | 40×40（够认出是哪篇即可） |
| 标题层级 | 90 字德语摘要，14px，单行截断 | 同（摘要就是这个列表的"标题"），但要有稳定的行内位置 |
| 译文状态 | 只能从摘要是否为"还没有德语译文"推断 | 独立状态列：未翻译 / 机器 / 人工 / 旧提示词 |
| 平台 | 事实行里的纯文字 | 独立定宽列（FB / IG 图标 + 文字） |
| 图片张数 | 事实行里的 `1 张图` | 并入缩略图角标 |
| 发布状态 | 无（只有审校状态） | 与审校状态同列或第二状态列 |
| 排期状态 | `建议 9/13 周日 17:00 柏林` / `暂无建议时刻`，12px 灰 | 独立列，已排期加粗（现在 `.when.firm` 已经这么做，但位置太弱） |
| 审校状态 | 仅 `status !== 'pending_review'` 时出现在事实行 | 始终有一列 |
| 行主动作 | "查看"按钮，命中面积占行的 4% | 整行可点 |
| 行次动作 | "稍后再审" + 红色"这篇不发" 常驻 | 收进行尾 `Dropdown`，`这篇不发` 标 `danger` |
| 批量动作 | **无** | 见下 |
| 筛选 | 3 个页签 + 1 个开关 + 2 个原生 select，且不入 URL | `Tabs`（状态）+ `Select`（平台/月份/分类）+ 筛选 chip（只看告警）；全部入 URL |
| 排序 | 服务端固定（有时刻的按时刻升序，其余按 id） | 暴露列排序（时刻 / 原帖时间），默认不变 |
| 状态页签 | 三组（待处理 / 已挂起 / 已处理），计数客户端算 | 保留三组；计数改用服务端 `summary.by_status` |
| 月/分类筛选 | 原生 select，选项客户端算 | `Select`，选项用服务端 `summary.tags` |

**能不能快速扫 15–30 条**：现在不能（4 / 7 条）。按上表改造后 1366 下可到 12–14 条、1920 下 18–22 条，一屏半覆盖 30 条。

**能不能不读文字就区分四类**：现在不能——`done`（已处理）与 `waiting`（`not_ready`）用同一个灰底，`quiet` 与普通行无差别。目标是四种状态各有一个定位固定的视觉标记（状态列的图标 + 颜色），行底色只用来表达"已完结、不用管"。

**整行是否该可点**：应该。这是主动作，且能顺带解决命中面积问题。

**少用的行动作是否该进菜单**：应该——但"这篇不发"要保留在菜单里的可见位置并标 `danger`，不能藏进二级菜单。提纲第 12 节说"安全关键的决定可能值得可见"，这里的判断是：它需要**可达**（一级菜单项）但不需要**抢眼**（不是行内红按钮）。因为它有必填理由 + 模态确认两道门，误触成本可控。

**筛选该用什么形态**：状态用 `Tabs`（它是互斥的主分组，且带计数）；平台 / 月份 / 分类用 `Select`（多值、可搜索）；"只看有硬闸"用一个可关闭的筛选 chip（它是临时聚焦，用完就关）。不用工具栏抽屉——只有 4–5 个条件，藏起来反而多两次点击。

## 7. 审核详情专项结论

提纲第 11 节逐项，以及"审校时必须一直看得见什么"的结论。

### 7.1 必须常驻可见

| 内容 | 为什么 |
|---|---|
| 英文原文与德语译文（并排） | 这就是工作本身 |
| 当前那一处标记的说明 | 决定"这处要不要改"的唯一依据 |
| 三档标记计数 | "还剩几处没看"的进度 |
| 状态 + 源文是否已变 | 决定"我现在能不能动它" |
| 主动作（编辑 / 通过） | 她来这里的目的 |
| 未看图片数 | 防漏看德语图（业务上的硬要求） |

### 7.2 按需出现

| 内容 | 出现时机 | 承载 |
|---|---|---|
| 标签与链接编辑 | 进入编辑态，或有未确认项 | 主工作区下方的分段 |
| 排期时刻与范围 | 状态 ∈ {pending_review, edited} 且 `options.available` | 吸顶条 primary 的 `Popover`，或右栏决策卡 |
| 图片逐张对照 | 有图片时（常态）——但用接触表起步，不是单张轮播 | 主工作区的第二个标签页或右侧 |
| 优化（付费） | 折叠，默认收起 | `Collapse` |
| 第三方作者授权 | `capabilities.third_party` 为真 | 页面顶部 `Alert` + 动作（这是真警告，配得上满宽） |
| 组装告警（缺德语图回退原图） | `meta.compose_warnings` 非空 | `Alert`（内容问题，需要看见） |
| 风险扫描失败 / 过期 | `risk_scan.status ∈ {failed, stale}` | `Alert type="warning"` |

### 7.3 应移入抽屉或二级

| 内容 | 去哪 |
|---|---|
| 操作记录（`trail`） | `Drawer`，吸顶条"处理记录"入口 |
| `prompt v1 / provider / model`、`attempt_id`、`snapshot_id`、`source_fingerprint` | 诊断 `Drawer` |
| 图片自动比较指标（dHash / 形变 / 缩放 / 耗时） | 图片区的 `Popover`；无记录时不渲染 |
| 模板只读内容 | `Drawer` 或 `Modal` |
| 元信息里的作者/合作方/原帖时间/永久链接 | 保留但压缩成一行行内元信息（不需要 393px 的 `<dl>`） |

### 7.4 对提纲里那几个假设的判断

| 假设 | 判断 |
|---|---|
| 吸顶审校头 | **要**，而且是解决 P0-4 / P0-6 的主要手段。三段结构见 P0-6 |
| 专用主审校工作区 | **要**。双栏对照应占满"吸顶以下到视口底"，不是页面中段的 437px（P1-10） |
| 译文对比布局 | **保留现有的并排 + 标记 + 跳转**，这是当前设计最强的部分。三条实现细节（码点下标、重叠优先级、不用 smooth 滚动）必须原样移植 |
| 问题摘要 | **要，但不是散文列表**。改成三档计数（可点跳第一处）+ 正文标记 + 当前那处的说明条（P1-11） |
| 次要上下文面板 | **要**，右栏保留，但内容从"元信息 + 操作记录"换成"决策卡（状态 / 时刻 / 冲突 / 阻塞原因）+ 压缩的来源信息" |
| 抽屉承载历史 | **要**（P1-7） |
| 抽屉承载诊断 | **要**（P1-7） |
| 可折叠的优化控件 | **要**（P1-9） |
| 排期区仅在适用时出现 | **部分同意**。排期入口应常驻（它是主动作），但"为什么不能排"要从一块常驻文字变成按钮上的 `Tooltip`（P2-10）。不能因为不可用就把整个主动作藏起来——那样她不知道该往哪走 |
