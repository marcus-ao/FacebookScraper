## 1. 目的与寿命

**目的：收束需求边界。** 在和业务同事做需求访谈**之前**先出这一版，
让她们对着实物反应，而不是对着"你想要什么功能"这个问题许愿。

**寿命：先当道具，但技术选型上不堵死升级路。**

- 需求没收完就按"要长大"写 → 会在错误的抽象上花时间
- 完全按扔掉写 → 界面反馈好的时候要整个重写

分界线很具体：**只读的那部分从第一天起就是生产代码，假交互那层随时可扔。**

## 2. 核心架构原则：读全真，写全假

这是整个原型的地基，**写第一行代码前必须先立**。

```
GET  /api/tasks                    真 —— 从 archive/ + translated.jsonl + state/ 只读算出
GET  /api/tasks/<id>               真
GET  /api/tasks/<id>/image/<n>     真 —— 直接读归档字节（Demo board 已验证这条路）

POST /api/tasks/<id>/approve       假 —— 只写原型自己的本地文件
POST /api/tasks/<id>/skip          假
PUT  /api/tasks/<id>/text_de       假
```

**为什么这样切**：读的那半碰的是只读数据，怎么试错都无害；写的那半碰的是追加式
生产真相源（`translated.jsonl` / `needs_human.jsonl` / `published.jsonl`），
而那正是不能拿来试错的地方。

### ⛔ 一条不许破的规则

> **假实现必须返回和真实现完全相同的 JSON 结构。**

少一个字段、多一层嵌套，切换到生产那天前端就得跟着改——**"立马便捷切换"这个目标就没了**。

写假实现时，先写好返回结构，再填假数据；不要"先随便返回点什么，以后再说"。

### 切换到生产 = 改三个 handler

| | 原型 | 生产 |
|---|---|---|
| `approve` | 写 `web/_fake_state.json` | 调 `pipeline` 的批准路径 |
| `skip` | 同上 | 写 `needs_human.jsonl` 的终态 |
| `text_de` | 同上 | 追加 `translated_human.jsonl` |

**前端一行不用改。**

## 3. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **Vue**（单文件组件 + 构建链） | 界面有脏状态、保存/放弃、实时校验、编辑态——原生 JS 会很快变成手写状态机。Vue 对"列表 + 详情 + 表单"上手最快，以后交给别人维护心智负担小 |
| 后端 | **FastAPI + uvicorn** | 从原型到 M2 一次不用换。stdlib `http.server` 到 M2（多用户并发 + 写入 + 登录）必须换掉，等于把切换成本推到最后 |
| 部署 | **开发机构建，`dist/` 拷到生产机** | 见下 |

### ⚠️ 那台常开的机器不装 Node

Vue 的构建产物是静态文件。**在开发机上 `npm run build`，把 `dist/` 拷过去**，
FastAPI 当静态文件伺服。

于是生产机上：Python 依赖数量不变（`playwright` / `httpx` / `openai` / `Pillow` / `tzdata`
＋ `fastapi` / `uvicorn`），**不需要 Node 运行时、不需要 `npm install`、断网也能跑**。

构建链只存在于开发环境——这是同时满足"用 Vue"和"不破坏极简依赖"的唯一方式。
（项目原本 32K 行代码只有 5 个依赖，这个风格值得保住。）

## 4. 目录与模块图约束

```
FacebookScraper/
  web/
    api/          FastAPI 应用；只读端与假写入端分开放，切换时只动后者
    ui/           Vue 源码（src/、package.json…）
    ui/dist/      构建产物。**生产机上只要这个目录**
```

### ⛔ 模块图规则

> `web/` **可以** import `core/` 和 `pipeline/`；
> **任何生产代码都不许 import `web/`。**

这样 `web/` 是模块图上的一个叶子，`tests/tests_hygiene.py` 的 DAG 护栏会**自动**
守住 docs/REQUIREMENTS.md §5.2 那条约束（Web 层不许复制流水线逻辑）——不用靠人记。

放在 `Demo/` 下面的"自由"是假的：那里不参与测试、不受 DAG 检查，而这个原型如果真要
长成 M2，那些检查正是需要的。

## 6. API 契约

### `GET /api/tasks`

```jsonc
{
  "tasks": [
    {
      "id": "in_neakasa.tech/3965025107383038890",
      "platform": "instagram",
      "thumbnail_url": "/api/tasks/<id>/image/0?variant=de",
      "text_de_excerpt": "Entdecke den neuen Neakasa M1 Pro – jetzt mit …",
      "image_count": 5,
      "schedule": { "at": "2026-09-15T10:00:00+02:00", "channel": "instagram" },
      "hard_alerts": [
        { "code": "money_not_mapped", "label": "新金额 $89.99 未收录" }
      ],
      "risk_count": 3,
      "author_flag": null,          // 常态 null；仅第三方作者时给值
      "status": "pending_review"    // 见 §7
    }
  ],
  "summary": { "total": 62, "with_hard_alerts": 3 }
}
```

**排序：按 `schedule.at` 升序**（最急的在最上面）。
顶部一条筛选：「3 篇有硬闸告警 → 只看这些」。

> ⛔ **不做"有告警"和"常规"两个 tab。** 分 tab 的实际结果是只有第一个被看，
> 第二个 tab 里的会被批量通过——那正好绕过了这个界面存在的意义。

## 7. 状态模型

> ⚠️ **已扩到七态，以 [FUNCTIONALITY §5.4](../docs/FUNCTIONALITY.md) 为准。**
> 下面这四态仍然准确，只是不完整。新增的三个：
> `snoozed`（挂起，默认 3 个工作日后自己回来）、`skipped`（不发，终态，必须填理由）、
> `handed_off`（她自己去后台发，终态，可选回填原帖链接）。
> **`skipped` 与 `handed_off` 必须分开**——前者是"决定不发"，后者是"决定不用系统发"，
> 合并会让"这个月发了几篇"算错。

**业务视角四态**，不是生产侧的发布五态——后者是系统视角，直接摆给她看只会造成困惑。

| 状态 | 含义 | 界面表现 |
|---|---|---|
| `pending_review` | 待我审 | 正常显示 |
| `edited` | 我改过（存在人工版译文） | 标一个「已修改」小标记 |
| `approved` | 已通过，等系统提交 | 整行变灰/半透明 |
| `scheduled` | 已排期 | 同上 + 排期时刻加粗 |

**没有"退回"。** Q1 选了"能直接编辑"之后，退回就没有存在必要——保留一个只会制造
没人处理的死信箱（退给谁？谁改？什么时候改完？）。发现不对就直接改，改完通过。

**但有一个终态出口：`skipped`（这篇不发）。** 它和退回不一样——它是决定，不需要谁来接手。
详见 §11。

## 8. 两种标记，两个时机，两种颜色

⛔ **这是两个功能，不是一个。混成一种颜色，用几次她两种都不信。**

| | 🔴 确定性检查（红） | ⚠️ 风险预扫描（黄） |
|---|---|---|
| 问的是 | 译文有没有把不该动的动了 | 这篇翻起来哪里容易翻坏 |
| 时机 | **翻译之后**比对原文与译文 | **翻译之前**扫英文原文 |
| 谁做 | regex（`core/translated.py` 已有三个函数） | LLM |
| 成本 / 误报 | 零 / 零 | 一次调用 / 会误报 |
| 语义 | **这里错了** | **这里注意看** |
| 覆盖 | 金额、话题标签、@提及、英制单位、尺码 | 俚语双关、歧义句、美国限定表述 |

### 风险预扫描只做那三类

金额、单位、标签这三类**已经有确定性实现**（`money_preserved` / `review_numeric_flags` /
`hashtags_preserved`），不需要 LLM。让 LLM 去做它们只会花钱买误报。

LLM 只负责真正模糊的三类：

| 类型 | 例子 | 为什么要标 |
|---|---|---|
| 俚语 / 双关 | "purr-fect"、"paw-some" | 直译必然翻坏，需要人改写 |
| 歧义句 | 主语不明、代词指代不清 | LLM 翻译时会自作主张选一个，可能选错 |
| 美国限定表述 | Black Friday、Prime Day、"ships from LA" | 搬到德国站要么不适用要么要改 |

📌 **第三类天然接上"这篇该不该搬"** ——美国限定表述被标出来，本身就是筛选依据。
这也是 `skipped` 那个动作的主要触发场景。

### ⚠️ 原型阶段不实时调 LLM

**预跑一次，结果存成静态文件。** 理由：零成本、零延迟、可重复演示，
而且演示当场不会因为 API 抖动而尴尬。接口契约不变，生产时换成实时调用即可。

## 9. 人工版译文

### 为什么不用"字面同构"

德语图那套是：`images_de.jsonl` 记录程序产出，`media_de/01.jpg` 是产物本身，
**人工直接放一张进去就能盖掉程序那张**（README：人工 > 程序）。

字面搬到文本上就是让她改 `text_de.txt`。但那有一个图片没有的问题：
**程序怎么知道这个文件被人改过？** 图片靠"文件在不在"就够了，
而 `text_de.txt` 本来就存在，只能靠比对内容哈希——脆弱，一次编码变化或换行差异就误判。

### 采用显式记录

新增账号级 `translated_human.jsonl`：

| | 机器译文 | 人工版 |
|---|---|---|
| 真相源 | `translated.jsonl` | **`translated_human.jsonl`** |
| 派生副本 | `text_de.txt`（人工版优先渲染） | 同一个文件 |

三个好处：追加式（和项目其它真相源一致）、能顺带记 `actor` 和时间（docs/REQUIREMENTS.md §4.3
本来就要求）、`--review` 只重建派生副本 **永远碰不到人工版**。

### 🐛 附带必须修的 bug

`tools/review_report.py:323` 是无条件重写：

```python
text_de.write_text(de, encoding="utf-8")   # 没有任何"人工改过就别覆盖"的判断
```

**今天她如果去改 `text_de.txt`，改动会静默消失。** 与 `media_de/`（人工不得覆盖）
的语义正好相反，这个不对称没有人设计过。

### 原文变更时的处理

译文绑 `source_text_sha256`，原帖被编辑、哈希对不上则译文作废重译。**人工版不能照搬这条**——
那是人花时间做的。

> 保留人工版，标红「原文已变更，请复核」（`stale: true`），重新进待审队列。

直接丢弃她的劳动，两次之后她就不改了；完全不管则德国站内容会和原帖对不上且没人知道。

## 10. 列表页

**一行的唯一职责：回答「我需不需要点开这篇」。** 所以显示的是异常，不是内容。

```
┌──────────────────────────────────────────────────────────────────────┐
│ ┌────┐  Entdecke den neuen Neakasa M1 Pro – jetzt mit …              │
│ │缩略│                                                                │
│ │ 图 │  🔴 新金额 $89.99 未收录          ⚠ 3 处需注意                 │
│ └────┘  📅 9/15 周一 10:00 柏林 · Instagram · 5 张图                  │
│                                          [查看]  [通过]  [这篇不发]   │
└──────────────────────────────────────────────────────────────────────┘

没有告警的：
┌──────────────────────────────────────────────────────────────────────┐
│ ┌────┐  Der Neakasa S1 Pro macht die Fellpflege …                    │
│ │缩略│  📅 9/16 周二 17:00 柏林 · Facebook · 1 张图                   │
│ └────┘                                    [查看]  [通过]  [这篇不发]  │
└──────────────────────────────────────────────────────────────────────┘
```

**干净本身就是信号**——"这篇可以快速过"。

### 不放进行里的三样，以及为什么

| 字段 | 为什么不放 |
|---|---|
| 原帖发布时间 | 她关心"什么时候发出去"（排期时刻），不是"US 站什么时候发的" |
| actor（谁改过 / 谁批过） | 留痕必须记，但**列表上显示会诱发互相盯梢**，几个人的小团队里是负面效果。放详情页 |
| 状态文字标签 | 视觉区分（已通过的行变灰）比多一列文字省地方 |

### 通用规则：常态不显示，异常才显示

近期 IG 帖 35/36 是合作帖——那是常态，每行都标就是噪声。
**只有第三方作者才标出来**，因为那才是需要她停下来的信号。

## 11. 详情页

三块：正文对比、图片对比、元信息。

### 11.1 正文对比

**左右并排，英文 ↔ 德语。** 德语侧默认只读，点「编辑」才进入编辑态。

> 为什么不做永远可编辑：审校的**主要动作是读不是写**（大部分篇她不会改），
> 永远可编辑会让光标乱跳、误触改动。更重要的是，显式编辑态能带出
> **「你正在修改机器译文」**这个语义——它会产生一条 `translated_human.jsonl` 记录，
> 是有分量的动作，不该像改个输入框那么随意。

**⚠️ 长度是这一块的真正难点。** 实测近 90 天 62 篇图文帖：

```
正文长度（字符）  最短 119 · 中位 843 · 75% 1346 · 最长 2838
```

德语通常比英语长 10~20%，所以一篇下来她要读 1700~3400 字符。**在这个长度下光高亮不够**——
她会扫一眼觉得"差不多"就过了。

**必须有「下一处 →」跳转按钮**，逐个跳到红/黄标记。它把"检查"从一个开放任务
变成一个有终点的任务（跳到没有下一处 = 都看过了），这个差别在实际使用中很大。

加分项：右侧缩略滚动条（像 IDE 那样在滚动条上标出全部标记位置）。

**两栏不做滚动同步**——德语更长，同步会逐渐错位。但**点高亮跳转时两边一起定位到
对应段落**。

### 11.2 图片对比

**左右并排**（原图 ↔ 德语图），适合逐字核对型号、优惠码、展位号。

> 演示时可以用 `Demo/` 里那个金线拖动的形式——**但那是给人惊叹用的**，
> 实际审校要的是两边同时可见、能放大。原型以实际可用为准。

**多图导航：底部缩略图条 + 主视图。** 实测张数分布：

```
 1 张 ████████████████████████████ 45 篇（73%）
 2 张 ███ 5    4 张 ██ 3    5 张 ███ 5    8 张 █ 2    10 张 █ 2
```

73% 是单图，但 27% 是轮播，最多 10 张。

- 纵向堆叠 10 组并排 → 一屏又一屏，**很容易漏掉中间某张**，而漏看一张德语图正是要防的事
- 标签页 → 看不出"我还有几张没看"
- **缩略图条可以给看过的打勾**，让"全部核对完"这件事可见 ✅

**没逐张看完就点通过：提示不拦。**（"还有 3 张没查看"）硬拦人工是这个项目的反模式。

### 11.3 元信息

排期时刻与渠道、原帖链接、作者（原创 / 合作 / 第三方）、四项图片指标、`trail` 留痕。

### 11.4 编辑时的实时校验

编辑德语正文时，`money_preserved` / `hashtags_preserved` **实时跑**（前端调 API，几十毫秒），
当场标红。

**但保存时不拦。** 这几个检查是**给人看的辅助**，不是硬闸——她可能有正当理由改一个金额
（比如原文写错了）。硬拦人工修改等于说"机器比人懂"，而这个系统的既定原则正好相反。

## 12. 屏幕假设

**只考虑桌面**（办公室电脑，≥1440px 宽）。左右并排在手机竖屏上物理不成立。

✅ **2026-09-11 业务确认成立，问号关闭。** 审校人在上海办公室用桌面电脑、中文界面，
工作时间上海 08:00–19:00。**不做移动端布局。**

⚠️ 但有一件事变了，不影响布局却影响推送设计：**她的审校时间是随机的，完全跟着飞书
推送走**——没有推送她就不会想起来打开这个页面。所以飞书卡片是这个系统的主入口，
不是通知，见 [FUNCTIONALITY §4.2](../docs/FUNCTIONALITY.md)。

## 13. 这个原型要回答的访谈问题

**做原型的正确用法：把不确定的需求做成界面上一个具体的东西，让她对着实物反应。**

| 界面元素 | 想套出的答案 |
|---|---|
| **`[这篇不发]` 按钮** | 「什么情况下我会点这个？」→ 直接拿到**内容取舍规则**，而且是她自己带场景说出来的 |
| 62 篇的列表长度 | 「每周 4~5 篇是什么感觉」→ 铺垫"你愿意每周花多少时间" |
| 排期时刻确认弹窗 | 她会当场对**时刻**和**渠道**提意见 |
| 真实德语译文 | 引出"这个词我们不这么说"——假数据只会引出"看起来不错" |
| ⚠️ 黄色风险标记 | 她认不认这类提示、会不会看 |
| 图片四项指标 | 她关不关心这些数，还是只看图 |

> ⚠️ **演示前必须说明：原型上点的"通过"不会真的发帖。** 否则她会以为已经排了。
